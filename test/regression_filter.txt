# Regression manifest — tests that pin a specific, previously-fixed bug.
#
# WHAT THIS IS
# ------------
# Each entry below was written to make one concrete bug non-recurring: a
# miscompile, a crash, a leak, a double-free, a wrong diagnostic. They are the
# suite's institutional memory. Losing one silently re-opens the bug it pins.
#
# This is the MIDDLE tier of the three-tier strategy:
#
#   test/light_filter.txt   ~145s  every phase of a plan      (breadth smoke)
#   test/regression_filter.txt     subsystem under change     (THIS FILE)
#   full sweep              ~51min pre-merge / pre-tag        (everything)
#   test/release_filter.txt        per cross-compiled target  (ABI/ISA/endian)
#
# HOW TO RUN
# ----------
#   ./regression_tests.sh --manifest test/regression_filter.txt
#   ./cajeta_tests.sh $(grep -v '^#' test/regression_filter.txt | grep .)
#
# Run the whole file before a release, or grep out the one section covering the
# subsystem you are changing and run just that.
#
# NOTE ON COST
# ------------
# This file is NOT cheap. Most entries JIT-compile a Cajeta program, and the
# dominant cost is per-process stdlib prime (~16s per distinct suite), not
# per-test. Running one section is fast; running all of it approaches the full
# sweep. Prefer sections.
#
# PROVENANCE
# ----------
# Generated by an Opus 4.8 multi-agent audit of all 681 test files, then
# validated: every name below resolved against `cajeta_test --gtest_list_tests`
# at generation time. Tests are listed fully-qualified (Suite.test) so a rename
# breaks loudly instead of silently dropping coverage.
#
# FORMAT: one `Suite.test` per line; `#` comments; blank lines ignored.
