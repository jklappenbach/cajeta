6. **Views as K/V in HashMap — multi-session structural piece.** `[mode-agnostic]` — probed 2026-05-18: `HashMap<int32, view>` and `HashMap<view, int32>` both fail at JIT verify today, with multiple interlocking issues. Surfaced bugs:
   - **Return-type mismatch in `get()`.** The V[1] miss-default trick assumes V's storage shape is uniform (primitive value or class pointer); for V=view, the array element is the view's inline body (struct), and the function returns `ret %struct %x` against a declared `ptr` return type. The class-pass-by-pointer rule in `ReturnStatement` correctly KEEPS views inline (via the `!foundIsView` guard) but the function-return-type computation upstream still picks `ptr`.
   - **Lambda parameter type mismatch.** Iteration paths (`forEach((V) -> void)`, `reduce(V, (V, V) -> V)`) hit `Call parameter type does not match function signature!` — the lambda's V param needs to flow through the closure ABI as either inline struct or pointer, and today the indirect-call argument type doesn't match the called function's formal parameter type.
   - **Design questions not yet resolved.** Does `view.hash()` exist? Does `view == view` compare bytes / body-pointer / something else? When `m.put(k, viewV)` runs, does HashMap copy the view's BYTES into vals[idx] or store the view's body pointer? Same lifetime issue: the view doesn't own its buffer, so storing a view past the buffer's lifetime dangles. None of these have stdlib-side decisions yet.

   Worth a dedicated multi-step session: (1) decide copy vs reference semantics for views in templated containers, (2) wire `view.hash()` / `view ==` if missing, (3) fix the V-shape-dispatch in HashMap.get's miss path (might need a `defaultOf<V>()` intrinsic instead of the V[1] trick), (4) fix lambda-arg coercion for views. Defer until there's a real stdlib case driving the requirements — composition with `class { view header; }` is the immediate workaround.
