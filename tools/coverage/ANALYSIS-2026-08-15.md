# Per-test coverage analysis — 2026-08-15

Supersedes `ANALYSIS-2026-08-10.md` for the numbers. That document's *caveats*
still hold and are repeated below; two of its *conclusions* do not, and are
corrected.

**Method — grafted, not re-measured.** The 2026-08-10 index survived in the
`cajeta-six` clone. Only 278 of 6,056 enumerated tests were unmeasured and 90
indexed units no longer existed, so re-deriving 5,778 unchanged line sets was
not worth an instrumented build plus 2h49m at 32 servers. The 5,778 were
grafted (`tools/coverage/graft_index.py`), the 90 phantoms dropped, and the 278
measured here on the fork-server harness against a fresh instrumented `-O0`
build. 272 produced trees; the other 6 are `DISABLED_`, which gtest enumerates
but never runs.

Freshness is now checkable rather than assumed:
`tools/coverage/check_index_freshness.py` reads **0 unmeasured / 0 phantom /
0 dangling**, with the 6 DISABLED reported separately.

## Corrections to the 2026-08-10 conclusions

**1. "The 37.8 s stdlib prime — 77% front-end, uncacheable to disk."** The
premise held when written; the number does not. Two-stage SLL/LL parsing
(`b48018a2`, 2026-08-15) took the prime to **4.9 s**, because that 77% was
almost entirely ANTLR adaptive prediction — measured `lex 85 ms / parse
14329 ms / visit 43 ms` over 350 files. See `bench/kernel-startup/FINDINGS.md`.

**2. The fork-per-test server's payoff is now much smaller.** It exists to
amortize that prime across a slot instead of paying it per test, and it is why
the original measurement fit in 2h49m rather than 10+ h. With the prime 7×
cheaper, the architecture is not wrong but its return is a fraction of what it
was when designed. Any future decision that leans on "the prime cannot be
cached, so fork" should re-derive the number first.

## Caveats — all still true

1. **Line coverage is not behavior.** A zero-unique test may hold the only
   assertion of a value, an ordering, or a diagnostic; this repo's ownership
   pins are exactly that shape. The 4,818 redundant units are a review queue,
   not a delete list. Spec §5.1 and §7 exist for this reason.
2. **Subprocess blind spot.** Suites driving the `cajeta` CLI as a child
   process contribute no attributed coverage. This is most of the zero-coverage
   list: `BuildToolCommands.cpp` (3,100 lines) and `ArchiveCommands.cpp`
   (1,317) are heavily exercised through the CLI and measure as untouched. Part
   of the gap list is a measurement artifact, not proof of untestedness.
3. **Durations mix two eras and must not be used.** The 5,778 grafted units
   were timed before two-stage parsing, the 272 new ones after it. Line sets
   are independent of parser speed and merge cleanly; timings do not. Any
   suite-time attribution over this index is invalid — re-measure, or take
   timings from a single era.
4. **Instrumented durations** run ~3–4× the -O2 cost; rankings hold.

## Dispositions this feeds

The 4,818 strictly redundant units are the input to plan unit 3, where each
gets fold / promote / delete with a recorded rationale (spec §7). The 184
zero-coverage files are the input to unit 6, minus whatever caveat 2 explains
away — which should be established before writing tests for them.
