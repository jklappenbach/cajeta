# Per-test coverage analysis — 2026-08-10

**Method.** Full per-test measurement on the fork-server harness: 5,868 of
5,872 enumerated units ran (the 4 absent are the fork meta-tests, which nest
servers), each in its own forked child with its own gcda tree; the parent's
post-prime `__gcov_reset` keeps the shared stdlib prime out of every tree, so a
unit's lines are what THAT test exercises. Instrumented `-O0` GCC build against
the fork LLVM. Wall time 16:14–19:03 (2h49m) at 32 servers. Results: 5,738
passed, 62 unique failures (`.coverage/analysis/failures.txt`), exactly 1
signal death. Universe: **49,309 distinct covered lines** across **258 of 455**
`src/cajeta` files.

**Caveats.**
1. Line coverage is not behavior: a zero-unique test may still hold the only
   assertion of a value/ordering/diagnostic (this repo's ownership pins are
   exactly that shape). Everything below is a review queue, not a delete list.
2. Subprocess blind spot: suites that drive the `cajeta` CLI as a child
   process (IncrementalBuild — 802s with a ZERO-line tree — and the buildtool
   family) contribute no attributed coverage. Part of the §3 gap list is this
   measurement artifact, not proof of untestedness.
3. Durations are instrumented-build times (~3–4× the -O2 cost); rankings hold.

## 1. What can be optimized

- **Landed during this exercise:** the fork-per-test prime server (plan Unit
  3F). The 37.8s stdlib prime — 77% front-end, uncacheable to disk — is now
  paid once per server instead of once per test/process. This is why the
  measurement itself fit in 2h49m instead of a projected 10+ h.
- **The remaining per-test cost is each test's own user-snippet compile.**
  The nucleo Table family is the extreme: every test compiles essentially the
  same ~18.8k-line surface for 6–13 min (instrumented) each. Lever: suite-level
  fixtures (compile the corpus once per suite) or the spec'd [C5] per-snippet
  cache.
- **Stress tests to cap to functional reps** (duration, unique lines):
  `GradAllTests.namedErrors` (917s, 13), `NumpyOpsTests.npyNumpyInteropDtypes`
  (885s, 0), `ConcurrentCompileTests.stressManyConcurrentCompiles` (797s, 0),
  `TableCoreTests.accessorTypoFailsCompileAndSetIsDeterministic` (758s, 0),
  `NullableColumn.bitmapIsSeparateAndAligned` (674s, 0),
  `XpuCpuPoolTeardown.poolWorkersJoinWithTheirModule` (636s, 0), plus
  `OwnershipLeakProbe.benchScaleStaysBounded` (load-shaped by design).
- **Reuse-eligibility is solved structurally:** under the fork server every
  test gets the cached stdlib; recommend making fork mode the sweep default.

## 2. Duplicates — merge / drop candidates

- **4,730 of 5,868 tests (81%) hold zero unique lines**; the tests holding
  zero unique lines consume **92% of total suite time** (75.6 of 81.7
  instrumented CPU-hours).
- **Greedy set cover: 879 units retain 99.50% of all coverage** — 4,989 units
  (85% of the battery) add no lines. (`.coverage/analysis/coverage-optimize.json`
  has keep/drop lists.)
- Highest-yield folds (identical or near-identical ~18.8k-line footprints,
  6–13 min each):
  - the nucleo table family — Pushdown/ZoneMap/BPlusIndex/GroupBy/
    NullSemantics/Rolling/Resample/SortJoin/FilterSelect/TableArrow/TableCore —
    dozens of tests, one shared footprint: fold per suite into one
    multi-assertion program each (the ownership probes' consolidation pattern:
    `stringElementModeMatrix` replaced 14 probes with one compile).
  - `FuseAllocation`/`FuseSugar`: 4 tests with byte-identical 18,277-line
    sets at ~10 min each → one program.
  - `CarameloSpatialIndexDeviceTests`: ~20 tests × 9 lines each →
    parameterize into one.
- Recommended shape: the 879-unit covering set (plus the pinned
  assertion-bearing tests it omits) becomes the **routine gate**; the full
  battery becomes nightly/pre-release only.

## 3. Gaps — where no test reaches

**197 of 455 files have zero attributed coverage** (`gaps.txt`). After
removing the subprocess blind spot (buildtool/CLI), the real holes:

- **The debugger stack**: DapServer (1,266+206), DebugController,
  DebugTypeTable, ValueInspector, DebugVars, DebugLocTable (~2,700 lines) —
  no automated driver exists.
- **`ObligationReplay.cpp` (328 lines)** — the D1 incremental-build defect
  lives HERE and its deterministic 3-command repro is documented in the
  compile-cache plan but not encoded as a test.
- **`CajetaJitHost.cpp` (2,076)** — the JIT host path (vs the test harness's
  own JIT路径); confirm reachability.
- **`SynthesizedMockClass.cpp` (200)** — mock synthesis untested.
- **OptixAccel (487)** — device-gated; expected on a non-Optix runner.
- Worst-covered (not zero) files ranked in `report.txt`.

## Recommended sequence

1. Triage the 62 failures — 32 are the entire JsonSynthesizerTests suite and
   13 CajetaMcpServerTests: two systematic reuse/fork-context issues, not 45
   independent bugs. 6 overlap the interrupted sweep's list.
2. Fold the nucleo/Fuse/Caramelo families (§2) — roughly −1,500 tests and
   −30–40% of suite time on their own.
3. Cap the §1 stress whales to functional repetitions.
4. Make fork mode the sweep default; adopt the 879-unit covering set + pins
   as the routine gate.
5. New tests: DAP/dbg driver, ObligationReplay (encode the D1 repro),
   SynthesizedMockClass; decide CajetaJitHost reachability.

Data: `.coverage/index/` (per-test line sets), `.coverage/analysis/`

failures.txt).

## Addendum — failure triage (post-delivery)

45 of the 62 failures are TWO causes, not 45 bugs:

- **JsonSynthesizerTests ×32 — REAL reuse defect.** Every failure is the
  same runtime throw: `Json.toBytes<T>: synthesizer not engaged`
  (Json.cajeta:94). On the reused-context path a fork child's compile never
  re-engages the synthesizer registry for a novel `toBytes<T>` instantiation;
  the ReuseHazard fresh-fallback path passes the SAME tests (~126s — fresh
  compile cost). Top follow-up: wire synthesizer engagement into the reuse
  path the way the fresh Compiler ctor does it. Suspect interaction with
  fcb9f3af (stdlib-resident method-template instantiations now survive the
  epoch) is unconfirmed — engagement may have been missing on this path all
  along, masked by the fallback.
- **CajetaMcpServerTests ×13 — environment, not a bug.** The tests exec the
  sibling CLI at `build-cov/src/cajeta`, which was never built (only
  cajeta_test was). Build the `cajeta` target in the coverage tree; this also
  shrinks the §3 subprocess blind spot.

Remaining 17: EinsumSynthesis ×4 and TableLoaderMaterialization ×3 (overlap
the interrupted sweep's suspects — likely the same reuse/emit family as the
Json defect), plus 10 singles across ownership/lint/fiber suites — untriaged.
