# Changelog

## Unreleased

## 0.55.0 (2026-11-27)

- **A `@Device` helper that takes `Shared<T>` panels reads its tile factors right on Vulkan.** A helper given a kernel's shared arrays (`static void tile(.., Shared<float32> rowF, Shared<float32> colF, ..)`) and doing a tile epilogue there (`mc.scaledAccumInto(facc, rowF, colF)`, `facc.rank1Accum(rowG[16], colG)`) computed wrong values on the spirv backend: every row read row 0's factor, since an element offset taken off a panel parameter did not step there, and a slice such as `rowG[16]` became a byte offset that nothing rooted either. A scalar access through such an offset, or through a chain of them, is now one access rooted at the workgroup array once the helper inlines, as the same epilogue in a kernel body already was. It lets a tile kernel's body be one helper shared by two kernels (in dev.cajeta.ml.kernels, the dense block GEMM and its MoE form).

- **A method generic over a vector width.** `public static Vector<int32,N> twice<uint32 N>(Vector<int32,N> v)` was refused with `CAJETA_ERROR_VECTOR_LENGTH` ("Vector length N must be a positive integer literal constant"): a method's own value parameter could not be a `Vector` length in its signature. It now compiles, and each call width (`twice<4>(a)`, `twice<8>(b)`) is its own instantiation. A kernel can call such a `@Device` helper too, including through a class template's type parameter (`P.lowBytes<64>(q, plane, g)`); that call was refused with "type argument '64' for `N` is not a device type here". A block format in dev.cajeta.ml.kernels writes its unpack once and the cpu driver runs it on 32- and 64-byte vectors.

- **`Unroll.from(start)` writes a kernel's constant `for` loop out.** `for (int64 g = Unroll.from(0L); g < 4L; g = g + 1L) { .. }` in a `@Kernel` or `@Device` method is lowered as four copies of its body with `g` a constant in each, so a shift count or an offset computed from `g` is an immediate and no loop reaches the device compiler. The start, bound and update must be compile-time constants; otherwise the build refuses with "Unroll.from: the loop's start, bound or update is not a compile-time constant, so it cannot be written out". An 8-row quantized GEMM whose unpack shift depends on the loop counter ran at 110% to 148% of its hand-unrolled twin's time on the cpu as a loop and at 91% to 104% with `Unroll.from`.

- **`k.registeredName()` gives the name a kernel registers under.** In the class that declares `@Kernel k`, `k.registeredName()` is a `String` constant: the name `Device.kernelAvailable`, the manifest and the census use. Inside a class template it is the current instantiation's name (`Own_test_Two_run` in `Own<Two>`), which host code had no way to spell, so a library written over a type parameter can ask whether its kernel is available and hand its name to a tile family. A generic (method-template) kernel is refused, since it has one name per launch type.

- **A kernel's launch-block facts are its own, not a namesake's.** The compiler collected the launch sites of every `@Kernel` under the bare method name, so two kernels called `gemm` or `tile` in different classes shared one verdict: a bounded kernel was refused as `[xpu-kernel-unbounded]` for another class's derived block, and on amdgpu a kernel was budgeted registers for a namesake's workgroup size (in cajeta-llm, `MmqProbe.q4kF16CoopKernel` was sized for 128 threads when its own block is 32). Launch sites are now keyed by the kernel's qualified name, and a bare `kernel.launch(..)` resolves to the launching class's own kernel before any other of that name.

- **A class template's own name inside the template means the current instantiation.** `Box.inc(T.value())` inside `Box<T>` used to resolve `Box` to a wildcard instantiation, whose body then failed on `T.value()` with `unknown type 'T'`; a `@Kernel` in a class template could not call the class's own `@Device` helper by name (`Own.plus(..)` in `Own<P>` was refused as a device builtin). Both now resolve to the instantiation being compiled, so a template can factor its code into static helpers and still call its type parameter's statics from host code and from a kernel.

- **A device helper's two arms stay selected on the cpu when the arm not taken shifts out of range.** A helper such as `if (j < 4) { return (a >> (8 * j)) & 63; } int32 s = 8 * (j - 4); return ((b >> s) & 15) | ..;` called in a short constant-trip loop of a kernel returned the two arms OR-ed together on x86 (262 of 768 values wrong in a Q4_K header decode; the GPU backends and the host were right). The fault was in LLVM's x86 instruction selection, which turned the blend of the two arms into an OR on the strength of the dead arm's lanes being "known zero" when they were poison. The LLVM fork no longer makes that rewrite unless the skipped lanes are known not to be poison. It takes effect with the next toolchain; v0.54.3 and earlier have the fault (specs/cpu-widened-loop-or-miscompile-spec.md).

- **A kernel template's piece that lacks a method is refused by the piece's name.** A `@Kernel` in a class template can call its class parameter's `@Device` methods (`P.fold(..)` in `Driver<P>`), each instantiation inlining its own. When the class bound to `P` had no such method the build said only "unsupported construct, device builtin 'P.finish()'". It now names the instantiation's class and the missing method: "P is test.Thrice in this instantiation, which has no @Device method finish taking 1 argument(s)" (kernel-drivers 1.1.3).

- **A wave kernel's lane that reads four `float16` elements in a row reads them with its neighbours in one step on the cpu backend.** A GPU-shaped kernel often gives each lane a few consecutive elements of a row (`x[i]` to `x[i + 3]`, with `i` four or eight apart from lane to lane). The index is 32-bit arithmetic the vectorizer cannot prove free of wrap, so every element was loaded and inserted on its own: 256 single-element loads a step in cajeta-llm's attention kernel. The four reads are now one call whose widened form checks at run time that the lanes follow each other and then takes the whole wave in one read; when they do not, it reads lane by lane as before. The values are the same bit for bit. `CAJETA_XPU_CPU_HALF_QUAD_PER_LANE=1` restores the per-element reads (gpu-kernel-parity 23.1.0).

- **`exp` in both arms of one branch is one call in a wave kernel on the cpu backend.** A widened work-item loop runs both arms of an `if` for every lane, so `if (u > m) { c = Math.exp(m - u); .. } else { w = Math.exp(u - m); .. }` made two `exp` calls where a GPU makes one. The two calls are now one call ahead of the branch that takes both arguments: it makes one scalar `exp` for each arm that has lanes in it, so a branch every lane takes the same way costs one. Each arm reads the value its own call would have returned. With the grouped read above, cajeta-llm's head-128 prefill attention kernel went from 8.6 to 5.5 ms a launch in a lifted harness (the cpu-only kernel takes 3.8). `CAJETA_XPU_CPU_EXP_PER_ARM=1` restores a call an arm (gpu-kernel-parity 23.1.0).

- **A wave kernel's `float16` reads are converted 16 lanes a step on the cpu backend.** A `float16` buffer element read and widened to `float32` inside a widened wave kernel was carried as a vector of `half`, which x86 without AVX512-FP16 takes apart element by element. The read is now 16 raw bits and the widening is a 16-lane F16C conversion; the values are the same bit for bit. About 15% on cajeta-llm's 8B prefill attention kernel (10.0 to 8.6 ms a launch). The lanes' elements are still loaded one at a time where each lane reads its own offset under a per-lane mask. `CAJETA_XPU_CPU_HALF_PER_LANE=1` restores the old form (`XpuCpuWaveHalfTests`, gpu-kernel-parity 23.1.0). Only a read directly in the work-item loop takes this form. A read inside a loop of the kernel's own that the vectorizer widens by itself is left as it was: routing those too made cajeta-llm's tile prefill attention about 4x slower on the cpu (8B 181 to 810 ms), which a bench on the models caught the same day.

- **A wave kernel's `Math.exp` of a value every lane shares is one call a wave on the cpu backend.** A widened wave kernel used to make a scalar `expf` call for every lane, even when the argument came from a wave reduction and was the same in all of them. The widened call now compares the lanes first: when they agree it makes one scalar call and copies the result, otherwise it makes a call a lane as before. The results are the per-lane calls' bit for bit. cajeta-llm's 8B prefill attention kernel (8 exponentials a key in each of 32 lanes) went from 36.7 ms to 10.5 ms a launch; on Llama 3.1 8B with the GPU-shaped kernels, prefill attention went from 1153 to 328 ms and decode attention from 6.15 to 2.44 ms a token. `CAJETA_XPU_CPU_EXP_PER_LANE=1` restores a call a lane (`XpuCpuWaveExpTests`, gpu-kernel-parity 22.2.4).

- **A cooperative-matrix tile in a `@Wave(width = N)` kernel runs once a wave on the cpu backend.** The cpu has no matrix unit, so a `CooperativeMatrix` is a software tile there, and every work-item of the wave used to compute the whole tile: 32 identical copies, and the tile's own loops were stepped across all the lanes of the workgroup. A kernel that declares `@Wave(width = N)` (and an `@Occupancy(maxThreads)` bound) now keeps one copy of each tile a wave in workgroup-shared memory. `splat`, `load`, `store`, `storeAs`, `mma`, `addScaledPow2` and `set` run on the wave's first lane, between workgroup barriers; `get`, `row` and `col` read the shared copy from any lane; `elements()` is the tile's size on the first lane and 0 on the others, so a per-element loop runs once. The multiply accumulates a row of the result a step, in the same per-element order, so results are unchanged. One 16x16x16 float16 multiply-accumulate went from 4.4 us to 76 ns, the time of the same product written as row work-items (`bench/cpucoop`), and cajeta-llm's head-256 prefill attention kernel went from 1.7 s to 3.8 ms a launch at 512 positions. Every verb that changes a tile, the epilogue verbs included, is the first lane's. A `@Device` helper handed such a tile runs on the wave's first lane too, and must return void. `CAJETA_XPU_CPU_TILE_REPLICATED=1` restores a tile a work-item (`XpuCpuTileOncePerWaveTests`, gpu-kernel-parity 22.2.3, spec 13.5).

- **A kernel without wave operations widens across work-items on the cpu where the vectorizer could not bound its accesses.** A kernel that is also built for a GPU cannot depend on the order of its work-items, so the cpu backend now tells LLVM's loop vectorizer that they are independent, as it already did for wave kernels. A gather, a scatter and a bias add over rows (`y[i] += b[i % n]`) used to stay scalar with "cannot identify array bounds". A kernel declared `@Kernel(targets = {"cpu"})` keeps work-item order, and so does any kernel that stores to one fixed location from every work-item. In cajeta-llm, 12 kernels now widen and 29 more are left scalar by the vectorizer's cost model instead of by the refusal. The `[xpu-cpu-scalar]` note now ends "each running its own vector code" when the body holds explicit `Vector` code, which is 158 of cajeta-llm's 289 notes (`XpuCpuPlainWidenTests`, gpu-kernel-parity 21.2.1).

- **A wave kernel whose lanes run explicit `Vector` code keeps that code whole on the cpu backend.** The
  compiler used to step all lanes through such a loop together and widen it across the wave, which
  rebuilt each lane's vector an element at a time and lost the VNNI dot instruction. The loop now runs
  lane by lane, and the wave operation after it still widens. An int8 dot mat-vec written as a wave
  kernel went from 15x slower than its row-a-work-item form to 1.4x (`bench/cpuwave`).
  A kernel whose widened regions hold no vectors also skips the scalarize step, so its dots stay
  VNNI instructions. cajeta-llm's GPU-shaped decode kernels on the cpu went from 4.7 to 11.7 tok/s
  on Llama 3.1 8B Q4_K_M (the cpu-only kernels make 22.6).
  `CAJETA_XPU_CPU_WIDEN_VECTOR_BODY=1` restores the old form (gpu-kernel-parity 20.2.2).

- **A cpu kernel that runs one work-item at a time says so.** On the cpu backend a kernel's work-items are a loop, and LLVM's loop vectorizer is what spreads them across SIMD lanes. When it does not, the kernel ran scalar with no word at build time. The build now notes it by name with the vectorizer's reason, `[xpu-cpu-scalar] rowSum: the work-item loop did not vectorize (the body has a loop of its own, and LoopVectorize widens only innermost loops)`, and `KernelManifest.vectorWidth()` gives the width the loop was built at, 1 when it stayed scalar. A wave kernel that does not vectorize is still refused, as before. `CAJETA_XPU_CPU_NO_VECTORIZE` now also turns the vectorizer off for kernels with neither barriers nor wave operations, as its documentation said (`XpuCpuScalarNote`, gpu-kernel-parity 19.1).

- **A Vulkan tile kernel whose 16x16x16 shape the device does not list takes the portable tile.** `CooperativeMatrixKHR` says a device has matrix units, not which shapes and types, and the RTX 4090's Vulkan lists int8 only at 16x16x32. A native 16x16x16 int8 multiply launched there anyway and every cell came back 0, with no error. The runtime now reads each tile type the module declares and requires the matching listed config: f16 with an f32 or an f16 accumulator, int8, or bf16. A kernel that lacks one takes its `$pt` variant and names the rung, or is refused by name. `CAJETA_XPU_DENY=coop-int8` (or `coop-f16`, `coop-bf16`, `coop-f16acc`) treats one as unlisted on any box (`XpuVulkanCoopConfig`, gpu-kernel-parity 14.2.6).

- **A read of an unmapped Vulkan buffer no longer waits for later work.** A KernelBuffer in unmapped device-local memory is read through a staged copy, and that copy went on the one queue behind every dispatch already submitted, so a host that waited an event and read what came before it still waited for what came after (561 ms against under 30 on gfx1151). The copy now runs on its own queue: a second queue of the main family, or another compute family, with buffers shared between the two. Reads are reached only once their writers are done, so results are unchanged. `CAJETA_XPU_VK_READ_QUEUE=0` puts the copy back on the main queue (`XpuVulkanBatchEvent.anUnmappedReadDoesNotWaitForLaterWork`, gpu-kernel-parity 16.2.4.2).

- **A Vulkan `$d2` build that will not make a pipeline falls back to the base kernel.** On a device with `VK_VALVE_shader_mixed_float_dot_product`, a kernel's f16 `dotSum` launches its `$d2` build. A validation layer older than the extension (1.4.341 under a 1.4.354 driver) refuses that module, and the launch failed with no fallback. The launcher now checks that the `$d2` build makes a pipeline before taking it. When it does not, one `[xpu-rung]` note names the kernel and the base build runs (`SpirvMixedDotTests`).

## 0.54.3 (2026-11-21)

- **A cooperative-matrix load or store can state its alignment, and nvptx then drops the placement guard.** 0.54.0's guard keeps both the wmma and the per-element form at every native site whose placement the compiler cannot prove, and that cost two cajeta-llm GEMMs on sm_89 a spill (`q4kWmmaDeqMw8Kernel` 8 bytes, `q5kWmmaIdMwKernel` 24). `load`, `store` and `storeAs` now take `vload`'s trailing `align:`, a constant power of two from 1 to 16 stating that the tile's address and its pitch in bytes are multiples of it: `a.load(xs, offset, 0, stride, align: 16)`. Where the statement covers the fragment's run, nvptx emits wmma alone, and both kernels spill nothing. A narrower statement changes nothing, the other backends and the reference interpreter accept it without effect, and a bad value is refused naming the verb and its line (`XpuCoopStatedAlignment`, coop-stated-alignment Unit 1).

- **An exact enum argument outranks one that decays to an integer.** When no overload matched exactly, resolution let every enum argument decay to its int32 ordinal and then picked among the candidates arbitrarily, because the closest-match scan scored every positional candidate the same. A call such as `f(n, Kind.B)` with `f(uint64, Kind)` and `f(int64, uint64)` could bind the second. The candidate whose formal is the argument's own enum type now ranks first. Calls with no enum argument resolve as before, and an enum still reaches an `int32`-only overload (`EnumOverloadRanking`, enum-overload-ranking Unit 1).

- **`heap KernelBuffer<T>(n, MemoryKind.Pinned)` allocates n elements of that kind.** MemoryKind's documentation showed this call, but there was no such constructor: it bound the package-private `(int64 deviceHandle, uint64 elementCount)` form, wrapped address `n` with a count of the kind's ordinal, and a kernel touching it faulted with CUDA 700. `KernelBuffer(uint64 elementCount, MemoryKind kind)` now allocates the kind and releases it on drop, and `KernelBuffer(0, n)` with `allocate(kind)` keeps working (`XpuKernelBufferKindCtor`, enum-overload-ranking Unit 2).

- **A debug build tests each stated tile alignment.** With ubTraps on (every debug build), a tile whose address or pitch breaks its `align:` is recorded and skipped rather than faulting the CUDA context, and the launch throws `XpuLaunchException` naming the kernel, the line and the misaligned address or pitch. The next conforming launch runs. The check writes its record with plain stores, so it costs a debug build no registers: a compare-and-swap at every tile site had spilled cajeta-llm's q5kWmmaIdMwKernel 16 bytes on sm_89. Vulkan and amdgpu are not checked: neither has a guard to drop, so a statement changes no code there. On gfx1151 the earlier check had pushed cajeta-llm's `q4kWmmaDeqMw8Kernel` into a 392-byte spill (coop-stated-alignment Unit 2).

- **A Relaxed kernel atomic is relaxed on Vulkan too.** Vulkan raised every `MemoryOrder.Relaxed` atomic to AcquireRelease, so it cost more there than on nvptx or amdgpu. On the RTX 4090 the decoupled look-back scan spent 120 us of 860 on that. A Relaxed atomic now lowers to memory semantics 0, as on the other backends. An atomic with no order still takes AcquireRelease, and SequentiallyConsistent still raises to it. `CAJETA_XPU_VK_RELAXED=0` at compile time restores the old lowering (`SpirvRelaxedAtomicTests`, gpu-kernel-parity 16.2.4.3.2).

- **8- and 16-bit lane groups read whole words on Vulkan.** A `vload` or `vstore` of int8, int16 or float16 lanes was one access per lane. With 16-byte alignment stated and 16 or 32 bytes moved, it is now one or two 16-byte accesses. With 4-byte alignment it moves whole 32-bit words. A group read inside a `@Device` helper counts too. Across cajeta-llm's 699 Vulkan kernels, 16-bit accesses fell from 6106 to 4570, and `q6kF16WaveMatVecColsKernel`'s 512 became 64. RADV already merged such reads, so proton's throughput is unchanged. Other drivers are not measured yet (`SpirvWideAccessTests`, gpu-kernel-parity 16.2.4.3.3).

## 0.54.2 (2026-11-20)

- **Kernel atomics on NVIDIA and AMD reach the device, not the whole system.** Every `KernelBuffer` atomic on nvptx and amdgpu was emitted at LLVM's default system scope, so on cuda it was an `atom.*.sys`, ordered against the host and every peer device. That broke the atomics spec's own promise of device scope, which Vulkan already kept. A `KernelBuffer` atomic is now device-scoped (`.gpu` on NVIDIA, `agent` on AMD) and a `shared` array's atomic is workgroup-scoped, as CUDA's and HIP's `atomicAdd` are. On an RTX 4090 the decoupled look-back scan went from 1490 to 538 us, ahead of CUB's 594, and its look-back now costs nothing (`XpuAtomicScope`, kernel-atomic-scope 1).

- **A kernel atomic can name its scope.** `MemoryScope { Workgroup, Device, System }` is an optional, compile-time-constant argument after the `MemoryOrder`: `flag.atomicExchange(0, 1, MemoryOrder.Release, MemoryScope.System)`. System scope is for a kernel that signals the host through a `Pinned` or `Unified` buffer while it is still running, and on the 4090 the host sees such a flag mid-launch. Vulkan has no wider shader scope than Device, so `System` lowers to Device there. A scope that is not a constant is refused by name (`XpuAtomicScope`, kernel-atomic-scope 2).

- **Vulkan kernel buffers stay in device memory on a discrete GPU.** A kernel buffer had to be host-mappable, and on a card without Resizable BAR the mappable device memory is a small window (224 MB on an RTX 4090), so larger buffers fell back to system RAM over PCIe: the scan at 2^26 took 281 ms on the 4090's Vulkan. A buffer now takes unmapped device-local memory, written through staging, and on a small window buffers over 1 MB skip it. The same scan takes 1.66 ms. `CAJETA_XPU_VK_ALLOC_LOG=1` names where each buffer lands (gpu-kernel-parity 16.2.4.1).

- **An aligned 32-bit `vload<4>` or `vstore` on Vulkan is one 16-byte access.** It was four 4-byte accesses, so a thread's 16 consecutive values scattered across the warp. With the alignment stated, the scan on the 4090's Vulkan went from 1659 to 865 us (gpu-kernel-parity 16.2.4.3).

- **A Vulkan kernel declaring `@Occupancy(maxWaves = N)` stages N tiles.** Its per-subgroup staging held 32 tiles, one per subgroup of 1024 threads, so cajeta-llm's `MwTile_64_64` carried 80 KB of staging. Four of its tile kernels now fit and run (gpu-kernel-parity 16.2.3).

- **Multi-block cpu kernel launches recover most of 0.54's slowdown.** The cpu pool's four per-launch words had no alignment of their own, so a larger static table in 0.54.0 moved them across two cache lines, and launches of more than one block ran 14 to 20% slower on Zen 5. They now share one 64-byte line wherever the struct lands, and run within 1 to 9% of 0.53 (the small-grid residual is unattributed).

- **`Device.variantBase(name)` names the kernel a compiler variant stands for.** It returns `gemm` for `gemm$pt`, `gemm$d2` or `gemm$v8$pt`, and an empty string for a name that is not a variant, so a library's kernel census no longer parses the suffixes itself (gpu-kernel-parity 14.2.5).

## 0.54.1 (2026-11-19)

- **Vulkan builds of large programs no longer crash the compiler.** A cooperative-matrix tile kernel's virtual-wave variant (`$v8`, `$v16`, new in 0.54.0) could leave a `@Device` helper that reads the lane holding a pointer into a function the build had already erased. A release compiler has no assertions to catch that, so it surfaced later as heap corruption or a segfault, depending on address layout: about 2 of 3 cajeta-llm Vulkan test builds crashed on 0.54.0. The variant's build now inlines every helper that reads the lane before it splits the kernel, and a variant that still has an outside use fails cleanly instead (`SpirvVirtualHelperLaneTests`, gpu-kernel-parity 18.3.3).

## 0.54.0 (2026-11-19)

- **`acc.storeAs<U>(dst, offset, layout, stride)` stores a float32 accumulator at 16 bits.** A kernel that writes a float16 or bfloat16 result no longer walks the fragment with `get`, `row` and `col`: `storeAs` converts each element as the scalar cast `(U) x` does, rounding to nearest even, at either layout, at any stride, into a `KernelBuffer<U>` or a `Shared<U>`. `store` keeps its meaning, `storeAs<float32>` is `store`, and any other `U`, an operand fragment or an accumulator of another type is refused by name. On nvptx a float16 tile on a 4-byte boundary with an even stride is one `wmma.store.d.f16`, a row-major bfloat16 tile packs pairs into 4-byte stores, and anything else stores per element. On Vulkan it goes through the per-subgroup staging tile, and the reference interpreter defines it for the conformance corpus. gemm128's 16-bit-output member on the 4090 keeps 128 registers with no spill (`XpuCoopStoreAs`, coop-converting-store Units 1 to 3).

- **Native cooperative-matrix loads and stores on nvptx are right at any placement.** wmma moves each lane's contiguous run as one access, 8 bytes for an f32 or s32 accumulator and 4 for a 16-bit fragment or an 8-bit A operand. Off that alignment a tile faulted the CUDA context, and a stride off that multiple put cells in the wrong place with no error: a float32 `store` at offset 11, stride 17 wrote all 256 cells wrong on the 4090. Loads and stores now take wmma where the run is aligned and otherwise gather or scatter per element through the fragment's lane map, measured on the device for every operand type, with no shared memory. The GEMMs keep their registers and spills. `CAJETA_XPU_NVPTX_PLACEMENT=per-element` forces the per-element form for tests, a kernel that took it is named at exit (`cajeta: note: [placement] ...`), and the manifest records `<verb>.misaligned` (`XpuCoopUnaligned`, `NvptxOperandMapTests`, coop-converting-store Unit 5).

- **`(bfloat16) x` keeps subnormals on every x86 CPU.** On a CPU with AVX512-BF16 or AVX-NE-CONVERT, such as Zen 5, LLVM converted with `vcvtneps2bf16`, which treats a float32 denormal input as zero, so 1.0e-40 became 0 instead of the bf16 subnormal 0x0001 on the host and in cpu kernels. cajeta-llvm r13 uses those instructions only where the function lets float32 denormals flush, and otherwise rounds exactly, inline and still vectorized. The cast, `Vector.toBF16`, the cpu tile's narrowing store and bf16 arithmetic are all covered, and a `@FastMath` cpu kernel keeps the one-instruction convert. This release builds against cajeta-llvm r13 (`Bf16CastDenormalTests`, bf16-cast-denormals).

- **Vulkan devices without cooperative matrices run cooperative-matrix kernels.** A kernel whose SPIR-V declares `CooperativeMatrixKHR` gets a `$pt` variant with every tile portable, and the launcher takes it on a device that lacks the capability, saying so once (`[xpu-rung] <kernel> runs on the portable tile`). A kernel whose layout assumes 32 lanes declares it and gets virtual-wave variants for narrower subgroups, and a `$pt` launch on a device whose subgroups cannot run 32 lanes is refused by name instead of computing the wrong cells (gpu-kernel-parity 10, 14).

- **A portable cooperative-matrix tile on Vulkan is spread across the subgroup.** A tile with no native config there (bf16 on RADV, f32 operands) was copied whole into each work-item, and the bf16 GEMM took 15 minutes to compile. It is now laid out across the 32-lane subgroup, as on nvptx and amdgpu (`SpirvPortableTileTests`, gpu-kernel-parity 10).

- **`Device.supports` answers from the driver.** Capabilities 4 to 12 are the native f16, int8 and bf16 matrix units, Float64, Float16Arithmetic, IntegerDot4x8, SubgroupWidth32 and 64, and FloatDot2Mix. `CAJETA_XPU_DENY=<capability,...>` makes any of them read as absent, as on a device without it, so one machine tests the fallbacks (`XpuCapabilityCatalog`, gpu-kernel-parity 13, 14).

- **f16 `dotSum` pairs run as one instruction on Vulkan where the driver offers it.** On a device with `VK_VALVE_shader_mixed_float_dot_product`, such as RADV on gfx1151, a kernel's f16 `dotSum` gets a `$d2` variant whose pairs are each `OpFDot2MixAcc32VALVE`. It rounds as hip's `dot2` does, so f16 `dotSum` results there can differ by one ulp a pair from 0.53.11. `CAJETA_XPU_DENY=mixeddot` turns it off (gpu-kernel-parity 18).

- **A boolean in a Vulkan storage buffer is a byte.** SPIR-V forbids its boolean type in an externally visible variable, so a `KernelBuffer<boolean>` failed spirv-val. Its loads and stores now go through bytes (`SpirvBooleanBufferTests`, gpu-kernel-parity 11).

## 0.53.11 (2026-11-18)

- **Cooperative-matrix element access, `fromWords` and the GEMM epilogues run on Vulkan.** `elements`, `row`, `col`, `get` and `set` on a native SPIR-V tile were refused, because SPV_KHR_cooperative_matrix gives no lane-to-element map. They now go through a per-subgroup staging tile in workgroup memory, with the same map as amdgpu's wave32 fragment (lane L holds column L mod 16, element e is row 2e + L/16), ordered by a subgroup-scope barrier. `fromWords` stages each lane's column and reloads it, as nvptx does. `scaledAccumInto`, `rank1Accum`, `scaledAccumInto2` and `scaledAccumI32`, including their `WaveVector.ofLane` forms, keep the tiles native instead of demoting the kernel to the portable tile, and the integer form matches `amdgcn.mul.i24` bit for bit. So the flash-attention prefill tiles and the int8 GEMM tiles that ran only on hip build for Vulkan from the same source. On Vulkan a view slot released while a batch is open is parked until the batch lands. Counters for tests: `Device.deviceAllocationCount()`, `streamSyncCount()`, `transferCount()`.
- **Bulk transfers and a Tensor-to-KernelBuffer bridge.** `gpu()`/`cpu()` are one copy each way; `Tensor.uploadTo(buf)`/`downloadFrom(buf)` move a contiguous host tensor's elements in one transfer through `KernelBuffer.uploadFrom/downloadTo`.
- **Per-element `Tensor` reads cost what a raw array loop costs in `--release`** (0.99x measured; 2.86x before). An accessor-shaped method (no calls outside its `throw` statements, no loops) pushes its line frame only on a throw path, so an inlined accessor carries no shadow-stack traffic; its exception traces are unchanged, and a sampled profile attributes its time to the caller. The cross-module inliner counts only return-reaching blocks toward its size limits and always inlines up to 64 hot instructions; `CAJETA_XMODULE_INLINE_TRACE=1` names what it copies or skips.
- **`Device.kernelUsable(name)` and `cajeta.xpu.KernelCap`.** Usable is registered, not held by a recorded defect (`KernelCap.hold(backend, name, why)`, until `release`) and not pinned off by a test (`setOverride`, `clearOverrides`); `kernelUnusableReason` says which.
- **A kernel in a class template over a type parameter calls that type's `@Device` statics.** `E.apply(…)` in `Fused<E>` lowered for `Fused<BiasRelu>` calls `BiasRelu.apply`: a consumer supplies an epilogue or a decode step to a library kernel by instantiating the template.

## 0.52.0 (2026-11-05)

- **`@Kernel(targets = {...})` names the backends a kernel is built for.** A target is `"cpu"`, `"gpu"` (vulkan, amdgpu and nvptx) or a backend name, with `@Unlowered`'s aliases; with none, a kernel is built for every backend as before. A backend outside the targets does not lower or register the kernel and spends no build time on it. There, `Device.kernelUnavailableReason(name)` answers `not a target`, a launch throws `XpuLaunchException` naming the kernel and the backend, and `Device.offTargetKernelCount()` and `offTargetKernel(i)` list such kernels for a census. An unknown target name fails the build (`CAJETA_ERROR_XPU_UNKNOWN_TARGET`). Before, a GPU-only kernel was lowered for the cpu backend and ran there as emulated blocks when a router reached it: cajeta-llm's 72B on cpu stalled for over ten minutes in one, and its cpu build spent 123 s vectorising wave kernels the cpu decode never routes to.
- **`@Unlowered` may only name backends among a kernel's targets** (`CAJETA_ERROR_XPU_UNLOWERED_OFF_TARGET`). A `hold = true` over every GPU backend, or over the cpu backend alone, notes the `@Kernel(targets = ...)` that says the same thing.
- **`@Backend` is retired.** It was parsed and never enforced; on a kernel it is now an error pointing at `@Kernel(targets)`.
- **A prefetch loop vectorises in proportion to its size on the cpu backend.** LoopVectorize looked a block's plan up by walking every predecessor back to the plan entry, once per recipe in `simplifyRecipes` and once per probe in its CSE, each probe also rebuilding a type analysis. cajeta-llm's Q6_K prefetch wave mat-vec took 31.7 s to vectorise and takes 0.67 s, and the library's cpu build spends 31 s vectorising instead of 170 s. The toolchain builds against `cajeta-llvm-23-r12`, which carries the fix.
- **A `--release` exe links a drop that only a classpath archive's code calls.** Each module is optimized alone before the link, so a drop function whose only caller was in a classpath archive (`Optional<Dispatch>` in `dev.cajeta.http`'s `DispatchPool.worker`) was deleted and the link failed with an undefined `__cajeta_stack_..._drop`. Object and exe emission now keep drop definitions `weak_odr` in their comdat, as the JIT already did. cabra builds `--release` against http 0.9.x again.
- **cpu kernel pool workers above a lowered cap park until it is raised**, instead of waking for every launch.
- **Autotune keeps one entry per build**, so two binaries over one store do not re-time each other.
- `CAJETA_TIME_PASSES` reports the cpu vectorize pipeline, and `CAJETA_XPU_CPU_DUMP_PRELV` writes the whole module, so `opt` can replay LoopVectorize on it.

## 0.51.0 (2026-11-03)

- **The cpu kernel pool's chunks shrink as a launch runs.** Each batch gives every participant one chunk of half the blocks left, divided among them, down to one block, so a worker slowed by other load on its core holds the launch for one small chunk instead of a whole share. On a 16-core Zen 5 host with eight busy loops beside it, cajeta-llm's 8B decode runs at 21.3 tok/s against 17.7 with one chunk a worker, and its Q4_K_M prefill at 290 tok/s against about 275; unloaded decode is level. `CAJETA_XPU_CPU_CHUNKS=n` (1 to 64) keeps n equal chunks a participant. Every chunk starts its data stream cold, so a kernel that streams weights should prefetch ahead rather than rely on the hardware prefetcher having trained.
- **`File.writeAllBytes` replaces an existing file on Windows.** The write is renamed into place, and the Windows CRT's rename refuses an existing target, so every overwrite kept the old bytes and said nothing: a program writing "ABC" then "XY" read back "ABC". The Windows arm now renames with `MoveFileExA` and `MOVEFILE_REPLACE_EXISTING`. Every earlier Windows release does the same.

## 0.50.0 (2026-11-02)

- **`KernelBuffer.prefetch(index)` asks for a cache line before a kernel reads it.** It is advice, not an access: the cpu backend emits a read prefetch into the data cache, the GPU backends emit nothing, the reference interpreter accepts any index, and outside a kernel it is the kernel-only error that `vload` is. A kernel that consumes a cache line per load outruns the hardware prefetchers. On proton (Zen 5), cajeta-llm's 8B decode prefetching its 8-row weight block two blocks ahead went from 25.8 to 27.6 tok/s on Q3_K_M (+7.1%), 32.4 to 34.3 on Q2_K (+5.8%) and 19.5 to 20.0 on Q5_K_M (+2.7%), and was level on Q4_K, Q6_K and Q8_0. See CajetaXPU.md.
- **The cpu kernel pool hands out a launch's blocks by claim.** The caller and the workers claim chunks against a generation-tagged word, so a worker that is slow to wake leaves its share to the others instead of holding the launch. Before, a worker preempted at full occupancy held every launch on the static split: cajeta-llm's 8B decode at 32 threads ran at 8.0 tok/s with 299,000 context switches, and now runs at 15.8 with 55,000. The default of one chunk a worker (`CAJETA_XPU_CPU_CHUNKS`) is level with the old split at one worker a core. Pool creation waits until its new workers are running.
- **A cpu device buffer is 64-byte aligned.** Buffers came from `malloc`, which places a large block 16 bytes past a page boundary, so every 512-bit load straddled two cache lines.
- **An array literal element read from a field, a static or an array element stores its value.** `[o.x, Q.K, src[1]]` stored the addresses of those slots: for `int32` elements, 8-byte pointer stores into 4-byte slots with the last past the array, which corrupted the heap and double-freed at exit, and for a class or `String` field the slot's address in place of the object. Every earlier release does the same.
- **A conditional with a `null` arm takes its type from the other arm.** `T x = c == null ? null : c.f;` was typed by its `null` arm as a primitive, so `x` bound as an owner and its drop freed the field's object at scope exit. A switch expression whose first case is `null` had the same defect. Both now bind a borrow.
- `return [a, b];` over locals compiles; it failed with "array literal element has no resolved type".
- **An executable runs the runtime's at-exit registry when its entry returns.** A singleton's `@PreDestroy` now runs at exit, as the DI guide says, and `CAJETA_XPU_CPU_TRACE` prints its summary from an `--emit=exe` program. Before, only `Cajeta.runAtExit()` fired the registry.
- Tuned tile shapes key on the hardware class (backend, multiprocessor layout, L2 and VRAM) and the driver version instead of the card's UUID, so a store seeded on one card serves every identical card.

## 0.49.0 (2026-10-31)

- **One binary for every x86 host: `--cpu=portable`.** The cpu backend's kernels are emitted once per ISA level (`v3`: AVX2, FMA, F16C, BMI2; `v3-vnni`: AVX-VNNI; `v4`: AVX-512 with VNNI; `v4-amx`: AMX-INT8), the host module at the x86-64-v3 baseline, and the runtime picks the highest level the host supports when the program starts. `CAJETA_XPU_CPU_LEVEL=<level>` or `Device.setCpuLevelOverride` forces a lower level, never a higher; `Device.cpuLevel`, `cpuLevelName` and `cpuKernelLevel` report them; `--cpu-variants` picks a subset. A plain `--emit=exe` is unchanged: one copy for the build host. On proton (Zen 5) with cajeta-llm's 8B Q4_K_M, the portable binary at v4 runs the native binary's instructions at 0.98 to 1.0x, is 3.5x its size and takes 5x as long to build; forced to v3 it runs prefill at 0.58 and decode at 0.965 of v4, at v3-vnni 0.69 and 0.97. See CajetaCPU.md §7; releases of cajeta programs pass it (RELEASING.md).
- **Integer dots below VNNI.** With AVX2 and no VNNI, a kernel's `dotAccum` lowers to `vpmaddwd`, or to the three-instruction `vpmaddubsw` form where the compiler proves every weight byte at most 128 (a masked nibble, a 6-bit assembly), following the bound through bitcasts and slots. The cpu backend stays bit-exact with the GPU backends: no saturating form without the proof. A 16-lane dot on an AVX-VNNI host is two 256-bit `vpdpbusd`; the 512-bit form was emitted whatever the target had, and a 64-lane kernel did not build at v3-vnni.
- **An AMX tier for int8 cooperative-matrix tiles** at level `v4-amx`, behind `CAJETA_XPU_CPU_AMX=1`: `CooperativeMatrix<int8,16,16>` with an int32 accumulator lowers to `tileloadd`, `tdpb{ss,su,us,uu}d` and `tilestored`, one tile a work item. Verified by instruction selection only, and off by default until measured on AMX hardware.
- A leveled kernel copy registers its manifest under its level, so `KernelManifest.of` on cpu describes the copy the host runs rather than the last one built.
- **The cpu pool defaults to one worker a physical core, and a worker spins about 1.3 ms before it sleeps** (`CAJETA_XPU_CPU_WORKER_SPIN`, in PAUSEs; a cap of 0 means physical cores). On proton, cajeta-llm's 8B Q4_K_M decode went from 15.9 to 20.3 tok/s against the old default of every hardware thread without spin.

## 0.48.0 (2026-10-29)

- **The compiler proves load alignment on every device backend, and `align:` states what it cannot prove.** One proof, run on NVPTX, AMDGPU, Vulkan and cpu, follows a buffer index through shifts, multiplies, constant masks, selects and phis. Where it shows an index is a multiple of the access width, the load or store is emitted wide. `vload<N>(i, align: A)` and `vstore(i, v, align: A)` state an alignment the proof cannot reach, A a constant power of two from 1 to 16 and no wider than the access: NVPTX and AMDGPU put it on the access, cpu ignores it, and Vulkan applies it as an index mask. A checked build (debug, or `ubTraps` on) tests every statement the proof does not confirm and raises at the launch naming the kernel, the line, the stated width and the element index (refusal reason 8); a release build checks nothing. On Vulkan a proven index is rebuilt in 32 bits as `(V & -4) + C + j`, the form RADV reads: on Mesa 26.0.8, cajeta-llm's Q2_K, Q3_K and Q8_0 column mat-vecs go from 8, 6 and 13 `v_alignbyte` to 2, 1 and 1, and no kernel gains any. See CajetaXPU.md §2.3.
- **A Vulkan view the device cannot bind is refused by name.** A view is bound at its byte offset, which the device allows only at multiples of `minStorageBufferOffsetAlignment` (16 on llvmpipe and NVIDIA, 4 on RADV). A view anywhere else was invalid usage a driver could round down; the launch is now refused naming the argument, the offset and the limit (reason 9). The check costs about 15 ns a buffer.
- **A Windows `--emit=exe` links again.** The COFF tree-shake dropped runtime entry points that codegen calls after it, so links failed with an undefined `__cajeta_shadow_cur_slow`.
- A release build of a `run(String[] args)` entry no longer crashes the inliner: the generated `main` passes the entry's trailing transfer word.
- A `Vector<int8,N>` passed through a `@Device` parameter keeps its signedness, so `dotAccum` in a helper lowers to `dp4a.s32.s32`, not `dp4a.u32.s32`.
- A host `dotSum` with a literal `0` accumulator casts it to the `int32` sum instead of emitting a mistyped add.
- Vulkan: an undefined cooperative matrix becomes a zero splat of its own type before codegen, so a conditionally loaded tile merges with a valid `OpPhi`; and an element GEP on an already offset `Shared` pointer folds onto its root, so a software tile keeps its per-column index.
- The macOS build bundles its Homebrew dylibs beside the binary and links a program's OpenSSL statically, so neither needs Homebrew.
- Profiler: the clock fit measures a rate only once its samples span 10,000 sandwich widths, else it keeps the nominal period.

## 0.47.0 (2026-10-25)

- **Vulkan keeps the device fed while the host records.** A batch submits its first chunk after 8 dispatches, then chunks that double up to 128, so the device starts early and later submits are few. A `KernelEvent` is now a `VkEvent` set inside the batch, so the host can wait on one point while the device runs what was recorded after it. A host read or write lands the batch only when a dispatch the host has not yet waited for touches that buffer. The 32-slot command-buffer ring reclaims one slot at a time: a wrap waits for the oldest chunk, not the whole queue. A launch's scalar arguments are freed at once instead of filling the deferred-free list, whose backstop flushed the batch every 4096 four-scalar launches. An event wait submits the open chunk before blocking. On a Radeon 8060S (gfx1151), cajeta-llm's 8B Q4_K_M decode went from 151.6 to 160.3 tok/s at 4 sequences (llama.cpp: 160.9) and from 42.3 to 44.3 at 1. Knobs: `CAJETA_XPU_VK_FIRST_CHUNK`, `CAJETA_XPU_VK_CHUNK` (both sizes), `CAJETA_XPU_VK_CHUNK_RAMP` (1 = fixed), `CAJETA_XPU_VK_NOCHUNK`; `CAJETA_XPU_FAULT=vk-no-events` restores the old event, which landed the whole batch.
- Vulkan's eager submit path (`CAJETA_XPU_VK_SUBMIT=eager`, and every launch under a GPU capture) rewinds the scalar-argument arena. After 65,536 scalar arguments a launch was refused with no message, and `Device.checkLaunch` called it "no device code registered".
- **A class with more than 64 reference, array or closure fields compiles correctly.** The hidden ownership word was one `i64` whatever the field count, so the 65th field's bit was poison and a `--release` build could fold a method's tail into `unreachable`: the process died with SIGTRAP and no message, while debug builds ran. Past 64 fields the word is now `[N x i64]`. A class with 64 or fewer keeps its layout, so archives built before agree with code built after.
- **A tie among timed tile shapes goes to the first listed.** `ShapeChoice` treated a lead under 3% as a tie but still took the fastest median, so two near-equal tiles were a coin flip per process. A different tile is a different accumulation order, so cajeta-llm's hip output differed between runs. A tie now takes the first survivor in listing order within the margin; a clear lead still goes to the fastest.
- `return #s` on a `String` with no title returns an owned copy (up to 256 B, a shared stake above) instead of panicking with code 3, or silently returning a borrow when the flag was known at compile time.
- Profiler: a batched Vulkan launch is timed inside the batch (two timestamp queries around its dispatch, read after the fence), so a profiled step runs as an unprofiled one does instead of serializing every launch. A long CUDA capture attributes every launch: the pending table grows, CUPTI's correlation map outlives its buffer, and settle collects CUDA as well as HIP.
- `CAJETA_XPU_VK_SYNC_LOG` names each pipeline as it is built, so RADV's shader statistics can be matched to kernels.
- Build flavors take `live-set` (`strict`, `bounded` or `off`), which lowers to `--live-set`.

## 0.46.2 (2026-10-22)

- **NVIDIA prefill is back to 0.43.1's speed.** 0.46.0 made `TileOps.scaledAccumI32` sign-extend both factors from 24 bits on every backend so AMD could use its 24-bit multiply. The new `Bits.mulInt24(a, b)` multiplies two factors that fit 24 bits signed; AMD sign-extends and keeps the full-rate `v_mad_i32_i24`, and NVIDIA, cpu and Vulkan use the plain 32-bit multiply. `scaledAccumI32` uses it. ## 0.46.0 (2026-10-21)

- **`CooperativeMatrix.addScaledPow2(src, e)`** adds `src * 2^e` to a float32 accumulator tile of the same shape, for a constant `e` in [-126, 127]. The product is exact, so every backend and the reference interpreter agree bit for bit. It is not an epilogue verb, so a Vulkan kernel that uses it keeps its native cooperative-matrix tiles instead of falling back to the software tile; on Vulkan it lowers to `OpMatrixTimesScalar` and `OpFAdd`. ## 0.45.0 (2026-10-20)

- **Dependencies are verified by default** (publisher-trust spec 4.1, 5.3 to 5.5). Every repository a manifest declares now checks an archive before it is stored or loaded: `cajeta build`, `deps`, plugins, melts and a notebook's `Packages.install` run the same check. The repository must serve release metadata signed through its root (olla's ships in the toolchain), the bytes must hash to it, and when that metadata names an organization the archive must carry a signature that verifies against the organization's key document. A present envelope that does not verify is refused under either policy. `~/.olla` keeps the envelope beside each mirrored archive, and the machine's own `cajeta install` builds still resolve. `settings.require-signatures` is retired: it is still read, has no effect, and warns.

  Migration: add `"verification": "checksum"` to any filesystem, git or private HTTP repository that does not sign its releases. Olla's 49 releases published before it signed metadata (2026-07-19 to 2026-09-03, all superseded) are admitted on their exact bytes, which this toolchain lists by sha256.

- **A local changed inside a `try` keeps its value after a throw** at O1 and above, `--release` included. `try` is setjmp/longjmp and the optimizer kept such locals in registers, so the catch and the code after it read the value from `try` entry; 0.43.1 and 0.44.0 did the same. ElementAccessBench `flatGet` went from about 14 ns to 1 ns per element.
- `Npy` encodes and decodes through the host buffer: decoding 2^23 int32 values went from 123 ms to 7 ms.
- xpu: a kernel whose workgroup memory exceeds the device's limit is unavailable (`Device.kernelAvailable` answers false) and a launch is refused by name before the driver, reason 7 in `Device.checkLaunch`. On Vulkan such a kernel reached the driver and RADV divided by zero.
- Windows: `Path.mkdirs` treats a drive prefix as a root, so a nested directory on another drive is created.

- Windows: under Git Bash or MSYS2, `--classpath` entries spelled `/d/...` resolve to `D:/...`, and `--emit=exe` falls back to MSYS2's `C:/msys64/mingw64/bin` gcc or clang when no C driver is on `PATH`.

## 0.43.1 (2026-10-17)

A started fiber resumes only on its home carrier, and every other carrier that found nothing it could take went round again at full CPU for the whole of that carrier's turn: three threads at 100% beside one hashing a password, and on a two-vCPU CI runner the spinner shared a physical core with the worker, so primavera's test step went from 18 minutes to past its 30-minute cap when its server moved to cajeta-http 0.7.0's pool. ## 0.43.0 (2026-10-16)

- `cajeta.io.net.reactor.ReadySet`: one fiber waits on many descriptors at once. Members persist across waits, a wait returns the members that became ready, and a fired member is re-armed by the next wait, so a wait costs the ready set and never the membership. On Linux it rides the epoll fiber-park engine; elsewhere it probes its members with a cooperative sleep until the kqueue and IOCP engines land. The framers of request dispatch wait on it (request-dispatch spec §3.4).
- `cajeta.concurrent.Carriers.count()`: how many carrier threads run fibers, `CAJETA_CARRIERS` when set and otherwise the smaller of the core count and the runtime's cap, resolved once for the process. A server sizes its framers by it.
- `TcpStream.readNow`: a read that answers `-1` when the socket would block instead of parking, the count when bytes are there, and `0` at EOF.
- `Channel.trySend`: a send that answers `false` on a full or closed channel instead of parking.
- The reactor's closing path reports a closed descriptor to the set that held it, and `CAJETA_REACTOR_TRACE=1` traces set arms, records, drops and re-arms beside the single-descriptor waits.
- `TlsStream` gains the entries a framer drives it with, none of them parking: `fd`, `fillNow`, `handshakeNow`, `flushNow` (a partial write stays pending for the next call), `readPlaintextNow` straight into a `ByteBuffer`, `writeNow` from an offset, `pendingOut`.
- The `TcpStream.read` and `write` intrinsics load a field array argument (`this.outBuf`) as the array rather than its slot's address. The bytes on the wire were the right length and the wrong contents whenever a buffer was a field instead of a local.
- A wire view built over a field array, `Header(this.buf)`, reads the array. The view constructor loaded only a local's slot; a field or element slot was handed to the view as the bytes, so the view read the slot's pointer as its first fields. Both spellings now agree (`MultiVarSizeViewTests.viewOverAFieldArrayReadsTheArray`).
- Runtime: the fiber pool's condvars (carrier backstop, timer thread, the program thread's timed wait) wait on CLOCK_MONOTONIC on Linux, so a wall-clock step no longer moves a timed park (991f5a55).
- Windows: the JIT symbol bridge binds `TlsStream`'s new non-parking entries, so a JIT-run program or test that links the stdlib loads on COFF; `scripts/check-jit-win-symbols.sh` keeps every TLS entry point bound.

## 0.42.1 (2026-10-15)

## 0.42.0 (2026-10-14)

- A String temporary passed to a borrow formal (`raise("failed the " + check + " check")`) is reclaimed when the callee throws. It was dropped after the call, which a throw skipped: 2 live objects per throw, hit by cajeta-cloud's `badToken` on every refused token. The temporary now holds a drop-chain entry around the call, so the throw's unwind frees it.
- Two archives that declare the same short type names in different packages (primavera's and cajeta-cloud's `TimeSource` and `ManualTimeSource`) load together. A class read before its interface used to bind to the other archive's interface (`CAJETA_ERROR_INTERFACE_NOT_IMPLEMENTED`), and `heap a.b.C()` built a same-named class from another package and faulted. Declared parents resolve in their own package first; a qualified creator builds the class it names.
- `XXHash3.hash` over inputs longer than 240 bytes no longer traps: its long path ran signed `int64` arithmetic, which traps on overflow, so every long hash ended in SIGILL. The scalar steps now run in `uint64`, as XXH3 means them.
- xpu: every launch is a submission. `k.launch(s, grid:, block:)(args)` reaches the runtime as a default-policy submission; `KernelSubmission` gains `earliestNs`, `latestNs`, `protectedLaunch`, `cuBudget`, `captureId`, `energyJoules`, `poolHandle`, `poolReserve` and `stream`; `SchedulePolicy` adds `Energy`. A submission whose window closed is rejected before dispatch with `XpuLaunchException`. `Scheduler.bypass(true)` or `CAJETA_XPU_SCHEDULER=bypass` takes the raw launch path. `cajeta profile summary` lists instrumentation records under the kernels.
- xpu: device calibration. `cajeta.xpu.calibration.DeviceCalibration` measures a device's peaks, bandwidth, launch cost and scheduling delay on first contact and keeps them through a `CalibrationStore` (records embedded at build, then the platform cache). `cajeta calibrate <program>` records a program's launches and replays them on this device into a snapshot; `cajeta build --with-calibration=<snapshot>` embeds the snapshot's records. The package is lazy, so programs that do not use it compile no calibration kernels.
- `@GenerateMock` on an interface: the mock implements it and forwards its own and inherited methods; a class target's whole chain is forwarded; `#R` methods return the engine's owned answer. The generated mock is a `@TestComponent`, injected in place of the production component under the test profile.
- xpubench: arms interleave in one process in Thue-Morse order, profiled passes are rounds with their own walls, and a contention witness marks KPIs measured beside foreign CPU or GPU load as `contended` rather than `worse`.
- The test harness JITs the stdlib once per process and links each test against it, so a test's JIT cost drops from about 11 s to about 50 ms and a full sweep's recorded test time from 31 to 19 CPU-hours. The runtime gains execution epochs (`__cajeta_rt_epoch_push` and `__cajeta_rt_epoch_pop_to`), which a host running several programs against one runtime uses to drop what a program's constructors registered. The stdlib's machine code is kept across test processes under `.cajeta/cache/prime/obj`, so a warm process links it in about 1.4 s instead of compiling it for about 10 s. The sweep primes that cache once before its shards start, so a cold sweep pays one stdlib compile instead of one per shard. Each sweep shard then runs one fork server that primes once and forks a child per chunk (`FORK=0` restores a process per chunk), 14.2 CPU-hours of recorded test time against 16.6.

## 0.41.0 (2026-10-13)

- An interface value held as an interface it extends dispatches that interface's methods. It used to call the derived interface's slots (silent wrong code), and with the base in a later file it faulted. Each (class, interface) table now ends with pointers to the class's tables for the interfaces it extends, so archives built by an older compiler must be rebuilt.
- A cast to an interface that extends the value's own (`(Wide) b`) finds the class's table at run time and throws `ClassCastException` when the class does not implement it. Interface casts now carry ownership like class casts. Each table gains a trailing directory slot.
- Integer widening extends by the source's signedness: a `uint32` above 2^31 now widens to the same positive value instead of a negative one.
- A templated interface used before the class it is instantiated over has been read (`Codec<Signup>` in a signature, `Signup` in a later file) keeps its methods. Calls through it were `CAJETA_ERROR_MEMBER_NOT_FOUND`; the stdlib's `Encoder<T>` was affected the same way.
- A lambda that captures an interface value keeps its own copy of it, so it no longer reads a dead frame once the function that converted the value returns.
- Templates: a bound holds through `implements` and waits for a type not yet parsed; a class template's bare name inside its own body names the instantiation.
- xpu: kernel manifests carry a work model derived from the kernel body, and manifest bytes are the bytes a kernel requests. `Scheduler.submit` reads a kernel's footprint from its manifest. API change: `KernelResourceDescriptor`'s constructor drops `vgprCount` and `ldsBytes`, and `KernelSubmission.ldsBytes` is renamed `sharedBytes`. A kernel declaring `@Cost` fails the build.
- xpu: `KernelManifest.of` returns a lent view of a record parsed once per process, so a program may keep the record and a submit no longer pays the JSON parse. Its signature changes from `#KernelManifest` to `KernelManifest`; a caller that binds the result with `#=` keeps compiling, since `#=` records the borrow.
- xpu: `Bits` over `uint64`, with `trailingZeros` and `leadingZeros` at both widths. A Vulkan launch of a kernel with no Vulkan device code is refused, as on the other backends.
