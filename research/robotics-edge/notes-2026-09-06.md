## 1. DARIS — *An Oversubscribed Spatio-Temporal Scheduler for Real-Time DNN Inference on GPUs*
Babaei & Chantem, Virginia Tech. arXiv 2504.08795, Apr 2025.

### 1.1 Core mechanism
DARIS schedules periodic soft-real-time DNN inference on **one** GPU whose total
demand exceeds capacity. Spatial partitioning: NVIDIA MPS creates `N_c` CUDA
contexts, each given `N_SM = ceil_even(OS × N_SM,max / N_c)` SMs, where `OS ∈
[1, N_c]` is an explicit **oversubscription factor** — `OS=1` means disjoint SM
sets, `OS=N_c` means every context sees the whole GPU. Temporal sharing: `N_s`
CUDA streams per context, plus **staging** — each DNN is cut at synchronization
points into `n_i` sequential sub-tasks, which is the only preemption point the
hardware gives them. Offline, contexts are populated by greedy utilization
balancing; online, an admission test gates low-priority arrivals and an 8-level
fixed-priority + EDF stage scheduler dispatches. DNNs migrate between partitions
with zero delay.

### 1.2 Task and timing model
- `τ_i(T_i, D_i, mret_i(t), p_i, ctx_i(t))`, implicit deadlines `D_i = T_i`, two
  priority classes HP/LP, `τ_i = {τ_i,1 … τ_i,n_i}` sequential stages. **[P]**
- Execution estimate is **MRET**, not WCET: `mret_i,j(t) = max_{p∈[t−ws,t−1]}
  et_i,j(p)` over a sliding window `ws = 5`; `mret_i = Σ_j mret_i,j`. Chosen
  explicitly to avoid the pessimism of history-based WCET (they cite Clockwork's
  one-DNN-at-a-time approach as the alternative, which sacrifices throughput).
  Bootstrap value is **AFET** (Average Full-Load Execution Time) measured with
  the target in one stream while the others run randomly. **[P]**
- **Virtual deadline per stage:** `D_i,j(t) = (mret_i,j(t)/mret_i(t)) · D_i`.
  Longer stages get proportionally more of the end-to-end budget. **[P]**
- Utilization `u_i = mret_i/T_i`; per-context `U_k^{h,t}` (HP), `U_k^{l,t}` (LP),
  active `U_k^a = U_k^{h,t} + U_k^{l,a}`. **[P]**

### 1.3 Admission test (cheap enough to run per arrival)
```
U_k^r(t) = N_s − U_k^{h,t}(t)              # remaining capacity of context k
admit j into ctx_k  iff  U_k^{l,a}(t) + u_j < U_k^r(t)
```
On failure: test the other contexts, migrate to the one with the **earliest
predicted finish time**; if none passes, **reject**. HP tasks bypass the test by
default; the `Overload+HPA` variant applies it to HP too. Cost is O(#contexts)
adds/compares per arriving job. **[P]**

### 1.4 Stage scheduler — priority promotion along a chain
8 fixed levels, EDF within a level:
1. all HP stages outrank all LP stages;
2. **the last stage of each task (`τ_i,n_i`) is promoted one level** — prevents a
   chain from being ruined at the finish line;
3. **a stage whose immediately preceding stage missed its virtual deadline is
   promoted one level** — this is the paper's substitute for priority
   inheritance across a chain. **[P]**

### 1.6 What a single-process runtime can adopt
- MRET-over-a-window as the online cost estimate, per **stage**, not per task.
  A single-process runtime can measure this exactly (device timestamps), so `ws`
  can be per-node adaptive rather than a global 5.
- Proportional virtual deadlines across a kernel chain — one division per node,
  recomputed only when the MRET vector changes.
- The O(#partitions) utilization admission test verbatim.
- The two promotion rules (last-node, missed-predecessor). Both are one integer
  compare at dispatch.
- "MPS alone beats MPS+streams": in cajeta terms, **do not stack a spatial
  partition on top of a priority-stream partition** without measuring; the two
  mechanisms interfere.

### 1.7 Testable requirements
1. When a submitted chain's per-node MRET vector is known, the runtime SHALL
   assign each node a virtual deadline proportional to its share of the chain's
   total MRET. `(all)`
2. When a node's predecessor missed its virtual deadline, the runtime SHALL
   raise that node's dispatch priority by exactly one level and no more. `(all)`
3. When a chain's terminal node becomes ready, it SHALL be dispatched at one
   level above its chain's nominal class. `(game)` `(simulation)`
4. When a new best-effort stream requests admission and
   `U_partition^{besteffort,active} + u_new ≥ N_lanes − U_partition^{latency}`,
   the runtime SHALL either migrate it to the partition with the earliest
   predicted finish time or reject it — never admit it silently. `(all)`
5. When latency-critical demand exceeds 100% of a partition's capacity, the
   runtime SHALL apply the admission test to latency-critical work too, and
   SHALL report the rejection rather than degrade every deadline. `(all)`
6. When staging (tile-boundary yield points) is disabled for a kernel, the
   runtime SHALL record that the kernel is non-preemptible and SHALL NOT admit
   a shorter-deadline co-runner into the same partition for its duration. `(all)`
7. When a workload's measured batching gain is below 1.10x (UNet's 1.08x),
   the scheduler SHALL NOT choose batching as its throughput mechanism for that
   workload. `(ML)`

## 2. XAuto — *Holistic Heterogeneous Scheduling for Autonomous Systems*
arXiv 2508.09503, 2025.

### 2.1 Core mechanism
Schedules a whole autonomous-driving DAG across every engine on a Jetson AGX Orin
(12-core ARM CPU, Ampere GPU, 2× DLA, PVA, 2× VIC). Two abstractions: an
**XNode** is a pipeline stage with a *multi-XPU implementation set*; an
**XMODULE** contains XNodes (the ROS-node analogue). An ILP simultaneously
assigns XNodes to XPUs and computes start/finish times minimizing makespan; the
runtime then **derives fixed priorities by sorting XNodes on their ILP finish
times** and enforces them with genuine preemption on GPU and DLA.

### 2.2 The ILP (this is the schedulability test, run offline)
Variables: `p^m_i ∈ {0,1}` (XNode *i* on XPU *m*), `s_i`, `f_i`, and
`d^m_{i,j,k}` = demand of XNode *k* on XPU *m* inside interval `[s_i, f_j]`.
```
(1)  Σ_m p^m_i = 1                                   single assignment
(2)  f_j ≤ s_i            ∀ (j → i) ∈ E              precedence
(3)  f_i ≥ s_i + wcet^m_i  when p^m_i = 1            execution
(4,5) Σ_k d^m_{i,j,k} ≤ f_j − s_i   ∀ s_i ≤ f_j      demand-bound feasibility
obj:  min max_i f_i
```
Constraints (4)(5) are a **demand-bound function**: over any interval bounded by
two scheduling instants, the total demand placed on an engine must not exceed the
interval's length. **[P]**

### 2.3 Preemption — the load-bearing measurement in this whole corpus
- **GPU:** preemption is done by disabling/enabling the **TSG (Time Slice Group)**
  attached to a CUDA context handle. Measured cost of *preempting a running task
  and switching to another*: **275 µs on average.** **[P]**
- **DLA:** suspend/resume of the cuDLA command queues via `cudlaDevHandle`:
  **132 µs.** **[P]**
- Priorities are re-evaluated before each XNode invocation, so the static ILP
  result can be overridden dynamically. **[P]**

### 2.4 Numbers (Jetson AGX Orin)
| Fact | Value |
|---|---|
| Synthetic DAG params | CPU exec 5–95 ms (mean 50 ms); GPU speedup 3–8x; DLA speedup 2–5x; recursive series-parallel, 0.4 terminal prob, +0.1 random cross-edges |
| vs ROS2 | 1.23x–1.88x (small), 1.23x–2.01x (large); **geomean 1.59x / 1.65x** |
| vs XAuto-H (HEFT assignment, XAuto runtime) | 1.22x / 1.24x |
| Ablation: no scheduling (assignment only) | **−16.1%** avg, **−25.4%** at 40 XNodes |
| Ablation: no assignment (scheduling only) | **−37.3%** avg, **−48.3%** at 40 XNodes |
| Real driving case, p99 end-to-end | ROS2 **42.0 ms** → XAuto **26.1 ms** (**1.61x**); HEFT assignment 30.1 ms |
| Same-assignment control | best ROS2 assignment found by exhaustive search = 37.7 ms; XAuto still **1.29x** better → runtime scheduling, not just placement, carries the win |
| ILP solve time | Gurobi, 32 threads: **≤20 XNodes converge <1 min**. Brute force >1 h at 15 XNodes, >24 h at 20 (10²⁷ combinations for 20 XNodes × 3 XPUs) |
| Runtime overhead | ~10% when XNode exec ≈ 0.1 ms, negligible above ~10 ms; **<0.5% total CPU** for 40 XNodes |

### 2.5 What a single-process runtime can adopt
- **The demand-bound constraint as the admission test**, evaluated only at
  stream-admission time, not per launch.
- **Priorities derived from a schedule, not declared by the programmer.** The
  submit seam can carry a policy tag; the *numeric* priority should be computed
  by sorting on predicted finish time.
- The 275 µs / 132 µs figures set the floor for any preempt-based design: a
  preemption that saves less than ~275 µs of deadline slack is a net loss.
- The overhead-vs-node-duration curve is the rule for *when to schedule at all*:
  a scheduler costing ~10% at 0.1 ms nodes is only affordable above ~1 ms.

### 2.6 Testable requirements
1. When the scheduler considers preempting a running kernel, it SHALL do so only
   if the projected deadline gain exceeds the platform's measured
   preempt+switch cost (275 µs measured on Orin; the runtime SHALL measure its
   own rather than assume). `(all)`
2. When admitting a new periodic stream, the runtime SHALL verify
   `Σ_k demand_k([a,b]) ≤ (b − a)` for every interval bounded by release and
   deadline instants inside one hyperperiod prefix, and SHALL reject otherwise.
   `(all)`
3. When a node's measured duration is below 100 µs, the runtime SHALL NOT run a
   per-node scheduling decision for it; it SHALL be batched into a
   pre-recorded submission group. `(all)`
4. When the same DAG can execute on more than one backend (AMDGPU / NVPTX /
   Vulkan / CPU), the assignment decision SHALL be made before the per-node
   ordering decision — assignment is worth ~2.3x more than ordering (37.3% vs
   16.1% ablation). `(all)`
5. When priorities are derived, the runtime SHALL order nodes by predicted
   finish time ascending, and SHALL re-derive before each graph invocation
   rather than once at record time. `(simulation)` `(game)`
6. When the workload exceeds ~20 schedulable nodes, the runtime SHALL NOT
   attempt an exact optimal assignment online. `(all)`

## 3. SURVEY — *Scheduling Techniques of AI Models on Modern Heterogeneous Edge GPU: A Critical Review*
Majeed & Meribout, Khalifa University. arXiv 2506.01377, Jun 2025.

### 3.1 Core content
Systematic comparison of 13 published schedulers for NVIDIA Jetson Xavier/Orin,
whose engines are: CPU (up to 12-core Cortex-A78AE in 3 clusters of 4, 2.2 GHz,
4 MB system cache), GPU (Ampere, **16 SMs**, 1.3 GHz, up to 2048 CUDA + 64 Tensor
cores, up to 170 sparse TOPS), **2× DLA v2** (fixed-function, 2 MB dedicated
SRAM, 9x faster than Xavier's DLA thanks to a local buffer that cuts SDRAM
traffic), **PVA** (Cortex-R5 + 2 DMA engines + 2 VLIW VPUs, 1 MB L2), **2× VIC**
(729.6 MHz Orin / 1036.8 MHz Xavier). All engines share one memory controller
fabric to external LPDDR5 — **memory contention is the survey's named primary
challenge.**

### 3.2 Taxonomy — Table III verbatim

|---|---|---|---|---|---|---|---|
| LP | 2019 | Both | Static | GPU, DLA, CPU (execute) | Multi-DNN | Linear programming | Min overall latency |
| GA | 2020 | Both | Static | GPU, DLA, CPU (process) | Multi-frame | Intra-accel parallelism + pipelining, genetic algorithm | Max throughput, low energy |
| Herald | 2021 | Inter | Static | GPU, DLA | Multi-DNN | Profiling + design-space exploration | Reduce latency |

### 3.3 Taxonomy — the survey's own cross-cutting axes
| Axis | Values | Note |
|---|---|---|
| Decision time | Static (10 of 13) / Dynamic (3) | "Static schedulers are inflexible when sudden changes occur during the execution pipeline" |
| Parallelism direction | **Vertical** = split layers into sub-groups per accelerator (the norm) / **Horizontal** = split a *single layer along its width* so several accelerators compute subsets of the same layer | Only Map-and-Conquer does horizontal; the survey names it the under-explored axis |
| Scope | **Inter**-accelerator / **Intra**-accelerator (multi-stream, multi-thread) / Both | Jedi: 1–6 pre-processing streams, 1–3 post-processing; DLA got 4 streams, GPU 2 |
| Execution mode | Single DNN / Multi-DNN / Multi-frame | Multi-frame ≈ pipelining across frames; Multi-DNN ≈ true co-tenancy |
| Duplication | PND (Partial Network Duplication) — same sub-network instantiated on both DLAs | Jedi only |

| Contention model | none / additive time factor / **multiplicative slowdown coefficient** | HaX-CoNN uses **PCCS**, a processor-centric contention-aware slowdown model, as a per-layer coefficient `C_{N_n,s(N_n)}` |
| Preemption | **none of the 13 preempts** — all are placement/pipelining schedulers | Preemption is absent from this entire literature; XAuto (§2) is the exception in the corpus |

### 3.4 Cost model vocabulary (worth mirroring in the submit seam)
```
L(N_n, s(N_n))                 layer latency on the chosen element
τ(N_n, s(N_n), OUT)            cost to EXIT device s(N_n)
τ(N_{n+1}, s(N_{n+1}), IN)     cost to ENTER the next device
pipeline(N_n, s(N_n))          penalty when consecutive layers land on different sub-units
C_{N_n,s(N_n)}                 contention slowdown multiplier (PCCS)
e(...)                         the same three terms, in energy
ECT, LT, M                     energy target, latency target, memory ceiling
size(F,I)                      memory for intermediate features F and indicator matrix I
```
HaX-CoNN's objective: `latency = Σ_n (L × C) + TR_n·τ_out + TR_n·τ_in`. AxoNN's:
`min latency s.t. energy < ECT`. Map-and-Conquer/MaGNAS: `min P s.t. latency < LT,
energy < ECT, size(F,I) < M`. **[P]**

### 3.5 Admission / feasibility tests found
- **LP scheduler:** plots a **feasibility ratio vs utilization ratio** curve
  (Fig 7). At utilization ratio 1 the system handles on average **12 DNN/RNN
  instances**; adding DLA+GPU+CPU reaches 100% feasibility at **2.8x** the
  DLA-only baseline capacity, with the curve collapsing to 0 past ~3.4x. This is
  a *soft, empirical* schedulability curve, not an analytical bound. **[P]**
- **AxoNN:** Z3 SMT; prediction accuracy **97.1%** on execution time and
  **98.2%** on energy (worst case 78.1% / 71.9%). Solve time: **5 s for one
  transition, ~1 minute for three** on Xavier. **[P]**
- **D-HaX-CoNN:** re-solves online, reaches the ideal solution in **<2 s** for a
  pair of DNNs, re-plans every 10 s, **solver overhead <2% of CPU** while the
  DNNs run concurrently. **[P]**

### 3.6 GPU mechanisms the survey cites as available
**NVIDIA Jetson (Xavier / Orin):**
- CUDA + cuBLAS for GPU; OpenMP for the 2/4/6-core CPU splits; **4 or 8 SMs**
  are the granularity the LP scheduler exposes for the GPU module. **[P]**
- **TensorRT** — builds an optimized engine, chooses GPU *or* DLA per layer,
  mixed precision, inter-layer and intra-layer optimization. **Constraint: a
  layer can be assigned only to DLA or GPU — never to PVA or VIC.** **[P]**
- **DeepStream** (on TensorRT), **VPI** (Vision Programming Interface) for PVA
  and VIC — but VPI limits PVA to tracking, filtering, pre-processing. **[P]**
- **DLA hardware constraints:** FP16 and INT8 only, and for some layers only one
  of the two (Equal → INT8 only; Slice and SoftMax → FP16 only); de-convolution
  padding must be zero; **kernel sizes must be 1–32**. Incompatible layers are
  redirected to GPU, which **interrupts the GPU if it is already occupied**. **[P]**
- Multi-stream inside an engine (TensorRT streams, 1–6 in Jedi). **[P]**
- PND — two instances of the same sub-network on the two DLA units. **[P]**
- The survey explicitly notes **no scheduler uses PVA or VIC**; only one paper
  models their energy/memory contention. **[P]**

**AMD:** the survey covers Jetson exclusively; **it names no AMD mechanism.**
Anything about ROCm/HIP below is mine, not the survey's. **[X]**

### 3.8 What a single-process runtime can adopt
- The full cost vocabulary as submit-seam metadata: per-node cost on each
  backend, **transition cost in and out**, a **contention slowdown multiplier**,
  and the three budget ceilings (latency, energy, memory).
- **Contention as a multiplier, not an addend.** PCCS is the only model in the
  survey that got the concurrent case right, and Herald — which used an additive
  transition cost with no contention term — was *worse than not scheduling at all*.
- The feasibility-ratio-vs-utilization curve as the shape of an empirical
  admission test when analysis is unavailable.
- Solver budgets: an SMT/ILP planner is affordable at ~2 s for 2 streams and
  <2% CPU when re-planned every 10 s. Not per-frame.

### 3.9 Testable requirements
1. When two kernels are considered for co-residency, the runtime SHALL model
   their mutual interference as a multiplicative slowdown on each, measured, and
   SHALL NOT assume additive costs. `(all)`
2. When a kernel chain crosses a backend boundary, the submit seam SHALL carry
   an explicit exit cost and entry cost for that transition, and the scheduler
   SHALL count both. `(all)`
3. When a co-scheduling decision would raise a latency-critical kernel's
   measured latency above its GPU-only latency, the runtime SHALL fall back to
   exclusive execution (the Herald failure mode). `(all)`
4. When a schedule policy names an energy ceiling, the runtime SHALL treat it as
   a hard constraint and minimize latency subject to it, not as a weighted term
   in a scalar objective. `(all)`
5. When an offline planner is used, its solve SHALL be bounded to ≤2 s for a
   two-stream problem and its re-plan interval SHALL be ≥10 s. `(all)`
6. When a node's memory footprint `size(intermediates)` would exceed the
   partition's ceiling, admission SHALL fail before any launch. `(simulation)` `(ML)`
7. When more than one engine class exists, the runtime SHALL expose them
   individually rather than as one pool — the survey's most-cited gap is that
   PVA and VIC are never scheduled despite being 7.6x faster than CPU at their
   own tasks. `(all)`

## 4. SURVEY — *Edge Computing and its Application in Robotics: A Survey*
Tahir & Parasuraman, University of Georgia. arXiv 2507.00523, Jul 2025.

### 4.1 Scope caveat, stated plainly
This is a **networking and task-offloading survey, not a GPU-scheduling survey**.
It contains no GPU preemption mechanism, no kernel granularity, no schedulability
analysis, and **no NVIDIA or AMD GPU scheduling primitives at all**. Its value
here is the constraint landscape and the offload decision structure. Requesting
"GPU mechanisms it cites" returns an empty set — recorded as a finding.

### 4.2 Taxonomies
**Computational domains (Fig 1):** Cloud → {Edge, Fog, Cloudlets} → {Dew, Mist,
Multi-access/Mobile Edge (MEC)}. Fog and Edge are used interchangeably in the
literature and are classified together here.

**Fog vs Edge robotics (Table II), six axes:**
| Aspect | Fog | Edge |
|---|---|---|
| Scope | Intermediate layers between cloud and robots (gateways, local servers) | Computing at or near the robot or sensor |
| Location | Distributed across network nodes | Directly at/on robots or edge devices |
| Control & coordination | Across multiple network nodes (warehouses, local hubs) | Mostly local, near robot or sensor |
| Latency & bandwidth | Reduces via intermediate processing | Minimizes via ultra-local processing |
| Example | Warehouse robots coordinating via local servers with occasional cloud | Robots processing sensor data on nearby embedded devices for real-time tasks |
| Administrative domain | Can span multiple trusted domains | Typically a single domain |

**Characteristics of edge robotics (§III):** Proximity, Low latency, Geographical
distribution, Mobility support (LISP: decouples host identity from location),
Heterogeneity.

**Objective taxonomy (Table III): 33 references × 7 objectives** —
Computational Offloading · Context Awareness · Localization · Navigation ·
Minimizing Latency · Resource Optimization · Minimizing Energy Consumption.
The survey's own conclusion from the table: **context awareness is by far the
least-explored objective**, despite being exactly the input a *dynamic*
offloading decision requires. **[P]**

**Challenge taxonomy (§VI):** Security · Context awareness · Handover mechanism ·
Network failure · Fault tolerance · Heterogeneity.

### 4.3 Numbers worth keeping
| Fact | Value |
|---|---|
| ColaSLAM | feature extraction + matching + transform optimization = **>70% of multi-robot SLAM processing time**; adaptive map redistribution reduces latency up to **40%** vs direct cloud offload, **52%** vs random, **15%** vs greedy |
| COTORRA testbed | orchestration achieved **<15 ms** task latency; but its DLT federation component exhibits a **19-second delay** — "prohibitively high… unsuitable for time-sensitive applications" |
| Lambrecht et al. | up to **38.59% energy savings** on navigation + vision by offloading; but offloading navigation *increased* total operation time |
| Hayat et al. (5G drone) | **partial offloading beats full offloading at every image resolution**, gap widening with resolution; full offloading only wins when the server is ≥2x the drone's compute |
| Qingqing et al. | image quality can be reduced by **an order of magnitude** without harming odometry accuracy |
| Zeng et al. SemCom | ULL-FT feature transmission achieves communication-efficient reliability with no inference-accuracy loss |

### 4.4 What a single-process runtime can adopt
- **Partial > full offload** generalizes to backend selection: moving *part* of a
  chain to a second engine beats moving all of it, unless the second engine is
  ≥2x faster.
- **Precision is a schedulable parameter.** If an order-of-magnitude image
  quality reduction leaves odometry accuracy intact, then a `SchedulePolicy`
  under deadline pressure should be allowed to degrade a stage's precision
  rather than miss.
- The 19-second outlier is the lesson about *any* consensus/synchronization step
  in a real-time path: measure its tail, not its mean.

### 4.5 Testable requirements
1. When a chain can be split across two backends, the runtime SHALL evaluate
   partial splits and SHALL NOT restrict itself to all-or-nothing placement. `(all)`
2. When a second backend is less than 2x faster than the first for a given node,
   the runtime SHALL keep the node local rather than pay the transfer. `(all)`
3. When a stage declares a degradable precision, the runtime SHALL be able to
   select a lower-precision variant to meet a deadline, and SHALL report the
   substitution. `(game)` `(ML)`
4. When any node in a latency-critical chain performs synchronization with an
   external party, the runtime SHALL record its p99 (not mean) and SHALL exclude
   it from a frame-budget policy if the p99 exceeds the budget. `(all)`
5. When a workload is admitted, its context (available engines, thermal state,
   power source) SHALL be an input to the placement decision and SHALL be
   re-read at re-plan boundaries. `(all)`

## 7. cuRobo — *Parallelized Collision-Free Minimum-Jerk Robot Motion Generation*
Sundaralingam et al., NVIDIA. arXiv 2310.17274, 2023.

### 7.1 Core mechanism
Whole-pipeline GPU motion generation. Forward kinematics, sphere positions,
self-collision, world collision, pose cost, bounds/smoothness, and an L-BFGS
optimizer are all CUDA kernels over a *batch of parallel seeds*. The pivotal
structural choice: **the entire forward kinematics + sphere-position computation
is one fused CUDA kernel**, where STORM — the prior art — used **125 separate
kernels** for the same computation. A particle-based (MPPI) phase initializes
L-BFGS, whose line search evaluates a *fixed discrete set* of step magnitudes in
parallel (Armijo/Wolfe) rather than searching iteratively, with a noisy 0.01
fallback that also prevents NaNs. Continuous collision checking is reformulated
as per-sphere sweep-forward/sweep-backward so each timestep's gradient is
independent and parallelizable.

the three facts a scheduler needs most:
1. **Kernels in a real GPU pipeline are 1–12 µs**, and there are ~20 of them per

2. **Graph capture is worth 10x** precisely because of that — the submission
   overhead dominated the device time by roughly an order of magnitude.
3. **Occupancy headroom is a property of the device, not the workload.** A 4090
   absorbs 12x more parallel work for 8 ms; an Orin 15 W pays 417 ms for the
   same increase. Co-scheduling is viable on the former and not the latter, and
   only measurement distinguishes them.

### 7.5 What a single-process runtime can adopt
- **Record-once, replay-many is mandatory, not an optimization.** The submit seam
  must support capturing a whole chain into a replayable object.
- **Fuse aggressively before scheduling.** 125 kernels → 1 is the same
  intervention as graph capture, applied at compile time; cajeta's cooperative
  tile surface is exactly the vehicle for it.
- The GPU-loses-at-batch-1 result (2.7 ms vs 0.9 ms) means the scheduler needs a
  **CPU fallback threshold per node**, not just a backend preference.
- Fixed downstream latency (58/68 ms) must be subtracted from the budget before
  scheduling; the schedulable budget is never the whole period.

### 7.6 Testable requirements
1. When a chain contains more than ~8 kernels whose individual durations are
   under 20 µs, the runtime SHALL capture it as a single replayable submission
   and SHALL NOT issue per-kernel launches. `(all)`
2. When the same logical stage has multiple data representations (OBB / mesh /
   voxel; BVH / grid / hash), the cost model SHALL be keyed on the
   representation, since the measured spread is up to 46x on the same device.
   `(simulation)` `(game)`
3. When measuring a device's co-scheduling headroom, the runtime SHALL sweep
   occupancy (e.g. 4 → 48 concurrent work units) and record the latency delta,
   and SHALL disable co-running when that delta exceeds the frame budget.
   `(game)` `(simulation)`
4. When a node's batch size is 1, the runtime SHALL consider the CPU backend,
   because a GPU implementation can be 3x slower than a good CPU one at batch 1.
   `(all)`
5. When a deadline is declared, the schedulable budget SHALL be the period minus
   measured fixed downstream latency, and the runtime SHALL require that fixed
   latency as an input. `(simulation)` `(all)`
6. When a chain is replayed unchanged, per-invocation host overhead SHALL be
   below 15% of device time (cuRobo's measured host share). `(all)`
7. When a kernel has a structural capacity limit (cuRobo: 1024 spheres from
   warp-wide primitives), the submit seam SHALL carry it and admission SHALL
   fail rather than silently truncate. `(all)`

## 8. MegBA — *A GPU-Based Distributed Library for Large-Scale Bundle Adjustment*
Ren et al. arXiv 2112.01349, 2022.

### 8.1 Core mechanism
Distributed GPU bundle adjustment built on three ideas. (1) **End-to-end
vectorisation**: a custom `JetVector` type stores each partial derivative in its
own contiguous array (structure-of-arrays), so Jacobian construction, Schur
elimination and PCG all become elementwise/BLAS-shaped kernels rather than
block-sparse gather loops. (2) **Distributed PCG over the Schur complement**:
camera blocks are partitioned across GPUs, the reduced camera system is solved by
preconditioned conjugate gradient, and each PCG iteration needs only **two
collective all-reduces**. (3) A **memory-efficient runtime** that reorders and
streams Jacobian blocks so problems exceeding one GPU's memory still solve.

### 8.2 Numbers
| Fact | Value |
|---|---|
| Largest synthetic problem | **80 M observations solved in 216.26 s on 8 GPUs**; **23.54x faster than Ceres** |
| BAL / 1DSfM datasets | consistently ~10–50x over Ceres and g2o at equal final cost |
| Communication per PCG iteration | **two all-reduces** — the entire distributed dependency |

### 8.3 Deadline / rate model
None; MegBA is a batch solver. Its relevance is as the canonical **"many
dependent kernels per solver step with a global barrier"** shape:

```
per LM outer iteration:
  build J           (elementwise, embarrassingly parallel, long kernels)
  Schur elimination (block-sparse → vectorised, still parallel)
  repeat PCG inner:
      SpMV                  (memory-bound)
      dot / axpy            (memory-bound, short)
      ALL-REDUCE            <-- barrier, drains occupancy
      ALL-REDUCE            <-- barrier
  update + cost eval
```

The barriers are the whole scheduling story: an all-reduce serializes the device,
and the shadow it casts is exactly where a complementary kernel from another
stream should run. **[X for the scheduling reading; the structure is [P].]**

### 8.4 What a single-process runtime can adopt
- **Vectorisation makes cost modelling possible.** After SoA vectorisation the
  solve is a sequence of long, regular, memory-bound kernels whose duration is a
  near-linear function of problem size — a scheduler can predict them. The
  pre-vectorisation block-sparse form cannot be predicted.
- **Collective barriers are schedulable events**, and the submit seam should be
  able to declare "this node is a barrier" so the scheduler knows occupancy will
  collapse and can pre-stage a co-runner.
- The arithmetic-character tag has a clear job here: SpMV/dot/axpy are all
  memory-bound, so **co-running two PCG iterations is useless** — the useful
  co-runner is compute-bound work from another stream.

### 8.5 Testable requirements
1. When a node is declared a collective/barrier node, the scheduler SHALL treat
   the interval as an occupancy hole and SHALL be permitted to admit a
   complementary-character kernel into it. `(simulation)`
2. When two ready kernels share the same arithmetic-character tag
   (both memory-bound), the scheduler SHALL NOT co-run them on the same
   partition. `(all)`
3. When a solver chain repeats a fixed inner loop (PCG), the runtime SHALL
   capture the inner loop once and replay it per iteration rather than
   re-recording. `(simulation)`
4. When a problem's working set exceeds device memory, admission SHALL fail with
   the required footprint rather than fall back to paging. `(simulation)`
5. When a node's duration is a predictable function of a declared problem-size
   parameter, the cost model SHALL use that function rather than a scalar
   history. `(simulation)`

## 10. *Real-time High Resolution Fusion of Depth Maps on GPU*
Trifonov (Artec Group / Keldysh Institute). arXiv 1311.7194, 2013.

### 10.1 Core mechanism
An OpenCL dense-reconstruction pipeline over a **block-based sparse TSDF**: the
volume is `N³` coarse blocks, each optionally subdivided into `M³` voxels; two
preallocated GPU buffers (an `N³` offset array and a packed TSDF payload) provide
two-level indirection, and block allocation/deallocation is done on the CPU by
writing offsets. Four stages repeat every frame: **Acquisition → Scene rendering
(raycast or marching cubes) → Registration (ICP) → Fusion (per-voxel Kalman
update)**. Sparsity is exploited in every stage: raycasting renders occupied
blocks' front and back faces into two helper textures to shrink each ray's
traversal interval; marching cubes uses prefix-sum compaction of occupied voxels;
fusion allocates only blocks intersected by the measured surface, updating
already-allocated visible blocks otherwise.

| Fact | Value |
|---|---|
| Dense baseline | 640³ at 4 bytes/voxel = **1 GB** — the whole motivation for sparsity |

### 10.3 Deadline / rate model
Implicit: a scanner frame rate. The paper's structural contribution to a
scheduler is that **a real fixed-rate GPU pipeline has three co-equal stages
with different arithmetic characters**:
- *measurement integration* — scattered writes into a sparse structure,
  allocation-coupled, memory-bound and irregular;
- *ICP registration* — dense reductions, compute-bound, with a **CPU-coupled
  seeding step**;
- *scene rendering* — raycasting, latency-sensitive, and the one whose cost is
  flat in resolution.

None dominates, so a scheduler that optimizes one stage in isolation gains at
most its share of the frame. This is the classic Amdahl constraint on a frame
graph, measured. **[P]** The mapping onto a render graph is **[X]**.

### 10.4 What a single-process runtime can adopt
- **Allocation is part of the schedule.** Block allocation is a CPU action
  interleaved with GPU stages; the scheduler must model host-side allocation
  points as nodes, not as invisible overhead.
- **Two-level indirection is the pattern for sparse tiles**, and the offset
  buffer's size (`4·N³`) is a fixed cost the admission test must count.
- **Choose the algorithm variant whose cost is flat in the scaling parameter.**
  Raycasting over marching cubes is the same decision as cuRobo's OBB over mesh
  — the variant with the better *slope*, not the better point value.
- Fusing the reduction's first stage into the producing kernel (their ICP kernel)
  is the cooperative-tile pattern in 2013 form.

### 10.5 Testable requirements
1. When a pipeline's stages have comparable durations (no stage above ~50% of
   the frame), the runtime SHALL NOT apply a co-scheduling optimization that
   benefits only one stage at the cost of another. `(game)` `(simulation)`
2. When a kernel allocates or frees device memory from the host mid-chain, the
   allocation SHALL be an explicit node in the graph with its own measured cost.
   `(all)`
3. When a sparse data structure is used, its fixed index overhead (here `4·N³`
   bytes independent of occupancy) SHALL be counted in the admission test's
   memory ceiling. `(simulation)` `(game)`
4. When two algorithm variants exist for a stage, the runtime SHALL record cost
   as a function of the scaling parameter and prefer the flatter slope when the
   parameter can grow. `(simulation)` `(game)`
5. When a reduction follows a producing kernel, the first reduction stage SHALL
   be fusible into the producer through the cooperative-tile surface. `(all)`
6. When a stage's input quality varies with a physical parameter (here,
   measurement variance ∝ distance⁴), the runtime SHALL permit per-invocation
   cost hints rather than a single static estimate. `(simulation)`

# Synthesis for deadline-driven pipelines

## S.1 A multi-rate DAG model a runtime could implement

### S.1.1 Entities
```
Stream   σ_i = (T_i, D_i, φ_i, class_i, policy_i)
             T_i     period            (frame period / control period / solver step)
             D_i     relative deadline (D_i ≤ T_i; implicit deadlines are the common case)  [P: DARIS]
             φ_i     phase / offset
             class_i LATENCY_CRITICAL | BEST_EFFORT                                          [P: DARIS HP/LP]
             policy_i THROUGHPUT | LATENCY | FRAME_BUDGET(b) | ENERGY(j)                      [X]

Node     v ∈ V_i, with:
             cost[backend]        measured MRET vector, per backend, per representation       [P: DARIS + cuRobo Tbl 5]
             character            COMPUTE_BOUND | MEMORY_BOUND | LATENCY_BOUND | BARRIER      [X, motivated by MegBA/offload]
             reads[], writes[]    buffer sets                                                  [cajeta's existing seam]
             transition_in/out    cost to enter/leave this backend                             [P: survey 1]
             footprint            device memory, incl. fixed index overhead                    [P: mmap 4·N³]
             capacity_limit       structural caps (cuRobo's 1024 spheres)                      [P]

Edge     (u → v) intra-job precedence.
```

### S.1.2 Multi-rate edges (the part none of the papers formalizes) **[X]**
Cross-stream edges connect graphs of different periods. Three kinds, all needed:
- **Sample edge** (fast consumer, slow producer, `T_prod > T_cons`): consumer
  reads the most recent *complete* producer output through a double buffer.
  Never blocks. This is OpenVLA's action chunking generalized: one producer job
  serves `N = ceil(T_prod / T_cons)` consumer periods, and `N` must be declared
  so the runtime can size the buffer and detect the failure mode.
- **Accumulate edge** (slow consumer, fast producer): consumer reads a reduction
  over the producer jobs since its last release. Needs a reduction kernel that is
  itself a node.
- **Rendezvous edge** (`T_prod == T_cons`, harmonic): ordinary precedence.

Restrict periods to a harmonic set where possible; the hyperperiod is then
`max(T_i)` rather than `lcm(T_i)`, which is what makes the admission test in S.2
cheap. Non-harmonic rates are permitted but the runtime should say so, because
the test then runs over a bounded prefix instead of an exact hyperperiod.

### S.1.3 Release and deadline derivation
```
job k of σ_i:  r_i,k = φ_i + k·T_i
               d_i,k = r_i,k + D_i − fixed_downstream_latency_i     [P: cuRobo 58/68 ms]

node v in job k, virtual deadline (DARIS's proportional rule):      [P]
               d_v = r_i,k + (Σ_{u ⪯ v} mret_u / Σ_{u ∈ V_i} mret_u) · D_i_effective
```
`fixed_downstream_latency` is required, not optional: cuRobo measured 58 ms
(UR5e) and 68 ms (UR10) between "trajectory sent" and "robot moves". The
schedulable budget is never the whole period. The game analogue is
present-to-photon latency; the HIL-simulation analogue is DAC/actuator latency. **[X]**

## S.2 An admission test cheap enough to run online

Two tiers, because the corpus shows the expensive one cannot be online.

**Tier 1 — per-arrival, O(#partitions), a handful of adds (adopt DARIS verbatim):** **[P]**
```
u_new = mret_new / T_new
for each partition k:
    U_k^remaining = N_lanes_k − U_k^latency_critical
    if U_k^besteffort_active + u_new < U_k^remaining:  ADMIT into k
migrate to partition with earliest predicted finish time, else REJECT
```
Cost is a few nanoseconds. It is a *utilization* test, so it is necessary-but-not-
sufficient for hard deadlines — which is exactly right for the classes cajeta
targets, and matches DARIS's measured outcome (zero HP misses, LP DMR <2%).

**Tier 2 — per-admission-of-a-new-stream, demand-bound function (adopt XAuto's constraints (4)(5)):** **[P] with an [X] bound**
```
dbf_i(t) = max(0, floor((t − D_i)/T_i) + 1) · C_i
test:   ∀ t ∈ TestSet:   Σ_i dbf_i(t) ≤ t · m_lanes
```
`TestSet` = the deadline instants inside the hyperperiod. **[X]** With harmonic
periods that is `Σ_i (H/T_i)` points where `H = max(T_i)`; for a 16.67 ms frame
with sub-rates at 2x/4x/8x this is tens of points, evaluable in microseconds.
For non-harmonic periods, truncate to the first busy-period prefix (the standard
bound) and mark the result as *sufficient-with-a-horizon*, not exact.

**Tier 3 — offline only.** XAuto's full ILP: ≤20 nodes in <1 min with Gurobi on
32 threads; brute force is >24 h at 20 nodes. AxoNN's Z3: 5 s for one transition,
~1 min for three. D-HaX-CoNN re-solves in <2 s for two DNNs at <2% CPU with a
10 s re-plan interval. **[P]** So: never per-frame; at most per-10-seconds; and
only for problems under ~20 schedulable nodes. Above that, use the sorted
finish-time heuristic.

**Empirical fallback.** When cost models are unavailable, survey 1's LP
scheduler used a *feasibility-ratio vs utilization-ratio* curve, measured. At
utilization 1 it sustained ~12 concurrent DNN/RNN instances, and adding
DLA+GPU+CPU pushed 100% feasibility to 2.8x the DLA-only capacity before
collapsing past 3.4x. **[P]** A runtime can build the same curve per platform at
install time.

## S.3 Priority inheritance across kernel chains

None of the ten papers implements classical priority inheritance. Two mechanisms
in the corpus do the equivalent job, and both are cheap: **[P]**

1. **Terminal-node promotion (DARIS "Last").** The final node of a chain is
   dispatched one level above its class. Removing it cost **+38% worst-case
   high-priority response**. In a frame graph this is the present/composite pass;
   in a solver step it is the state write-back. **[P]**
2. **Missed-predecessor promotion (DARIS "Prior").** A node whose predecessor
   missed its virtual deadline is promoted one level. This propagates urgency
   *forward along the chain* as lateness accumulates — a chain that is falling
   behind climbs the priority ladder. Removing it raised average response for all
   tasks. **[P]**

**What genuine inheritance requires, and what cajeta already has.** **[X]** True
priority inheritance is needed when a low-priority kernel *holds a resource* a
high-priority chain needs. On a GPU the resources are (a) buffers and (b) the
partition itself. cajeta's submit seam already carries **read/write buffer
sets**, which is precisely the resource declaration:
```
when a BEST_EFFORT node B writes a buffer that a LATENCY_CRITICAL node L reads,
    and L's chain is ready,
    B inherits L's priority until B completes.
```
This is the WAR/RAW hazard the seam already computes, reinterpreted as a priority
ceiling. It costs one max() at dispatch. Combined with the two DARIS promotions
it gives: forward urgency propagation (missed predecessor), chain-tail protection
(last node), and hazard-based inheritance (buffer overlap).

**The bound on all of it.** Inheritance only helps if the holder can be finished
or preempted quickly. XAuto measured **275 µs** to preempt and switch on Orin's
GPU. **[P]** So the rule is: inherit and let it run to completion if the holder's
remaining time is under ~275 µs; preempt only above that.

## S.4 Where preemption is actually available on consumer GPUs, and at what granularity

**Paper-sourced:** **[P]**
- Jetson Orin GPU, via TSG (Time Slice Group) enable/disable on the CUDA context
  handle: **275 µs to preempt + switch.** XAuto.
- Jetson Orin DLA, via cuDLA command-queue suspend/resume: **132 µs.** XAuto.
- DARIS's "staging" — synchronization points between DNN sub-tasks — is described
  explicitly as the substitute for hardware preemption: *"a synchronization-based,
  coarse-grained preemption mechanism."* Removing it cost **33% throughput** and
  **+22.5% low-priority deadline misses.**
- Survey 1's 13 schedulers: **none of them preempt.** The entire Jetson
  scheduling literature it reviews is placement + pipelining.

**My assessment of the current landscape, not from the corpus:** **[X]**
| Backend | Mechanism actually reachable from a userspace runtime | Granularity |
|---|---|---|
| NVIDIA consumer (Pascal → Ada) | Stream priorities (`cudaStreamCreateWithPriority`, range from `cudaDeviceGetStreamPriorityRange`, typically 2–3 levels); **green contexts** (`cuGreenCtxCreate`, CUDA 12.4+) for in-process SM partitioning; MPS `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` for cross-process; CUDA Graphs | **Kernel boundary.** Hardware compute preemption exists on Pascal+ but is used by the driver for the display watchdog and the debugger; there is no application API. |
| NVIDIA datacenter | above, plus MIG (A100/H100/A30) | Hard partition, static |
| AMD (RDNA / CDNA, ROCm) | `hipStreamCreateWithPriority`; **CU masking** (`hipExtStreamCreateWithCUMask`) — a per-stream compute-unit bitmask, the closest analogue to green contexts and available on consumer parts; AQL barrier bits for in-queue dependencies without a host round-trip; MES / CWSR (compute wave save-restore) exists in the kernel driver for queue timeouts but is not application-visible; SPX/CPX partitioning on MI300 | **Kernel boundary** for applications; CU masking gives spatial partitioning at CU granularity |
| Vulkan / SPIR-V | Queue priorities (advisory float at device creation); multiple queue families (graphics / compute / transfer); `VK_EXT_global_priority` (LOW/MEDIUM/HIGH/REALTIME — actually enforced by some drivers, typically gated on privilege); timeline semaphores | **Kernel/dispatch boundary.** No preemption API. |
| CPU fallback | OS thread priorities, real cooperative yield | Instruction |

**The conclusion this forces for cajeta.** On every GPU backend cajeta targets,
preemption is a **kernel-boundary** property. Making preemption finer therefore
means making kernels shorter — which reintroduces the launch overhead cuRobo
measured at 10x. The only way out of that trade is a **cooperative tile kernel
that polls a yield flag between tiles**: a long-running kernel that is
*software*-preemptible at tile granularity, so it gets graph-capture economics
and preemption granularity at the same time. That is DARIS's staging pushed one
level down, from between-kernels to between-tiles, and it is exactly what the
"cooperative tile" surface is for. **[X]**

Practical granularity target: a tile whose duration is ~10–50 µs. Below that the
yield check costs too much relative to work; above that the preemption latency
exceeds the 275 µs figure that makes preemption worth doing at all. **[X]**

## S.5 Energy and power as a schedule input

**Paper-sourced:** **[P]**
- Three of the 13 schedulers in survey 1 (AxoNN, Map-and-Conquer, MaGNAS) use
  energy as a **hard constraint**, not a weighted term: `min latency s.t.
  energy < ECT`, and Map-and-Conquer adds `latency < LT` and `size(F,I) < M`.
  Map-and-Conquer achieved **630 mJ → 136 mJ (4.62x)** on VGG-19 at comparable
  25 ms latency.
- **~50.3% of AI-workload energy goes to off-chip traffic** — so *ordering*
  changes energy at fixed FLOPs.
- Precision is the steepest energy lever measured: **0.22 pJ/MAC at 3-bit vs
  1.76 pJ/MAC at 8-bit** (8x), with the mixed-signal advantage collapsing from
  81% to 31% over the same range.
- Platform power for the manipulation stack: VLMaps ~63 W (Thor) / ~50 W (Orin),
  GraphEQA 32/25 W, π0.5 35/30 W, RTAB+nvblox 25/16 W, against a **216 Wh**
  battery with a 30 W baseline draw. Offloading one stage bought **+160%**
  autonomy.
- Jetson power modes (15 W vs 60 W MAXN) change cuRobo's 20-kernel total from
  **316 µs to 662 µs** — a 2.1x cost-model shift from a runtime-settable mode.

**Design consequence.** **[X]** Energy belongs in the policy enum as a *budget
per period* (`ENERGY(joulesPerFrame)`), evaluated as a constraint alongside the
deadline, with three inputs the runtime must own: a measured pJ/op table indexed
by precision, a per-node buffer-traffic count, and a re-derivation trigger on
power-mode change. The last is not optional: a cost table captured at 60 W is
wrong by 2.1x at 15 W.

## S.7 Mapping onto game frame graphs **[X unless marked]**

A render graph at 60 Hz has a **16.67 ms** budget (8.33 ms at 120 Hz) holding 50–300
passes, many of them 20–200 µs. That is cuRobo's regime — 1–12 µs kernels, ~20 per
solve **[P]** — scaled up by an order of magnitude in count. Five direct transfers:

1. **Record once, replay per frame.** cuRobo's 10x from graph capture **[P]** is
   the same result console engines get from pre-recorded command buffers. A
   submit seam that issues per-pass launches will lose an order of magnitude on
   a pass-dense frame. The frame graph *is* the captured graph.

2. **The async compute queue is DARIS's LP class.** DARIS's measured contract —
   zero high-priority deadline misses, best-effort DMR <2%, high-priority
   response 2.5x faster **[P]** — is exactly the contract an engine wants from
   async compute. And DARIS's staging ablation (−33% throughput, +22.5%
   best-effort misses when staging is removed **[P]**) says the async work must
   be cut into yieldable chunks or it will block the graphics queue.

3. **The offload paper's MPS table is a measurement of async-compute starvation.**
   **[P]** Unthrottled co-run costs the latency-critical task **+230%**; an
   explicit reservation brings it to **+3%**. That is precisely the "async
   compute starved my graphics queue" failure console developers describe, with
   numbers attached. On AMD, `hipExtStreamCreateWithCUMask` is the reservation;
   on NVIDIA, green contexts. **The reservation ratio is the frame-budget policy's
   principal knob**, and the 90/10 vs 50/50 asymmetry (3%/261% vs 46%/0%) says
   the right default is nearer 50/50 than 90/10 unless the latency-critical
   stream is genuinely at its deadline.

4. **Present-pass promotion.** DARIS's "Last" rule (+38% worst-case response when
   removed **[P]**) maps onto the final composite/present pass: a missed present
   is a dropped frame no matter how early the G-buffer finished. Promote the
   tail of the chain.

5. **Frame-budget policy = XAuto's objective over one period.** XAuto minimizes
   makespan subject to demand-bound feasibility **[P]**; a frame-budget policy is
   that with the makespan bound fixed at the frame period and everything that
   does not fit deferred to the best-effort class. XAuto's p99 42.0 → 26.1 ms
   result **[P]** is a frame-time result in all but name, and the control that
   matters is that even the *best* static assignment left 37.7 ms — runtime
   ordering carried 1.29x of the win on its own.

Where the mapping breaks: games have a hard *periodic* deadline with no value
after it (a late frame is a dropped frame), whereas the robotics papers mostly
measure soft degradation. So a frame-budget policy should support **discard**, a
mode none of the papers implements: if a best-effort node cannot finish before
present, cancel it rather than let it run into the next frame.

## S.8 Mapping onto time-stepped simulation **[X unless marked]**

A time-stepped solver runs many dependent kernels per step, often with global
reductions, and — for interactive or hardware-in-the-loop use — a wall-clock
budget per step. Four transfers:

1. **MegBA is the shape.** **[P]** Its PCG inner loop is SpMV → dot/axpy → two
   all-reduces, repeated. Every kernel is memory-bound, so co-running two
   solver streams gains nothing; the useful co-runner is compute-bound work.
   That is the whole justification for the arithmetic-character tag on the submit
   seam: **the tag is what tells the scheduler that two ready kernels are
   *not* complementary.**

2. **Barriers are the opportunity.** **[P for the structure, [X] for the reading]**
   An all-reduce drains occupancy. Declaring a node as `BARRIER` lets the
   scheduler pre-stage a complementary kernel into its shadow — the only reliable
   co-scheduling window in a serial solver chain.

3. **Occupancy headroom decides whether co-running is viable at all.** cuRobo's
   Fig 29 **[P]**: 4 → 48 concurrent units costs **+8 ms** on an RTX 4090 and
   **+417 ms** on an Orin 15 W. On a large GPU a solver leaves room; on a small
   one it does not. This must be *probed* at startup per device, not assumed —
   and it is a two-point measurement, so it is cheap.

4. **mmap's three co-equal stages are the multi-rate structure.** **[P]** Its
   acquisition / registration / fusion bands are all comparable and all grow with
   resolution. A simulation has the same shape: a fast inner integrator, a slower
   contact or collision update, a slower render/telemetry path. Those are three
   different periods over shared buffers — the exact case S.1.2's sample and
   accumulate edges exist for. And because no stage dominates, optimizing one in
   isolation is bounded by its share of the step.

**The HIL budget.** For hardware-in-the-loop, the schedulable budget is the
wall-clock step **minus fixed I/O latency** — cuRobo measured 58 ms and 68 ms of
actuation delay on two UR arms **[P]**, which on a 100 ms budget is more than
half of it. A simulation runtime that schedules against the nominal step and
ignores the I/O leg will overrun every time. Make `fixed_downstream_latency` a
required input, not an optional hint.

**What simulation does *not* inherit.** Offline (non-interactive) simulation has
no deadline at all, so the DARIS/XAuto machinery is dead weight there — a pure
throughput policy with graph capture and aggressive fusion is the whole answer.
The deadline apparatus should be inert unless a period is declared.

## S.9 The three findings that most constrain cajeta's design

1. **Preemption is not available at the granularity the problem needs, on any
   consumer GPU, from any of the backends cajeta targets.** The corpus's only
   real preemption number is 275 µs **[P]**, on a Jetson, via a mechanism
   (TSG-on-CUDA-context) that is neither portable nor exposed on desktop parts.
   Survey 1's entire 13-scheduler literature preempts *nothing*. The workable
   answer is the cooperative tile with a software yield check, which is DARIS's
   staging one level down. Design the seam around that, and treat any hardware
   preemption that turns out to be reachable as a bonus.

2. **Unpartitioned co-running is the worst option, not the best.** +230% versus
   +75% for plain serialization **[P]**. A "co-run complementary kernels"
   scheduler that does not also enforce a compute-unit reservation will make
   latency-critical work more than three times slower than doing nothing. The
   reservation — CU masks on AMD, green contexts on NVIDIA — is not an
   optimization on top of co-running; it is a precondition for it.

3. **Per-kernel scheduling decisions cannot be afforded at real kernel sizes.**
   Real kernels are 1–12 µs **[P]**; scheduler overhead is ~10% at 100 µs nodes
   **[P]**; graph capture is worth 10x **[P]**. So the scheduling unit must be a
   *captured chain*, not a kernel, and the scheduler must run at chain-admission
   and chain-completion boundaries — not at every launch. This is the single
   strongest argument for the submit seam carrying whole geometry + buffer-set +
   character + policy for a chain rather than per-dispatch.
