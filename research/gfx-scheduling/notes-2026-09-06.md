# CLASS 1 — GAME RENDERING PIPELINES

## 1.1 FrameGraph — Frostbite (O'Donnell, GDC 2017) — *SOURCES.md*

**Mechanism.** A frame is rebuilt every frame as a graph of passes and resources. In a
*setup* phase each pass declares the resources it creates, reads and writes, using virtual
handles rather than real allocations. A *compile* phase culls passes whose outputs nothing
consumes, computes each resource's first-write/last-read interval, and derives every barrier
and layout transition from the declarations. An *execute* phase realizes the resources
(aliasing memory across disjoint lifetimes) and records the commands. The point is
decoupling: a pass author never writes a barrier and never knows the global frame structure,
so features compose. Async-compute placement and transient memory reuse become derived
properties of the declaration, not hand-authored code.

**Numbers.** None published in an obtainable form (GDC Vault gates the deck).

**Adoptable.** The three-phase split — declare / compile / execute — is the exact shape a
general compute scheduler needs, and it is what makes read/write sets the *only* user-facing
input. Rebuilding per frame (rather than caching a graph) is what allows the graph to be
data-dependent without invalidation logic.

**Requirements.**
- When a pass declares only its resource reads and writes, the runtime must derive every
  barrier, transition and cross-queue fence without further author input. (both)
- When a pass's outputs are not read by any surviving pass, the runtime must cull that pass
  and never record it. (both)
- When two transient resources have disjoint live intervals, the runtime must be free to
  place them in the same memory. (both)
- When the graph is rebuilt from scratch each frame, graph construction cost must stay below
  the per-frame budget it is scheduling into. (game)

## 1.2 Render-graph mechanics — Arntzen "Render graphs and Vulkan" — *SOURCES.md*

**Mechanism.** The most concrete published algorithm. Each pass classifies every resource
as write-only (`loadOp = CLEAR/DONT_CARE`), read-write (`loadOp = LOAD`) or read-only. The
graph is built by walking back recursively from the backbuffer, then reversing and
deduplicating the traversal to get a legal order. A *reordering* pass then spreads passes
apart to maximize overlap, ranked by (1) can these passes be merged into one render pass,
(2) how many passes fit between a write and its dependent read, (3) does the reorder keep
the graph acyclic. Each pass sorts its resources into an *invalidate* bucket (inputs needing
cache invalidation plus layout transition) and a *flush* bucket (outputs needing cache
flush); a barrier is omitted when the caches are already in the right state. Cross-queue
edges must use semaphores, not events, and shared resources are declared `CONCURRENT` to
dodge queue-family ownership transfers.

**Numbers.** None (design article).

**Adoptable.** Verbatim: the invalidate/flush bucket model is a clean way to implement
barrier derivation with redundant-barrier elimination, and the three-key reorder ranking is
a directly implementable overlap heuristic.

**Requirements.**
- When a resource is already in the access/layout state a pass needs, the runtime must emit
  no barrier for it. (both)
- When two passes are adjacent and mergeable, the runtime must prefer that ordering over one
  that maximizes distance between producer and consumer. (game)
- When a dependency crosses queues, the runtime must express it with a semaphore/timeline
  value rather than an intra-queue event. (both)
- When a reorder would introduce a cycle, the runtime must reject it and keep the original
  order. (both)

## 1.3 Unreal RDG and Unity SRP render graph — *SOURCES.md*

**Mechanism.** Two shipping production implementations that agree on the model. Unreal:
`FRDGBuilder::AddPass()` takes a name, a *parameter struct whose members are the read/write
declarations*, pass flags (`Compute` / `Raster` / `AsyncCompute`), and a deferred lambda.
Resources are transient (graph-bounded lifetime, may alias any disjoint-lifetime resource)
or external. A transient allocator plans allocations across the execution timeline; barriers
are derived by graph traversal and emitted as *split* barriers to hide latency. Async-compute
placement is derived by locating the last graphics producer and first graphics consumer of
an `AsyncCompute` pass and putting the fences there. Unity: record-then-execute, with
automatic culling, last-reader-frees, memory reuse for identically-shaped textures, automatic
graphics/compute queue synchronization, and native-render-pass merging on tile-based mobile.

**Numbers.** Unreal reports a "significant reduction in the GPU memory watermark" from
transient aliasing; neither exposes hard figures.

**Adoptable.** Two things a compute scheduler should copy: (a) the read/write declaration is
the *shader parameter binding itself*, so the declaration cannot drift from the actual
access; (b) async-queue assignment is a derived placement of *fences* around a pass tagged
"may run async", not a user-chosen queue.

**Requirements.**
- When a kernel's buffer arguments are bound, those bindings must be the authoritative
  read/write set — there must be no second, separately-maintained declaration. (both)
- When a pass is marked async-eligible, the runtime must place its wait after the last
  producer and its signal before the first consumer on the primary queue, automatically. (game)
- When a resource's last reader completes, its memory must become available for reuse
  without an explicit free. (both)
- When the target is a tile-based GPU, the runtime must be able to merge adjacent passes so
  intermediates stay in tile memory. (game)

## 1.4 Halcyon architecture (Wihlidal, SEED/EA 2018) — `papers/wihlidal-2018-halcyon.pdf`

**Mechanism.** A full engine built on an API-agnostic high-level command stream: every
render command carries a *queue type*, and encoding a command list updates a *queue mask*
that records the scheduling rules and restrictions for that list. Commands are stateless, so
recording is fully parallel; the low-level translation to D3D12/Vulkan is deliberately serial
("basically memcpy speed") because a serial pass gives perfect redundant-state filtering.
Render Graph runs in two phases: *construction* (declares input/output dependencies, serial
by design — a chained hierarchical blur needs each step's input size to size its output) and
*evaluation* (highly parallel; records high-level commands and inserts automatic barriers and
split barriers). Dependencies moved from explicit producer→consumer chaining to *implicit
data flow through explicit nested scopes*, looked up by type, because explicit chaining
produced messy coupling. Graphs compose at different frequencies — async compute, per-GPU,
even out-of-core on another machine.

**Numbers.** PC drivers lose **~5% to aliasing barriers and discards**, which is why Halcyon
uses a simpler memory model than Frostbite's. Multi-GPU transfer through system memory costs
**~1 ms per 15 MB**. Automatic queue scheduling is called out as unsolved: *"it's not enough
to just specify input and output dependencies. You also need heuristics on task duration and
bottlenecks."*

**Adoptable.** The queue-mask-per-command-list idea (a recorded batch carries the set of
queues it is legal on) is a cheap, exact way to constrain placement. The serial-construct /
parallel-evaluate split is the right concurrency shape. And the scope-based implicit dataflow
is the answer to "how do passes find each other's outputs without coupling".

**Requirements.**
- When commands are recorded, they must be stateless so recording parallelizes; state
  filtering must happen in a single serial lowering pass. (both)
- When a command list is built, it must carry a queue mask that the scheduler uses to
  restrict placement. (both)
- When the scheduler assigns queues, dependency edges alone must not be the only input — it
  must also consume per-pass duration and bottleneck estimates. (both)
- When resource aliasing is enabled, the runtime must be able to measure and report the
  aliasing-barrier cost, because it is ~5% of frame time on PC and can exceed the saving. (game)
- When a pass's output must reach a distant consumer, it must be discoverable through a
  typed scope lookup rather than an explicit hand-written edge. (both)

## 1.5 DOOM / idTech 6 (Sousa & Geffroy, SIGGRAPH 2016) — `papers/sousa-2016-idtech6.pdf`

**Mechanism.** The clearest production async-compute schedule. The observation: "shadow and
depth passes barely use compute units — fixed graphics pipeline heavy" and "opaque pass not
100% busy either". So the whole post-processing chain (post / AA / upsample / compose UI)
runs on the *compute queue* while shadows, depth and opaque of **frame N+1** run on the
graphics queue — an explicitly cross-frame overlap. The GUI is rendered into a premultiplied
alpha buffer on the graphics queue so the compose can happen on compute. Present is issued
from the compute queue when available, for lower latency. Crucially they *restrict wave
allocation for async compute* to avoid stealing all compute units and thrashing caches.

**Numbers** (PS4, GCN, 1080p): async compute wave-limit tuning **saved up to 1.5 ms** in
some scenes. Per-pass VGPR tuning for the concurrent case (56 VGPR PS + 24 VS on graphics,
32 VGPR for the upsample CS on compute, giving 4PS+1CS/VS or 3PS+2CS+1VS occupancy)
**saved 0.7 ms** versus a 64-VGPR version. Opaque pass 8.9 ms default → 6.2 ms with
serialized iteration + single-cell fast path (a scalarization result, but it sets the scale:
the whole opaque pass is ~6–9 ms of a 16.7/33.3 ms frame).

**Adoptable.** Two hard lessons: async work must be *resource-capped*, not just scheduled;
and the best overlap partner is often the *next* frame's work, so the scheduler's window must
be able to span a frame boundary.

**Requirements.**
- When co-running a compute kernel against graphics, the runtime must be able to cap the
  co-runner's wave/CU allocation, not merely admit it to a second queue. (game)
- When occupancy is tuned, the register budget must be chosen for the *concurrent* pair, not
  for each kernel in isolation. (game)
- When the graph for frame N is scheduled, work from frame N+1 that has no dependency on
  frame N must be eligible to start. (game)
- When present can be issued from the queue that produced the final image, the runtime must
  allow it rather than forcing a hand-back to the graphics queue. (game)

## 1.6 Practical DirectX 12 (Thomas/AMD + Dunn/NVIDIA, GDC 2016) — `papers/thomas-2016-practical-dx12.pdf`

**Mechanism.** Joint vendor guidance, unusually blunt. Async compute: "use with great care",
"always check this is a performance win", "maintain a non-async compute path", "poorly
scheduled compute tasks can be a net loss" — with the explicit analogy to hyperthreading, and
the rule that two data-heavy techniques throttle shared resources (caches). Two scheduling
models are contrasted: *unrestricted* (simple to implement; downsides are frame-to-frame
non-determinism and no control over which techniques pair) and *explicit scheduling through
fences* (frame-to-frame determinism, app control over pairing, costs more to implement) —
they recommend explicit. Barriers: batch them, use minimal usage flags, avoid read-to-read,
use split barriers. Fences are the sync primitive and are not free.

**Numbers.** Async compute: **"seeing up to a 10% win currently, if done correctly."**
Good pairing: shadow render (I/O limited) with light culling (ALU heavy). Poor pairing:
G-buffer (bandwidth limited) with SSAO (bandwidth limited). Pairing need not be 1-to-1.
**"Each fence is about the same CPU and GPU cost as ExecuteCommandLists"**, and
**"don't expect fences to trigger signals/advance at a finer granularity than once per
ExecuteCommandLists call."** **"Barrier count should be roughly double the number of
surfaces written to."** `COPY_SOURCE` is significantly more expensive than
`SHADER_RESOURCE` because it enables copy-queue access.

**Adoptable.** The determinism argument settles a design question: a scheduler that places
async work by heuristic every frame produces non-reproducible frame times, which is worse
for a game than a slightly worse but stable placement. And the fence cost model
(≈ one submission) bounds how finely a DAG can be sliced across queues.

**Requirements.**
- When the scheduler places co-running work, the placement must be deterministic frame to
  frame given the same graph. (game)
- When a cross-queue dependency is emitted, its cost must be modelled as at least one
  submission, so the scheduler must not split a graph into more queue-crossings than the
  overlap gain pays for. (both)
- When two candidate co-runners have the same dominant bottleneck (both bandwidth, both RT,
  both cache), the scheduler must not pair them. (game)
- When async compute is enabled, a non-async fallback path must remain selectable and must
  be exercised, because async is a measured win, not a guaranteed one. (both)
- When a resource state is set, it must be the minimal set of usage flags that covers all
  subsequent reads, so no read-to-read barrier is needed. (game)

## 1.7 Vendor async-compute guidance — NVIDIA, AMD, Interplay of Light — *SOURCES.md*

**Mechanism.** NVIDIA frames the whole thing as *unit throughput*, not occupancy: async
compute exists "to reduce the number of unused warp slots and facilitate the simultaneous use
of nonconflicting datapaths" (FP / ALU / memory / RT core / tensor core / graphics pipe).
Critically, they identify *where the gap comes from*: resource transitions (barriers) and
descriptor-heap changes trigger a **wait-for-idle**, and "WFI forces all warps on the same
queue to be fully drained" — the drain is the hole async work fills. AMD's model is
hardware-shaped: a single geometry frontend means multiple graphics queues are pointless, and
they "haven't seen significant performance benefits from using more than one compute queue".
AMD is explicit that "manually specifying the tasks to run in parallel is more efficient than
trying to automate this process."

**Numbers.** NVIDIA: don't overlap two RT-core workloads (same units, interference degrades);
be careful with more than two queues when hardware-accelerated GPU scheduling is off; don't
use D3D12 queue priorities to influence async scheduling. AMD: **~10% frame time** recovered
by double-buffering copy-queue uploads to remove an inter-queue stall. Interplay of Light,
measured on **RTX 3080 Mobile at 1080p**: GTAO + raytraced shadows 5.73 → 4.60 ms
(**1.13 ms saved**); GTAO + BRDF LUT + Hi-Z + shadowmap 7.00 → 5.70 ms (**1.30 ms**);
GTAO + RTGI + BRDF LUT over shadowmap 6.63 → 4.71 ms (**1.92 ms**). GTAO over a *rasterized*
shadowmap costs 2.10 ms combined versus 3.22 ms over *raytraced* shadows — same compute pass,
1.1 ms difference purely from the partner's bottleneck.

**Adoptable.** A bottleneck *vector* per kernel (ALU / bandwidth / L2 / RT / geometry /
tensor) is the minimum metadata a co-run scheduler needs; "these two are both bandwidth
bound" must be expressible and must veto a pairing. And the WFI insight gives the scheduler a
target: the drain windows created by its own barriers are where co-runners belong.

**Requirements.**
- When the runtime records a barrier that forces a queue drain, it must treat the drain window
  as a placement opportunity for independent work. (both)
- When two kernels are candidates to co-run, the runtime must compare per-unit bottleneck
  profiles and reject pairs that saturate the same unit. (game)
- When more than one compute queue is requested, the runtime must be able to justify it by
  measurement, defaulting to one graphics + one compute + one copy. (both)
- When the platform has hardware-accelerated GPU scheduling disabled, the runtime must limit
  itself to two concurrently-fed queues. (game)
- When a copy-queue upload feeds a graphics pass, the staging buffer must be double-buffered
  so the graphics queue never stalls on the copy queue. (both)

## 1.8 Timeline semaphores and queue priority — Khronos / Vulkan spec — *SOURCES.md*

**Mechanism.** A timeline semaphore is a monotonically increasing 64-bit counter; submissions
name wait values and signal values. Three properties matter to a scheduler: **wait-before-
signal** (a submission may wait on a value not yet signalled, so an *entire* graph can be
submitted up front and let the GPU sort out the order), **many waiters per signal**, and
**no reset between reuses**. Host-side `vkSignalSemaphore` / `vkWaitSemaphores` /
`vkGetSemaphoreCounterValue` complete the picture. Per-device queue priority is a normalized
float translated to an implementation-defined discrete level; the spec guarantees essentially
nothing. `VK_KHR_global_priority` (core in 1.4) adds system-scope LOW/MEDIUM/HIGH/REALTIME,
queryable per family, defaulting to MEDIUM, overriding per-process priority.

**Numbers.** The spec's own text is the number: "the implementation makes no guarantees with
regards to ordering or scheduling among queues with the same priority"; "an implementation
**may** allow a higher-priority queue to starve a lower-priority queue on the same VkDevice
until the higher-priority queue has no further commands"; "**no specific guarantees** are
made about higher priority queues receiving more processing time". Global priority above
MEDIUM requires privilege (`VK_ERROR_NOT_PERMITTED`) and the spec warns "abuse of this
feature may result in starving the rest of the system".

**Adoptable.** Timeline semaphores are the right internal currency for a dependency DAG:
one counter per queue, each node's completion is a value, and every edge is
`wait(queue, value)`. Wait-before-signal means the scheduler never has to topologically
order its *submissions*, only its *values*. Conversely, queue priority must not be the
mechanism for the scheduler's own priorities — it is advisory and unquantified.

**Requirements.**
- When the runtime expresses a dependency edge, it must use a timeline value, so the whole
  graph can be submitted before any of it has run. (both)
- When the runtime implements its own priority or deadline policy, it must not rely on
  device queue priority to enforce it. (both)
- When a global-priority level above the default is requested and denied, the runtime must
  fall back rather than fail. (both)
- When a high-priority queue is fed continuously, the runtime must itself bound the
  lower-priority queue's starvation, since the driver will not. (both)

## 1.9 GPU work graphs — D3D12 blog + SIGGRAPH 2025 course — *SOURCES.md*, `papers/kuth-2025-work-graphs-course.pdf`

**Mechanism.** GPU-side work generation with hardware scheduling. Three launch modes:
*broadcasting* (a dispatch grid per record, like a compute shader), *coalescing* (hardware
packs multiple records into one thread group up to a declared max, so LDS is shared across
records), *thread* (one thread per record; the scheduler transparently clusters records from
different launches into shared waves — "fully transparent to the programmer... with the
exception that some work graph limits, like the maximum number of output records, are split
up among the invisible group"). Producers allocate consumer records with
`Get{Group,Thread}NodeOutputRecords()`; `DispatchGraph()` starts it from CPU or GPU memory.
The course also documents the hardware path: the command processor's **Micro Engine
Scheduler** owns a set of GFX and compute queues, each a small firmware-programmed processor
with an input ring buffer, and maps incoming commands onto them.

**Numbers.** The motivating cost is stated structurally rather than numerically: with
classic dispatch + barrier chains, "a pipeline must finish its entire computation before any
other pipeline can even start... this can leave many work group processors idle, especially
when a pipeline computation is about to finish" — i.e. the tail of every stage is dead time.
`ExecuteIndirect` adds *empty launches* and forces worst-case memory reservation ("we could
end up rendering all objects or zero objects... we must always be prepared for the worst
case"). Work graphs are acyclic except self-recursion of **depth ≤ 32**, with bounded record
size (bulk data goes through UAVs) and an app-provided backing store from
`D3D12_WORK_GRAPH_MEMORY_REQUIREMENTS`. The AMD/Coburg procedural-forest demo runs
**13–40 ms frame-to-frame**, mitigated by continuous LOD driven by measured frame time.

**Adoptable.** This is the strongest argument for the cooperative-tile surface: the win is
not "fewer launches", it is *eliminating the drain between dependent stages* and
*eliminating worst-case intermediate allocation*. The coalescing launch mode is the exact
semantic a cooperative-tile kernel wants: "give me up to N records, packed, sharing LDS".

**Requirements.**
- When a producer stage's output feeds a consumer stage, the runtime must offer a path that
  does not drain the machine between them. (both)
- When output cardinality is data-dependent, the runtime must not require the caller to
  reserve worst-case intermediate memory. (both)
- When a tile kernel declares a maximum record count per group, the runtime must pack records
  from independent producers into one group up to that maximum. (both)
- When a graph is self-recursive, the runtime must enforce a declared maximum depth. (both)
- When frame time exceeds budget, a work-generating graph must be able to reduce its own
  amplification factor (LOD) rather than overrun. (game)

## 1.10 Whippletree (Steinberger et al., SIGGRAPH Asia 2014) — `papers/steinberger-2014-whippletree.pdf`

**Mechanism.** A persistent-megakernel scheduler: one kernel occupies every SM, worker
blocks loop pulling work items from software queues and branching to the right task body,
and new work is produced by pushing into those queues. Tasks are typed at three
granularities — thread, warp/block-of-threads, and whole-block — which lets the same graph
express both fine-grained items and cooperative-tile work. The queue implementation is the
whole ball game: it must support simultaneous enqueue and dequeue, and contention makes it
the bottleneck, so they use distributed queues, and shared-memory-local queues where the
producer and consumer are the same block.

**Numbers** (GTX 580 / 680 / TITAN, CUDA 5.5): the megakernel variants win all 12 tests,
**up to 4× over time-sliced kernels** (i.e. over successive kernel launches) and **up to 40×
over Softshell**. Shared-memory local queues are **up to 2×** faster than global queues at
larger tree depths, while global queues win at low depth where load balancing across worker
blocks matters more. The crossover is explicit: "TSK becomes more efficient with increasing
tree depth as the relative overhead of kernel launches diminishes", and CUDA Dynamic
Parallelism beats TSK for *small* trees "likely because it avoids CPU-GPU round-trips."

**Adoptable.** The measured crossover is the design rule: persistent/megakernel scheduling
wins exactly when per-item work is small relative to launch cost, and loses when items are
large. A scheduler should therefore own *both* lowerings and pick between them, not commit
to one.

**Requirements.**
- When per-item work is small relative to launch overhead, the runtime must be able to lower
  a kernel DAG onto a persistent worker loop instead of discrete launches. (both)
- When producer and consumer of a queue are the same block, the runtime must use a
  block-local (shared-memory) queue. (both)
- When work is unevenly distributed across worker blocks, the runtime must fall back to a
  global queue for load balance. (both)
- When a task type declares block granularity, the whole block must be dispatched to it
  together so it can use shared memory and wave intrinsics. (both)

## 1.11 GPU preemption — GPreempt (USENIX ATC'25) + Pascal/Volta whitepapers
`papers/fan-2025-gpreempt.pdf`, `papers/nvidia-2016-pascal-whitepaper.pdf`, `papers/nvidia-2017-volta-whitepaper.pdf`

**Mechanism.** Three preemption families, with different costs. *Wait-based* (block-level,
e.g. Effisha) makes each kernel check at thread-block boundaries — cheap, but the arriving
high-priority task still waits for the slowest in-flight block. *Reset-based* kills the
kernel and recomputes later — fast, but requires idempotent kernels, which "scientific
computing and graph computing" violate, and which CUDA Graph makes harder still.
*Switch-based* (GPreempt) sets a short hardware timeslice on best-effort work and does a real
context switch, plus a *hint-based pre-preemption* that starts the switch during the
latency-critical task's data-preparation phase, hiding the cost. On the hardware side,
Pascal made compute preemption **instruction-level** rather than thread-block level
(Kepler/Maxwell); Volta added independent thread scheduling and hardware-accelerated MPS.

**Numbers** (NVIDIA A100 unless noted). GPU context is **44.3 MB** (108 SMs × 420 KB: 164 KB
shared memory + 64K 32-bit registers per SM) versus <1 KB on an x86 CPU; at 1.1 TB/s that is
a **40 µs** context save, and the measured combined preemption overhead is **~100 µs**. With
a best-effort timeslice of **200 µs**, yield takes on average t/2 and at most **~160 µs**.
Block-level preemption *added* **66.4% (5 ms)** to latency-critical latency in a
many-BE-task workload while *removing* **30 ms** in another — i.e. its cost is workload
dependent and can dominate. A minimal `cudaMemcpy` alone costs **~80 µs**.

**Adoptable.** Preemption is a 100 µs-class operation on current hardware. That is the
number every deadline policy must be built around: a scheduler cannot promise a response
time finer than ~100 µs by preemption, so anything tighter must come from *admission control*
(don't launch a long kernel when a deadline is near) or *slicing* (make kernels short by
construction). The pre-preemption hint generalizes: the runtime knows a high-priority
submission is coming while its inputs are still uploading.

**Requirements.**
- When a deadline is closer than the measured preemption cost (~100 µs class), the runtime
  must refuse to admit a long-running low-priority kernel rather than plan to preempt it. (both)
- When the runtime supports preemption, it must measure and expose the platform's actual
  preemption latency rather than assume the vendor's granularity claim. (both)
- When a high-priority submission's input transfers begin, the runtime must begin yielding
  the device before the kernel itself is enqueued. (both)
- When a kernel is not idempotent, the runtime must never use kill-and-restart as its
  preemption mechanism. (simulation)
- When a low-priority kernel is admitted, the runtime must bound its uninterrupted execution
  to a configured timeslice. (both)

## 1.12 Real-time DAG scheduling for GPU tasks (Zhang et al., DAC 2026) — `papers/zhang-2026-rtgpu-dag.pdf`

**Mechanism.** Takes a DAG of kernels and produces a *predictable* makespan. The task is
decomposed into a sequence of *balanced groups*, each holding kernels that may run
concurrently. Within a group, a **parallelism scaling** mechanism adjusts each kernel's
resource demand (grid/block dimensions → SMs required, `m_i`) according to its computation
load, so group members finish at similar times and do not contend. Kernels too large for the
spare capacity are **segmented** into smaller sequential pieces. Group ordering is enforced by
*constructed extra dependencies*, not by priorities — because, they state flatly,
"kernel-level preemption through prioritized CUDA streams is unreliable" and "the GPU's
hardware scheduler introduces non-determinism in the actual execution order of concurrently
launched kernels."

**Numbers.** V100 modelled as **M = 80 SMs**. Versus existing methods: worst-case makespan
reduced **up to 32.8%**, measured execution time **up to 21.3%**. Implemented with stock CUDA
APIs — no driver or hardware changes.

**Adoptable.** This is the concrete answer to "how do I schedule a DAG when I cannot control
the hardware scheduler": shape the *submission* so the hardware has no bad choice left.
Grouping + resource-demand scaling + explicit extra edges is implementable on top of streams
and events alone, which is exactly cajeta.xpu's position.

**Requirements.**
- When kernels in the same concurrency group have unequal loads, the runtime must scale their
  launch geometry so their expected durations match. (both)
- When a kernel's resource demand exceeds the spare capacity of its group, the runtime must
  segment it into sequential pieces rather than let it serialize the group. (both)
- When ordering between groups matters, the runtime must enforce it with explicit dependency
  edges, never with stream priority. (both)
- When the scheduler reports a makespan, that figure must be a bound derived from the group
  decomposition, not an average of observations. (simulation)

## 1.13 Destiny's multithreaded renderer (Tatarchuk, GDC 2015) — `papers/tatarchuk-2015-destiny.pdf`

**Mechanism.** The CPU-side half. A frame is an explicit job graph with pipelined phases:
*simulate → visibility → extract → prepare → submit*. Extract is the latency-critical phase
because it holds the game-state lock; it does a minimal copy and then unlocks so the next
tick's simulation can start, while *prepare* (transforming to GPU-ready form: dual
quaternions, skinning matrices, cloth and particle sim) runs in parallel with the next
simulation. Submit goes wide "to reduce latency by finishing the work faster and to keep GPU
fully saturated without any idle time bubbles". *Render stages* filter what each view
submits, so a shadow view only walks objects subscribed to the shadow-generate stage.

**Numbers.** Moving visibility work out of the latency-sensitive extract phase
**reduced game latency by 3–4 ms on last-gen consoles and ~2–3 ms on current-gen**. Per-
feature *constant budgets* are maintained by LOD bucketing during prepare — e.g. a consistent
per-frame skinning budget — so a busy frame degrades quality rather than overrunning.

**Adoptable.** Two things: pipelining across the frame boundary (phase N+1 of one stage
overlaps phase N of another) is what actually hides latency, and a *per-feature budget* with
quality fallback is the mechanism that makes frame time predictable under bursty load.

**Requirements.**
- When one pipeline phase holds a lock or a serialization point, the runtime must minimize
  the work inside it and move transformation work to a later, parallel phase. (game)
- When a subsystem is given a per-frame budget, the runtime must let it shed work (LOD) to
  stay inside it, rather than overrunning. (game)
- When submission work is parallelized, the goal must be measured as GPU idle time
  eliminated, not CPU throughput. (game)

## 1.14 GPU-driven rendering pipelines (Haar & Aaltonen, SIGGRAPH 2015) — `papers/haar-2015-gpu-driven.pdf`

**Mechanism.** Culling and draw generation move onto the GPU: coarse CPU quad-tree cull →
GPU instance culling (frustum + occlusion) → GPU cluster culling → `MultiDrawIndexed
InstancedIndirect`. The design goal stated up front is "**no CPU/GPU roundtrip**" and support
for *n* viewports/frustums from one pass, with per-instance state persistent for static
instances. The CPU is described as "the scarcest resource".

**Numbers.** Deck is diagram-heavy; the load-bearing claim is structural (round-trip
elimination) rather than a single figure.

**Adoptable.** Establishes the requirement that the count of work items is a GPU-resident
value. A scheduler whose DAG shape depends on a CPU-visible count cannot host this pipeline.

**Requirements.**
- When the number of work items is produced on the device, the runtime must dispatch from a
  device-resident count without a readback. (both)
- When several views share a culling pass, the runtime must let one dispatch feed multiple
  consumer sub-graphs. (game)
- When instance state is static across frames, the runtime must let it persist rather than
  requiring re-upload. (game)

## 1.15 Frame pacing and frame budgets — Android Frame Pacing (Swappy) — *SOURCES.md*

**Mechanism.** The deadline model a game scheduler must satisfy. A render loop that does not
divide the refresh produces frame times like "49 ms, 16 ms, 33 ms" at a perfectly stable
average. Presenting as fast as possible causes *buffer stuffing*: the present queue fills,
the game loop blocks on VSYNC, and a whole frame of latency is added permanently. Swappy
fixes both: presentation timestamps (`EGL_ANDROID_presentation_time`,
`VK_GOOGLE_display_timing`) prevent short frames from presenting early, and sync fences
(`VkFence`) make long frames wait rather than build back-pressure. Auto mode picks the swap
interval from *measured CPU and GPU times*, and disables pipelining for ultra-fast frames to
reduce latency.

**Numbers.** 60 fps = **16.67 ms**; mobile targets are **8–10 ms CPU + 8–10 ms GPU** with
**2–3 ms headroom** for thermal throttling and OS overhead. The achievable rate ladder is
quantized by the panel: 60 Hz → 60/30/20 fps; 60+90 Hz → 90/60/45/30; +120 Hz →
120/90/60/45/40/30. Case study: Mir 2's slow-session rate fell from **40% to 10%**.

**Adoptable.** The scheduler's deadline is not "as fast as possible" and not a continuous
value — it is a *specific quantized instant*, and both earliness and lateness are defects.
That makes the frame budget a hard constraint the DAG must be planned against, with measured
CPU and GPU times as the input.

**Requirements.**
- When a frame's work is scheduled, the runtime must plan against a fixed deadline (e.g.
  16.67 ms at 60 Hz), and must expose measured CPU and GPU time separately. (game)
- When a frame completes early, the runtime must not present it early. (game)
- When frames run long, the runtime must inject a wait rather than let submissions queue up
  and add a frame of latency. (game)
- When the achievable frame rate drops, the runtime must choose the next rung of the
  refresh-rate ladder rather than free-running. (game)
- When measuring against budget, headroom for thermal throttling must be reserved (2–3 ms of
  a 16.67 ms budget on mobile-class hardware). (game)

# CLASS 2 — ENGINEERING SIMULATION (CFD / FEM / PARTICLE / MULTIPHYSICS)

## 2.1 CUDA Graphs and HIP graphs — vendor docs — *SOURCES.md*

**Mechanism.** Capture a repeated sequence of kernels, copies and their dependencies once
(`cudaStreamBeginCapture`/`EndCapture`, or explicit node construction), instantiate it once
(`cudaGraphInstantiate` pre-initializes the kernel descriptors), then replay it with one
submission per iteration. The whole point is that the per-launch CPU work — driver entry,
argument marshalling, descriptor setup — is paid at instantiate time, not per kernel per
iteration. HIP mirrors the API exactly (`hipStreamBeginCapture` … `hipGraphLaunch`), with
the same stated precondition: "a GPU kernel might run faster than the time it takes for the
framework to set up and launch the kernel."

**Numbers** (NVIDIA's own microbenchmark, chain of short kernels):

| scenario | per-kernel time |
|---|---|
| individual launches, sync each kernel | **9.6 µs** |
| overlapped launches, one sync per timestep | **3.8 µs** |
| CUDA graph launch | **3.4 µs** |
| kernel execution alone (floor) | **2.9 µs** |

Graph creation + instantiation ≈ **400 µs once**, amortizing to **~0.02 µs/kernel** over
1000 iterations.

**Adoptable.** Graph capture is the single highest-leverage mechanism for the simulation
class, and the numbers set the decision rule: it buys back the gap between 3.8 µs and 2.9 µs
in the good case and between 9.6 µs and 3.4 µs in the naive case, so it matters when kernels
are ~10 µs or shorter and the graph is replayed hundreds of times.

**Requirements.**
- When the same kernel DAG is submitted more than a threshold number of times with unchanged
  topology, the runtime must capture and replay it instead of re-submitting node by node. (simulation)
- When a graph is captured, instantiation cost must be paid once and amortized; the runtime
  must report the break-even replay count. (simulation)
- When a captured graph's *parameters* change but its topology does not, the runtime must
  update in place rather than re-instantiate. (simulation)
- When the backend is HIP rather than CUDA, the same capture/replay path must be available.
  (simulation)

## 2.2 Kernel batching with CUDA Graphs (Ekelund, Markidis & Peng, 2025) — `papers/ekelund-2025-cudagraph-batching.pdf`

**Mechanism.** The key move is *unrolling several time-step iterations into one graph*, not
just capturing one step. They build a skeleton iterative application, derive an analytic cost
model (graph creation cost linear in node count, execution saving proportional to launches
avoided), and minimize total time over the batch size. The stated framing is exactly the
cajeta problem: "as the GPU's computational capabilities increase, while the execution time
of the computational kernels decreases, the cost of kernel launching remains approximately
constant" — because it is OS, driver, API and fixed setup latency, none of which track GPU
improvements.

**Numbers** (NVIDIA A100 40 GB + AMD EPYC 7302P, CUDA 12.3; also GH200/H100 96 GB).
Graph creation is linear at **≈ 4.2 µs per node** (k_c = 4.18–4.27 × 10⁻⁶ s) with a base of
0.16–0.42 ms, up to **2500 nodes**, after which linearity breaks. The **optimal iteration
batch is ~50–100 kernels per graph**, and it is essentially workload-independent. The
crossover where graphs beat plain launches is at **2–3 graph launches**. Speedup is
**>1.5× for the smallest workloads**, falling as workload grows ("larger workloads have lower
potential performance gain from CUDA Graph"). GPU memory grows linearly with node count, so
the optimal batch is also a memory decision. Validated on Rodinia Hotspot / Hotspot3D and an
FDTD Maxwell solver.

**Adoptable.** Directly: batch size ≈ 100 nodes as a default, a cost model of the form
`T = I·(a/S + b) + I·(k_c·S + b_c)` to pick it per platform, and a rule that a graph is only
worth building if it will be replayed ≥ 3 times.

**Requirements.**
- When the runtime batches iterations into one graph, it must cap the batch at a measured
  optimum (~50–100 kernel nodes on A100-class hardware), not at the whole loop. (simulation)
- When graph node count exceeds the platform's linear-creation regime (~2500 nodes on A100),
  the runtime must split into multiple graphs. (simulation)
- When a graph would be replayed fewer than ~3 times, the runtime must submit directly
  instead. (simulation)
- When choosing batch size, the runtime must account for graph memory growing linearly with
  node count. (simulation)
- When per-kernel work is large, the runtime must expect and report a *smaller* graph benefit
  rather than assuming a fixed win. (simulation)

## 2.3 CUDA Graphs on real benchmarks (Diakun & Czarnul, ICCS 2025) — `papers/diakun-2025-cudagraphs-investigation.pdf`

**Mechanism.** The sober counterweight: NAS Parallel Benchmarks (CG, LU, MG, IS, EP) ported
to CUDA Graphs and compared head-to-head against the stream version across four GPU classes
and five problem sizes.

**Numbers** (RTX 2080 / RTX 4070 Ti / Quadro RTX 8000 / A100 80 GB). **CG: +3.3% average**,
best **+4.13%** (Class C, RTX 4070 Ti). **LU: +2% average on RTX 4070 Ti, +7% on A100,
maximum +11.87%** (Class B). **MG and some IS cases are net negative** — attributed to short
absolute run times where instantiation overhead is not amortized. Related work they cite:
a **524,288-node** graph gave 14%, while a small case ran **306 µs with a graph versus
285 µs without — 7% slower**.

**Adoptable.** The honest expectation for whole-application graph capture on real solvers is
**2–12%**, not the 3× the microbenchmark suggests, and it is *negative* for short runs. So
graph capture must be a measured, per-graph decision with a fallback, and the runtime should
be able to turn it off per graph.

**Requirements.**
- When graph capture is enabled for a DAG, the runtime must measure the captured and
  uncaptured paths and keep the faster one. (simulation)
- When total runtime is short relative to instantiation cost, the runtime must not capture. (simulation)
- When reporting a graph-capture win, the runtime must attribute it to launch-count
  reduction, so a null result on a compute-bound graph is not treated as a defect. (simulation)

## 2.4 GROMACS heterogeneous parallelization (Páll et al., JCP 2020) — `papers/pall-2020-gromacs-jcp.pdf`

**Mechanism.** The most refined production example of a scheduled multi-kernel time step.
Non-bonded work is split into *local-only* and *non-local* (halo-dependent) kernels; PME
long-range electrostatics goes to a separate stream to overlap with short-range; bonded work
is scheduled on the non-local stream because it is small. Dependencies are enforced with
asynchronous *events* between in-order streams, and the design goals are stated explicitly:
maximize CPU–GPU overlap, move data early, keep data on the accelerator as long as possible,
overlap transfer with compute, and *optimize task scheduling for the critical path*. In the
GPU-resident mode the entire innermost iteration including integration runs on the device,
which "can fully remove the CPU from the critical path and reduces the number of
synchronization events."

**Numbers and mechanisms with teeth.** Co-designed with NVIDIA, **stream priority bits were
added to the hardware and exposed in CUDA** specifically so non-local work could launch in a
high-priority stream and *preempt* the local kernel, returning remote forces early while the
local kernel overlaps communication — and they note only **one priority bit** is available and
ask for more. GPU APIs give no fine-grained block-scheduling control, so kernel-tail
imbalance is tuned *indirectly*: pair lists are sorted so long lists are not scheduled late,
and lists are heuristically split when there are too few for the hardware. Kernel tails and
"scheduling gaps during a sequence of short dependent kernels (e.g. the 3D-FFT kernels used
in PME)" are mitigated by overlapping kernels through multiple streams with event
dependencies. The PME/short-range load balancer scans cutoff × grid-spacing combinations
using CPU cycle counters and **converges in a few thousand steps**. GPU pair kernels reach
within 10% of peak throughput around **48k atoms**; below that, "the challenge for small
systems is the overhead incurred from kernel invocation and other fixed-cost operations."

**Adoptable.** Three transferable ideas: split a kernel by *dependency class*
(local vs halo-dependent) so the independent half can start immediately; use priority to
express "this result unblocks a remote peer, get it out first"; and run a periodic online
autotuner that redistributes work between two units at constant accuracy.

**Requirements.**
- When part of a kernel's input depends on a transfer and part does not, the runtime must
  support splitting it so the independent part runs during the transfer. (simulation)
- When a kernel produces a value that unblocks a remote or downstream consumer, the runtime
  must let it be marked so it is dispatched ahead of same-stage local work. (simulation)
- When a sequence of short dependent kernels leaves scheduling gaps, the runtime must be able
  to overlap independent kernels into those gaps via a second queue. (both)
- When the runtime cannot control block scheduling, it must expose launch-geometry and
  work-ordering controls that let a caller reshape the tail. (both)
- When two units can share a workload at constant accuracy, the runtime must provide an
  online balancer that converges within a bounded number of steps and is robust to
  measurement noise and frequency scaling. (simulation)

## 2.5 GROMACS halo exchange redesign (Doijade et al., SC-W 2025) — `papers/doijade-2025-gromacs-halo.pdf`

**Mechanism.** Replaces the CPU-launched pack → copy → exchange → unpack chain with a fused,
GPU-initiated NVSHMEM halo exchange: a single kernel processes all communication pulses in
parallel, an elected warp leader issues asynchronous TMA stores while other warps keep
packing (decoupling warp progress and avoiding block-wide sync), and dependent pulses wait on
per-pulse signals rather than a global barrier. This makes the whole halo exchange
GPU-resident and CUDA-graph-capturable, so a full multi-node time step can be captured.

**Numbers — the best launch-overhead accounting in the corpus.** "GPU kernel launches and
memory copies (typically **2–10 µs**)" and "event dependency management API calls (typically
**< 1 µs**)". A typical GROMACS time step requires "approximately **20 launch API calls and
30 event management calls**", and "at peak iteration rate it reaches **over 50% of GROMACS'
CPU wall-time**. This can throttle GPU execution, leaving idle gaps between kernels."
Iteration rates are sub-millisecond. In fully GPU-resident runs "typically **tens to hundreds
of time-steps are launched before CPU–GPU synchronization is required**". Separately, a
scheduling fix — moving pair-list pruning to a dedicated **low**-priority stream and
introducing a **third, medium**-priority stream for local reduction and update so those
preempt pruning — gave **up to 10%**. NVSHMEM versus MPI on DGX-H100: **+46% at 4 GPUs**
(45k atoms), +4% at 4 GPUs and **+28% at 8 GPUs** (180k), **+17% at 8 GPUs** (360k) — the
gain shrinks as the problem becomes compute-bound.

**Adoptable.** This is the numeric justification for the whole scheduler: at sub-millisecond
steps, launch and event API overhead is **more than half the host's time**, and the fix is
(a) fewer, fused submissions, (b) graph capture of the whole step, (c) *three* priority
tiers, not two.

**Requirements.**
- When a time step issues more than a handful of launches, the runtime must count them and
  report launch+event API time as a fraction of step time. (simulation)
- When the step is fully device-resident, the runtime must allow tens to hundreds of steps to
  be enqueued before requiring a host synchronization. (simulation)
- When priorities are offered, there must be at least three tiers, so a background
  maintenance kernel can be demoted below the critical path without being demoted to the
  same tier as latency-critical work. (both)
- When a communication or transfer step is expressible as a device-side kernel, the runtime
  must allow it inside a captured graph rather than forcing a host round-trip. (simulation)
- When per-pulse dependencies exist inside one fused kernel, the runtime must support
  signal-based intra-kernel ordering rather than requiring separate launches. (simulation)

## 2.6 GPU-aware asynchronous tasks (Choi, Richards & Kale, 2022) — `papers/choi-2022-gpu-aware-async-tasks.pdf`

**Mechanism.** Charm++ overdecomposition: the domain is split into many more chares than
devices, and because "updating only the interior of a domain block does not depend on
neighbors' halo data, it can overlap with the halo exchanges" *automatically* — the runtime
gets overlap from the dependency structure instead of hand-written non-blocking MPI with
manually chosen overlap regions. The paper's honest finding is the counter-pressure:
"performance gains from overdecomposition-driven overlap can degrade with finer task
granularity", because per-operation GPU overheads outweigh the overlap. Their answer is
kernel fusion (fewer, bigger kernels) plus CUDA Graphs (capture the fused sequence), used
together.

**Numbers.** Evaluated on **Summit** (4608 nodes × 2 POWER9 + 6 V100, 16 GB HBM2 each,
dual-rail EDR IB, 23 GB/s injection), Jacobi3D proxy, weak and strong scaling. The
qualitative result that matters: as strong scaling proceeds, "the proportion of kernel launch
overheads in execution time [grows]", and overdecomposition *exacerbates* it — so the runtime
must trade overlap against launch count.

**Adoptable.** The tension is a first-class scheduler concern: more tasks = better overlap
and better load balance, but more launches. A scheduler that owns both the decomposition
factor and the fusion/capture decision can pick the optimum; one that owns only one of them
cannot.

**Requirements.**
- When a domain is decomposed into interior and boundary regions, the runtime must schedule
  interior work concurrently with boundary exchange without the caller writing the overlap. (simulation)
- When decomposition granularity increases the launch count past the overlap benefit, the
  runtime must fuse or capture to compensate. (simulation)
- When both fusion and graph capture are available, the runtime must be able to apply them
  together (fuse first, then capture the reduced sequence). (simulation)

## 2.7 Performance-portable PETSc for GPUs (Mills et al., 2021) — `papers/mills-2021-petsc-gpu.pdf`

**Mechanism.** A survey of what actually goes wrong in a GPU sparse-solver library, framed
around the *kernel queue*. "High-level instructions are issued in the order they arrive in
the queue. Should the queue become empty, the GPU computations and memory transfers will
cease. **One of the most challenging problems currently faced by large-scale
distributed-memory GPU-based computing is preventing this queue from becoming empty.**"
Three countermeasures are named: pipelining (keep enqueuing ahead), kernel fusion, and CUDA
graphs. The structural obstacle is MPI: "even GPU-aware MPI implementations cannot pipeline
MPI calls and kernel launches because the MPI API does not utilize the stream queue... **the
stream queue must be empty for every MPI call**." They also push *outer-loop fusion* —
block Krylov methods and multiple right-hand sides that "significantly decrease the number of
sequentially launched kernels", replacing collections of BLAS-1 dots with a single BLAS-2.

**Numbers.** Determining whether a pointer is host or device (`cudaPointerGetAttributes`)
costs **~0.3 µs on OLCF Summit**, and GPU-aware MPI implementations pay it on every call.
NVIDIA cuSPARSE SpMV on a **V100 reaches only 4% of peak** for extremely sparse matrices —
i.e. the solver inner loop is nowhere near compute-bound, so overhead dominates.

**Adoptable.** "Never let the queue go empty" is the single-sentence statement of what a
kernel scheduler is for. And the MPI finding generalizes to any foreign API in the loop: a
call that requires a drained queue costs the entire pipeline, so such calls must be
identified and hoisted.

**Requirements.**
- When the runtime has ready work, it must keep the device queue non-empty; queue-empty time
  must be a measured, reportable metric. (simulation)
- When an operation requires a fully drained queue, the runtime must classify it as a barrier
  and schedule around it rather than issuing it mid-loop. (simulation)
- When a sequence of BLAS-1-shaped reductions is issued, the runtime must be able to fuse
  them into one kernel. (simulation)
- When a per-call host-side query costs a measurable fraction of launch time (~0.3 µs class),
  the runtime must cache it rather than repeat it per operation. (simulation)

## 2.8 Ginkgo (Anzt et al., ACM TOMS) — `papers/anzt-2020-ginkgo.pdf`

**Mechanism.** A portable sparse-linear-algebra framework whose solver iterations are chains
of small dependent kernels dispatched through several layers of runtime polymorphism (format
selection → executor selection → kernel variant selection). Because that dispatch chain runs
*per operation per iteration*, the paper isolates and measures it directly by running a
1×1 problem where kernel execution time is negligible.

**Numbers.** Per-iteration **framework** overhead, averaged over 10,000 runs of 1,000
iterations: **CGS 1.00 µs, BiCGSTAB 1.26 µs, CG 1.28 µs, FCG 1.45 µs, GMRES 1.51 µs** — "at
most 1.5 µs for any of the solvers". Compare to the 2–10 µs launch cost from §2.5: the
runtime's own dispatch is the same order as a kernel launch.

**Adoptable.** A hard budget for cajeta.xpu's own per-node scheduling cost. If the scheduler
spends more than ~1 µs per kernel node deciding what to do, it has eaten the launch saving it
was built to recover.

**Requirements.**
- When the scheduler dispatches one kernel node, its own host-side cost must be under ~1 µs,
  and must be measurable in isolation with a null kernel. (simulation)
- When dispatch involves several selection layers (backend, variant, format), the result must
  be cached across iterations of an unchanged loop. (simulation)
- When the scheduler is benchmarked, a degenerate-size problem must be part of the suite so
  framework overhead is visible rather than hidden by kernel time. (both)

## 2.9 Taskflow (Huang et al., IEEE TPDS 2021) — `papers/huang-2021-taskflow.pdf`

**Mechanism.** A composable task-graph system with three parts relevant here. (1) `cudaFlow`:
a GPU task graph declared as a first-class task inside the CPU task graph, mapped to a CUDA
graph. (2) `cudaFlowCapturer`: for code you cannot rewrite, capture existing stream calls
into a graph — and the mapping algorithm is spelled out. **Levelize** the capturer graph into
a two-level array in topological order (tasks at one level may run concurrently); assign each
level-member a **round-robin stream** id bounded by a `max_streams` parameter, because "GPU
has a limit on the maximum kernel concurrency (e.g. 32)"; record an event at the producer and
wait on it at the consumer **only for dependencies not already satisfied by being in the same
stream**. (3) Adaptive work stealing that grows and shrinks the worker set with the available
parallelism, avoiding both under-utilization and busy-wait waste.

**Numbers.** Against oneTBB on a large machine-learning workload: **29% faster, 1.5× less
memory, 1.9× higher throughput**. Max kernel concurrency cited as **32 streams**.

**Adoptable.** The levelize + bounded round-robin + same-stream-elides-the-event algorithm is
a complete, implementable DAG→queues mapping, and it is exactly what cajeta.xpu needs to turn
a read/write-derived DAG into stream/queue assignments with the minimum number of events.

**Requirements.**
- When mapping a DAG onto queues, the runtime must levelize it and assign queues round-robin
  within a level, bounded by the platform's maximum kernel concurrency. (both)
- When a dependency's endpoints land in the same queue, the runtime must emit no event for
  it. (both)
- When available parallelism shrinks, the number of active worker threads must shrink with
  it rather than spinning. (both)
- When a device task graph is nested inside a host task graph, the two must compose without
  the host blocking on the device. (both)

## 2.10 Legion (Bauer et al., SC 2012) — `papers/bauer-2012-legion.pdf`

**Mechanism.** The canonical read/write-set→DAG derivation. Tasks name the *logical regions*
they touch, with **privileges** (read-only, read-write, reduce) and **coherence** (exclusive,
atomic, simultaneous, relaxed). Two tasks touching the same region read-only can run in
parallel; if either writes or reduces, coherence modes decide the dependence. Children are
registered in the sequential order the parent spawns them and enqueued for dependence
analysis, so the program is written sequentially and the parallelism is *discovered*.
Scheduling is done by a **software out-of-order processor (SOOP)**, explicitly analogous to
hardware OoO scheduling over register arguments, with a **deferred execution model** that
decouples issuing an operation from when it runs so analysis never blocks.

**Numbers.** Structural contribution; performance figures are application-level.

**Adoptable.** Privileges + coherence is a richer read/write declaration than plain
read/write, and the extra expressiveness pays for itself in exactly the cases a simulation
hits: `reduce` lets many tasks accumulate into one buffer concurrently without a false
serialization, and `atomic`/`simultaneous` coherence distinguishes "I need mutual exclusion"
from "I need ordering". A read/write-only model must serialize all of them.

**Requirements.**
- When a buffer is declared with reduce access, concurrent producers into it must not be
  serialized against each other. (simulation)
- When two tasks both hold read-only access to a buffer, no dependency edge may be
  generated. (both)
- When dependence analysis runs, it must not block issue — analysis for step N+1 must proceed
  while step N executes. (simulation)
- When tasks are spawned in program order, the derived DAG must be equivalent to the
  sequential semantics. (both)

## 2.11 Realm (Treichler et al., PACT 2014) — `papers/treichler-2014-realm.pdf`

**Mechanism.** The event runtime under Legion, and the strongest statement of *deferred
execution*: "all runtime actions are non-blocking" — spawning computation, moving data, and
acquiring reservations all return immediately with an event. Because a deferred model creates
enormous numbers of events, they introduce **generational events**, compressing many logical
events into one object so events can be copied freely and stored in arbitrary data structures
"without reference-counting overhead or explicit deallocation". *Reservations* are the
deferred-model replacement for locks: you request one and get an event, rather than blocking.

**Numbers.** Applications using Realm are **22–135% faster than equivalent implicit
(bulk-synchronous) versions** on the Keeneland supercomputer, including against an
independently written and optimized MPI code. Microbenchmark event trigger rates are one to
two orders of magnitude higher than what the real applications need — i.e. the event system
is deliberately over-provisioned so it never becomes the bottleneck.

**Adoptable.** Two design constraints: nothing in the scheduler API may block, and the
dependency-token representation must be cheap enough to allocate per node without
reference counting. The 22–135% figure is the value of deferred execution over
bulk-synchronous, which is the gap cajeta.xpu is trying to capture.

**Requirements.**
- When any scheduler operation is invoked, it must return immediately with a completion
  token; no API may block the submitting thread. (both)
- When a dependency token is created, its cost must be low enough to allocate one per kernel
  node without reference counting or explicit free. (both)
- When mutual exclusion is needed between deferred operations, it must be expressed as a
  deferred acquisition returning a token, not a blocking lock. (both)
- When the event/token system is benchmarked, its throughput must exceed the application's
  requirement by at least an order of magnitude. (both)

## 2.12 PaRSEC dynamic task discovery (Hoque et al., ScalA 2017) — `papers/hoque-2017-parsec-dtd.pdf`

**Mechanism.** Contrasts two ways to give a runtime a DAG. The *Parameterized Task Graph*
(PTG) is a compressed algebraic description expanded on demand — it never materializes the
whole graph, which is what lets PaRSEC scale, but it must be written in a DSL. *Dynamic Task
Discovery* (DTD) lets the user write ordinary sequential code with loops and conditionals and
call an insert-task API with data-access modes; the runtime discovers the DAG online and
distributedly. The paper's contribution is the optimizations needed to keep online discovery
cheap and a cost model for the overhead of dynamic construction versus PTG's compressed form.

**Numbers.** Overhead is modelled analytically and validated experimentally against dense
linear algebra in shared and distributed memory, compared to other runtimes.

**Adoptable.** The dual-representation idea maps directly: cajeta.xpu's captured graph is the
compressed form (cheap to replay, fixed topology) and its per-submission DAG is the discovered
form (flexible, costs analysis per node). The runtime needs both and needs a rule for when the
discovered form is compressed into the replayable one — a bounded *window* of resident graph
so a million-step loop does not materialize a million-node DAG.

**Requirements.**
- When a loop inserts tasks faster than they retire, the runtime must bound the number of
  resident graph nodes with a window rather than materializing the whole graph. (simulation)
- When a discovered DAG's topology repeats, the runtime must compress it into a replayable
  form. (simulation)
- When the graph is built from sequential insertion order with access modes, the resulting
  parallel execution must be equivalent to the sequential program. (simulation)

## 2.13 Celerity instruction-graph scheduling (Knorr, Salzmann & Thoman, 2025) — `papers/knorr-2025-multigpu-scheduling.pdf`

**Mechanism.** Three levels of IR: a **task graph** (buffer-access declarations, replicated on
all nodes), a **command graph** (the task index space split across devices/nodes, with the
peer-to-peer transfers that split implies), and the paper's contribution, the **instruction
graph** — individual SYCL and MPI operations plus allocations and coherence copies, modelled
as a DAG so that memory management, transfers, communication and kernel launches can all
overlap. The architecture is what matters: a dedicated **scheduler thread** builds command
and instruction graphs, an **executor thread** drives instruction state machines, and
**backend threads** absorb submission latency; all inter-thread communication is unidirectional
through single-producer-single-consumer queues so nothing shares a lock. Two bounding
mechanisms: **horizons** periodically compact tracking structures, bound scheduling
complexity, and act as forward-progress markers that let finished graph regions be pruned;
a **lookahead window** over the command graph lets the scheduler defer committing to a buffer
backing allocation until it has seen enough future accesses, avoiding an alloc/copy/free
resize chain.

**Numbers.** Strong-scaling benchmarks on up to **128 GPUs** in a production cluster.

**Adoptable.** The whole architecture. Specifically: the runtime's own graph analysis must
run *concurrently with* device execution on its own thread, communicating through SPSC queues,
or the analysis becomes the bottleneck at sub-millisecond steps. Horizons are the answer to
unbounded dependency-tracking growth in a million-step loop. Lookahead is the answer to
premature allocation commitment.

**Requirements.**
- When the runtime analyses a graph, that analysis must run on a thread separate from both
  the submitting thread and the execution driver, connected by single-producer-single-consumer
  queues. (both)
- When a long-running loop accumulates dependency-tracking state, the runtime must insert
  periodic horizons that prune completed regions and bound tracking cost. (simulation)
- When buffer sizes are not known until later tasks are seen, the runtime must look ahead a
  bounded window before committing an allocation. (simulation)
- When submission to the backend has latency, it must be absorbed by a separate thread so it
  does not enter the executor's main loop. (both)

## 2.14 StarPU (Courtès, INRIA RR-8278 2013; Augonnet et al., CCPE 2011) — `papers/courtes-2013-starpu-extensions.pdf` + *SOURCES.md*

**Mechanism.** A task is a **codelet** — several per-architecture implementations of one
logical operation (CPU version, CUDA version, OpenCL version) — plus a list of **data handles
with access modes** (R, W, RW). The runtime builds the dependency graph from the handles
alone, keeps a software cache of each handle's replicas per memory node, issues transfers
implicitly when a task is scheduled somewhere its data is not, and dispatches through a
**pluggable scheduling policy**. The performance-model policies (HEFT / dmda) predict each
worker's execution time for the task *and* the transfer time to get its data there, then pick
the worker minimizing the sum — history-based models are built by calibration runs.

**Numbers.** The canonical CCPE paper is paywalled and could not be obtained openly (HAL is
behind a bot challenge); the open INRIA report covers the same task model.

**Adoptable.** Two ideas cajeta.xpu should take: a kernel is a *set* of per-backend
implementations behind one name, and placement decisions must price the *data movement* the
placement implies, not just the compute. The per-handle replica cache is the mechanism that
makes "which device already has this buffer" answerable.

**Requirements.**
- When a kernel has implementations for several backends, the scheduler must choose the
  backend, not the caller. (both)
- When placing a kernel, the runtime must include the cost of moving its inputs to the chosen
  device in the decision. (both)
- When a buffer has a valid replica on the target device, the runtime must not re-transfer
  it. (both)
- When a scheduling policy is selected, it must be replaceable without changing task code. (both)
- When a performance model is used, it must be built from measured history and must degrade
  gracefully when no history exists. (simulation)

# SYNTHESIS A — THE RENDER-GRAPH MODEL AS SCHEDULER REQUIREMENTS

To host a game renderer, a general compute scheduler must be able to express and satisfy the
following. This is the union of Frostbite FrameGraph, Unreal RDG, Unity SRP render graph,
Halcyon, and Arntzen's deep dive, with the vendor async-compute rules layered on.

### A.1 Passes and resources
1. When a unit of work is submitted, it must be a *pass*: a name, a set of resource
   declarations, a queue-class tag (raster / compute / copy / async-eligible), and a deferred
   recording callback. (game)
2. When a pass declares a resource, the declaration must be the binding itself — reads,
   writes and read-writes distinguished — so the declared set cannot drift from the accessed
   set. (game)
3. When a resource is written but never read by a surviving pass, the producing pass must be
   culled. (game)
4. When a resource's declared access is write-only, the runtime must treat the previous
   contents as discardable (`DONT_CARE`), and when read-write, it must preserve them. (game)

### A.2 Derived barriers and transitions
5. When the graph is compiled, every barrier, layout transition and cache flush/invalidate
   must be derived from the declarations; no pass author may write one. (game)
6. When a resource is already in the required state, no barrier may be emitted for it. (game)
7. When latency can be hidden, transitions must be emitted as split barriers (begin early,
   end late). (game)
8. When barriers are emitted, they must be batched, and the total count must be on the order
   of twice the number of written surfaces — a graph that emits materially more must be
   flagged. (game)
9. When resource aliasing is enabled, the runtime must account for the aliasing-barrier and
   discard cost, measured at **~5% of frame time on PC drivers** (Halcyon), and must be able
   to disable aliasing when that cost exceeds the memory saving. (game)

### A.3 Transient resource lifetime and memory
10. When two transient resources have disjoint live ranges, they must be eligible to share
    memory, and the runtime must plan those allocations across the whole execution timeline
    rather than greedily. (game)
11. When a resource's last reader completes, its memory must be reclaimable without an
    explicit free. (game)
12. When a resource must outlive the graph, it must be declarable as external and excluded
    from aliasing. (game)

### A.4 Queue assignment and co-running
13. When a pass is marked async-eligible, the runtime must place its cross-queue wait after
    the last producer and its signal before the first consumer, automatically. (game)
14. When choosing co-runners, the runtime must consult a per-pass bottleneck profile
    (ALU / bandwidth / L1-L2 / RT core / tensor / geometry front-end) and must reject pairs
    that saturate the same unit. Measured effect of getting this right vs wrong:
    **GTAO over rasterized shadows 2.10 ms vs over raytraced shadows 3.22 ms** on RTX 3080
    Mobile. (game)
15. When co-running is enabled, the achievable saving to plan for is **1.1–1.9 ms per frame
    at 1080p on RTX 3080 Mobile**, and **"up to 10%"** frame time per joint AMD/NVIDIA
    guidance — not a multiple. (game)
16. When a co-runner is admitted, the runtime must be able to cap its wave/CU allocation;
    uncapped async compute steals all CUs and thrashes caches (**up to 1.5 ms recovered by
    capping, DOOM on PS4 GCN**). (game)
17. When the same graph is submitted with the same inputs, queue placement must be identical
    frame to frame; heuristic re-placement per frame is a defect because it destroys frame-time
    determinism. (game)
18. When a cross-queue dependency is emitted, its cost must be priced at approximately one
    submission (**"each fence is about the same CPU and GPU cost as ExecuteCommandLists"**),
    and signal granularity must be assumed no finer than one per submission. (game)
19. When the platform exposes one geometry front-end, the runtime must not create more than
    one graphics queue; when vendor guidance says extra compute queues do not pay, the default
    must be one graphics + one compute + one copy. (game)
20. When a barrier forces a wait-for-idle that drains a queue, that drain window must be
    treated as a placement opportunity for independent work. (game)

### A.5 Frame budget and pacing
21. When a frame is scheduled, it must be scheduled against a fixed deadline —
    **16.67 ms at 60 Hz**, with mobile-class targets of **8–10 ms CPU + 8–10 ms GPU and
    2–3 ms reserved headroom** — and CPU and GPU time must be reported separately. (game)
22. When a frame finishes early, it must not be presented early. (game)
23. When frames run long, the runtime must inject a wait rather than let submissions queue,
    because queueing adds a permanent frame of latency (buffer stuffing). (game)
24. When the frame rate cannot be held, the runtime must step down the display's refresh-rate
    ladder (e.g. 90 → 60 → 45 → 30 on a 90 Hz panel) rather than free-run. (game)
25. When a subsystem is given a per-frame budget, it must be able to shed work (LOD) to stay
    inside it — the mechanism that keeps a **13–40 ms** procedural workload inside a
    frame. (game)
26. When work has no dependency on the current frame, it must be eligible to start during the
    current frame — DOOM overlaps frame N's post-processing with frame N+1's shadow/depth/
    opaque, and that cross-frame window is where the async gain actually lives. (game)

### A.6 Construction cost and concurrency
27. When the graph is rebuilt per frame, construction must be a serial pass (so chained
    passes can size their outputs from their inputs) and evaluation/recording must be
    parallel. (game)
28. When recording, commands must be stateless so recording parallelizes; redundant-state
    filtering happens once, serially, at lowering. (game)
29. When a pass needs a resource produced far upstream, it must be findable through a typed
    scope lookup rather than an explicitly authored edge, or the graph acquires
    O(passes²) coupling. (game)
30. When the graph supports composition, sub-graphs must be able to run at different
    frequencies (every frame, every N frames, on another queue, on another device). (game)

# SYNTHESIS B — THE SIMULATION-STEP MODEL AS SCHEDULER REQUIREMENTS

A simulation step is a DAG of dependent kernels executed thousands to millions of times with
identical topology and changing data. The dominant cost at strong scale is not compute — it is
submission, synchronization, and queue starvation.

### B.1 The launch-overhead budget (the numbers to design against)
1. When per-kernel launch cost is budgeted, use **2–10 µs per kernel launch or memcpy** and
   **<1 µs per event/dependency API call** (GROMACS on H100-class hardware). (simulation)
2. When estimating how much of a step is overhead, note a real MD step issues
   **~20 launch calls + ~30 event calls**, which at peak iteration rate is
   **over 50% of host wall-time** and leaves idle gaps between kernels. (simulation)
3. When the naive per-kernel path is measured, budget **9.6 µs/kernel with a sync per kernel,
   3.8 µs overlapped, 3.4 µs via graph, against a 2.9 µs execution floor** (NVIDIA
   microbenchmark). (simulation)
4. When the scheduler's own per-node host cost is budgeted, it must stay under **~1 µs**;
   Ginkgo's entire solver framework dispatch is **1.00–1.51 µs per iteration**, and a
   scheduler costing more than that has eaten what it saves. (simulation)
5. When the runtime is benchmarked, a degenerate (1-element) problem must be in the suite so
   framework overhead is measured directly rather than hidden behind kernel time. (simulation)

### B.2 Graph capture and replay
6. When a DAG's topology repeats, the runtime must capture it once and replay it, provided it
   will be replayed at least **~3 times** (the measured crossover). (simulation)
7. When batching iterations into one graph, the batch must be capped at a measured optimum —
   **~50–100 kernel nodes on A100-class hardware**, essentially workload-independent — and
   not at the whole loop. (simulation)
8. When graph node count approaches the platform's linear-creation regime (**~2500 nodes on
   A100**, above which creation time and execution time both degrade), the runtime must split
   into multiple graphs. (simulation)
9. When sizing a graph, graph creation must be priced at **~4.2 µs per node** plus a
   0.16–0.42 ms base on A100, and graph memory must be priced as linear in node count. (simulation)
10. When a captured graph's parameters change but its topology does not, the runtime must
    update in place rather than re-instantiate (**~400 µs** to instantiate). (simulation)
11. When reporting expected benefit, the honest range for whole-application capture on real
    solvers is **2–12%** (NAS CG +3.3% avg, LU +7% avg on A100, max +11.87%), and it can be
    **negative** for short runs — so capture must be a measured per-graph decision with a
    live fallback. (simulation)
12. When the backend is HIP, the same capture/replay path must exist (`hipGraph`). (simulation)

### B.3 Queue starvation and pipelining
13. When ready work exists, the device queue must never be empty; **queue-empty time must be a
    first-class measured metric** — "one of the most challenging problems currently faced by
    large-scale distributed-memory GPU-based computing is preventing this queue from becoming
    empty" (PETSc). (simulation)
14. When a foreign API call requires a drained queue (GPU-aware MPI does, on every call), the
    runtime must classify it as a full barrier, count it, and schedule around it. (simulation)
15. When the step is fully device-resident, the runtime must allow **tens to hundreds of steps**
    to be enqueued before requiring a host synchronization. (simulation)
16. When graph analysis is performed, it must run concurrently with device execution on a
    dedicated thread, connected by single-producer-single-consumer queues, so the runtime's own
    analysis is never on the critical path. (simulation)
17. When submission to the backend has latency, a separate backend thread must absorb it. (simulation)

### B.4 Halo / boundary overlap
18. When a kernel's inputs divide into an independent (interior) part and a
    transfer-dependent (boundary) part, the runtime must support splitting it so interior
    compute runs during the exchange, without the caller hand-writing the overlap. (simulation)
19. When a kernel produces a value another rank or device is waiting on, it must be markable
    so it is dispatched ahead of same-stage local work — GROMACS had a *hardware stream
    priority bit added* for exactly this, and notes only one bit exists. (simulation)
20. When priorities are offered, there must be **at least three tiers**: GROMACS gained
    **up to 10%** by moving pruning to a low-priority stream and adding a medium tier for
    reduction/update so it preempts pruning while staying below the critical path. (simulation)
21. When overdecomposition increases the launch count past the point where overlap pays, the
    runtime must fuse and/or capture to compensate — the two must be usable together. (simulation)
22. When a communication step is expressible as a device-side kernel, it must be legal inside
    a captured graph rather than forcing a host round-trip. (simulation)

### B.5 DAG derivation from access sets
23. When tasks declare data handles with access modes, the runtime must derive the DAG from
    those alone, and the parallel execution must be equivalent to sequential insertion order. (simulation)
24. When two tasks both hold read-only access, no edge may be generated; when a buffer is
    declared *reduce*, concurrent producers must not be serialized against each other. (simulation)
25. When mapping the DAG onto queues, the runtime must levelize it, assign queues round-robin
    within a level bounded by the platform's max kernel concurrency (**e.g. 32**), and emit
    no event for a dependency whose endpoints share a queue. (simulation)
26. When kernels in one concurrency group have unequal loads, the runtime must scale their
    launch geometry so their durations match, and must segment any kernel too large for the
    group's spare capacity — worth **up to 32.8% worst-case makespan / 21.3% measured**. (simulation)
27. When group ordering matters, it must be enforced with explicit dependency edges, never
    with stream priority — "kernel-level preemption through prioritized CUDA streams is
    unreliable", and the hardware scheduler's execution order for concurrently launched
    kernels is non-deterministic. (simulation)
28. When a loop inserts tasks faster than they retire, the resident graph must be bounded by a
    window and periodically compacted by horizons that prune completed regions. (simulation)
29. When buffer extents are not known until later tasks are seen, the runtime must look ahead a
    bounded window before committing a backing allocation, to avoid alloc/copy/free resize
    chains. (simulation)

### B.6 Placement, backends and preemption
30. When a kernel has multiple backend implementations, the scheduler chooses the backend; when
    it places a kernel, it must price the implied data movement, and must not re-transfer a
    buffer that already has a valid replica on the target device. (simulation)
31. When a scheduling policy is chosen, it must be replaceable without changing kernel code,
    and any performance model must be built from measured history with graceful cold-start. (simulation)
32. When a deadline is tighter than the platform's measured preemption cost, the runtime must
    use admission control instead of preemption. Budget: A100 context is **44.3 MB**
    (108 SM × 420 KB), **40 µs** to save at 1.1 TB/s, **~100 µs** measured end-to-end, and a
    200 µs timeslice yields in **≤160 µs**. Block-granularity preemption can *add*
    **66.4% (5 ms)** to a latency-critical task's latency. (simulation)
33. When a kernel is not idempotent — the normal case in simulation, since global state changes
    during execution — kill-and-restart must never be used as the preemption mechanism. (simulation)
34. When per-item work is small relative to launch cost, the runtime must be able to lower a
    kernel DAG onto a persistent worker loop with software queues instead of discrete
    launches (**up to 4× over successive launches**, Whippletree), using block-local shared
    memory queues where producer and consumer are the same block (**up to 2×** further), and
    falling back to a global queue when load balance dominates. (both)
