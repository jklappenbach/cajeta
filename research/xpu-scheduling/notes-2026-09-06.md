## 1. Strati, Ma, Klimovic — **Orion: Interference-aware, Fine-grained GPU Sharing for ML Applications** (EuroSys '24)

### 1.1 Core mechanism

Orion is a dynamically-linked shim that **intercepts CUDA runtime calls** —
`cudaLaunchKernel`, `cudaMalloc/Memcpy/Memset/Free`, plus cuDNN/cuBLAS entry points for
convolution, batch-norm and GEMM — and buffers each client's operations in a
**per-client software queue** instead of letting them reach the driver. A polling
scheduler thread drains the queues at **individual-operator granularity** (kernels run
10–100s of µs for inference, 100s–1000s of µs for training). High-priority kernels go
straight onto a dedicated high-priority CUDA stream. A best-effort kernel is admitted
only if **all three** hold: (a) no HP kernel is currently running, *or* (b) the BE
kernel's SM footprint is under `SM_THRESHOLD` **and** its arithmetic character is the
*opposite* of the running HP kernel's (compute-bound vs memory-bound), **and** (c) the
sum of expected durations of already-outstanding BE kernels is below `DUR_THRESHOLD`
(default **2.5 %** of the HP request latency). Classification and SM footprint come from
an **offline** Nsight Compute pass: roofline verdict where available, else
compute-bound/memory-bound if the respective utilization exceeds **60 %**, else
`unknown` (unknowns are allowed to co-run with anything). SM footprint is computed
analytically as `sm_needed = ceil(num_blocks / blocks_per_sm)` where `blocks_per_sm` is
the min over the threads / registers / shared-memory limits.

### 1.2 Key quantitative results (V100-16GB, GCP n1-standard-8, PyTorch 1.12, CUDA 10.2)

Utilization of *single* DNN jobs (Table 1) — the motivation:

| workload | batch | SM busy | compute thpt | mem BW | mem cap |
|---|---|---|---|---|---|
| ResNet50 inference | 4 | 24 % | 30 % | 22 % | 9 % |
| MobileNetV2 inference | 4 | 6 % | 18 % | 21 % | 7 % |
| BERT-large inference | 2 | 95 % | 72 % | 28 % | 14 % |
| ResNet50 training | 32 | 81 % | 48 % | 45 % | 32 % |
| Transformer training | 8 | 49.5 % | 29 % | 30 % | 53 % |

Compute throughput spans **18–72 %**, memory bandwidth **21–49 %**, memory capacity
**7–53 %** — and the compute and memory spikes occur at *different* instants.

The controlled co-run (Table 2) is the load-bearing experiment:

| pair | sequential | collocated | speedup |
|---|---|---|---|
| Conv2d + Conv2d | 2.59 ms | 2.63 ms | **0.98×** |
| BN2d + BN2d | 1.78 ms | 1.65 ms | 1.08× |
| Conv2d + BN2d | 2.15 ms | 1.52 ms | **1.41×** |

Conv2d = 89 % compute / 20 % memory; BN2d = 14 % compute / 80 % memory. Two BN2d kernels
each using only 40 % of SMs still interfere badly, because they collide on bandwidth.

End-to-end: inference+training p99 within **14 %** of dedicated-GPU ideal (REEF-N is
2.3–3× worse; REEF averages 3.44× ideal on the Apollo trace, 2.5× on Poisson), aggregate
throughput up to 1.3× (Apollo) / 2.3× (Poisson). Inference+inference p99 within 22 %
(Apollo) / 15 % (Poisson), throughput up to 2× / **7.3×**; MPS is 1.89× ideal p99.
Training+training: HP throughput within 16 % of ideal at 1.6× aggregate (MPS and Streams
lose 1.7×; Tick-Tock loses 1.93×). Cost savings 1.26–1.49×. ResNet50 inference collocated
with ResNet50 training moves compute throughput **7 %→36 %**, memory bandwidth **10 %→47 %**,
SM utilization **11 %→49 %**. On A100-40GB with 5 clients, Orion holds p99 within **9 %**
of ideal (REEF 21 %, MPS 2.2×).

Ablation (what actually pays): stream priorities alone −25 % p95; adding
compute/memory-character matching −48 % more; adding SM-size awareness −54 % more.
**Once character + size are in, stream priorities are marginal.** Interception overhead
< 1 %. Nsight Systems profiling costs +5 % iteration time; Nsight Compute costs **2–5 s
per kernel**, offline only.

### 1.3 Hardware/driver assumptions

- **Holds**: kernel launches are interceptable; stream priorities are advisory only; no
  user-controllable SM placement; no preemption of a submitted kernel. All true on both
  gfx1151 (HSA/ROCm queues) and the 4090.
- **Holds better for cajeta**: Orion pays for LD_PRELOAD-style interception of a
  third-party runtime. cajeta *owns* the submit seam, so the queue, the geometry, and the
  buffer sets arrive for free and correctly typed.
- **Fails / changes on consumer parts**: the compute-vs-memory dichotomy is calibrated
  against a V100 whose ridge point (see Roofline, §7) is high. On gfx1151 the APU shares
  LPDDR5X with the CPU, so the "memory-bound" class is *much* wider and the
  complementarity window is *narrower* — two kernels that look complementary on a 4090
  can both be bandwidth-bound on the APU. `SM_THRESHOLD` and the 60 % classification
  cut-off must be re-measured per device, not copied.
- **Fails**: Orion's profiling depends on Nsight Compute's roofline verdict. cajeta has
  no equivalent oracle; the arithmetic-character tag must come from the compiler
  (byte-traffic / FLOP counts recoverable from the Group/Tile IR) or from a first-run
  measurement, not from a vendor tool.
- Orion's own measured gap: **the GPU cannot schedule kernels during a memcpy**, so
  host↔device transfers show up as unfillable utilization holes. On gfx1151 with unified
  memory this defect largely disappears; on the 4090 over PCIe it does not.

### 1.4 Adopt / adapt / cannot

- **Adopt directly**: per-client software queues with late binding; arithmetic-character
  tag as a first-class scheduling input; the "opposite character" admission predicate;
  the outstanding-BE-duration throttle expressed as a fraction of the protected job's
  deadline; classifying kernels the profiler can't decide as `unknown` and letting them
  co-run freely (they are small).
- **Adapt**: the SM-footprint estimate. Orion computes it from CUDA occupancy rules;
  cajeta must compute the AMD/NVIDIA/SPIR-V equivalent per backend from the Group/Tile
  geometry plus register/LDS pressure the codegen already knows. This is *cheaper* for
  cajeta than for Orion because the numbers are compile-time facts, not queried
  attributes.
- **Cannot**: rely on stream priorities as a correctness mechanism (they never preempt);
  rely on a vendor roofline tool at runtime; assume the three-way {compute, memory,
  unknown} split is enough for a rendering pipeline where the third axis is fixed-function
  (rasterizer, RT cores, texture units).

### 1.5 Requirements

1. **When a kernel is submitted, the seam carries an arithmetic-character tag drawn from
   {compute-bound, memory-bound, indeterminate}, and the tag is derived from measured or
   compiler-derived FLOP-per-byte, never defaulted.** *(all)*
2. **When two runnable kernels carry the same non-indeterminate character tag, the
   scheduler does not co-run them; when they carry opposite tags it may.** *(all)*
3. **When a kernel is tagged `indeterminate`, it is admitted for co-running with any
   partner.** *(all)*
4. **When a candidate best-effort kernel's estimated group footprint exceeds the
   device's group-slot capacity minus the protected kernel's footprint, it is not
   admitted.** *(game, ML)*
5. **When the sum of estimated durations of already-submitted, not-yet-complete
   best-effort kernels exceeds a configured fraction of the protected work item's budget
   (default 2.5 %), no further best-effort kernel is submitted until that set drains.**
   *(game — this is the frame-budget policy's core; ML)*
6. **When the schedule policy is `latency` or `frame-budget`, admitting a best-effort
   kernel must never increase the protected kernel's measured p99 by more than 15 % over
   its solo-run baseline, and a regression test asserts this on both the AMDGPU and CPU
   backends.** *(game, ML)*
7. **When the character tag is unavailable because no profile exists, the first execution
   of that kernel runs solo and records its FLOP/byte, and only subsequent executions are
   eligible for co-running.** *(all)*

## 2. Ng, Demoulin, Liu — **Paella: Low-latency Model Serving with Software-defined GPU Scheduling** (SOSP '23)

### 2.1 Core mechanism

Paella **bypasses the GPU hardware scheduler entirely** by making occupancy observable.
A modified TVM compiler injects, into every kernel, code that makes **one designated
thread per block** atomically append a 64-bit record `{type(8b), smId(8b), kernelId(32b)}`
to a pinned host-visible ring (`notifQ`) at **block start** (reading `%smid` via inline
PTX) and at **block end**, batched so one record covers up to **16 blocks**. A
single-core userspace dispatcher polls `notifQ` and maintains exact live per-SM usage of
**blocks, threads, registers and shared memory** (Table 1). All host CUDA calls are
wrapped: launches go into per-job **waitlists** (active/inactive per CUDA stream
semantics) driven by Boost **stackful coroutines**, and `cudaStreamCreate` returns a
*virtual* stream that is bound to a real one only at dispatch. Kernels are released only
when the dispatcher can guarantee placement, plus a tunable **+B blocks** of slack to
cover the notification round-trip. Policy is SRPT over estimated remaining time
(`Σ_i max(0, C̄_i − c_i)·T̄_i` from profiling runs) with a **deficit-counter** fairness
threshold; both live in red-black trees.

### 2.2 Key quantitative results

- HoL demonstration on a **GTX 1660 SUPER** (22 SMs, 1024 threads/SM, **32 hardware
  queues**): synthetic jobs of 8 kernels × 128 threads × 9 registers, ~300 µs each →
  176 kernels could be resident. Naive job-at-a-time submission fills the 32 queues with
  *dependent* kernels and uses **32/176 = 18 %** of the GPU. Paella gets **2.2×** better
  goodput on the same work.
- Serving-framework overhead: for a single request to NVIDIA Triton, everything that is
  not CUDA execution or memcpy is up to **66 % of end-to-end latency**; for some models
  the platform overhead **doubles** the execution time (Fig. 3 shows >100 % overhead
  ratios for DenseNet121, GoogleNet, GPT2).
- Latency headroom examples: a real-time NLP app sampling voice at 24 kHz has
  **41.5 µs** per inference query.
- Paella vs baseline: **1.4× more load, 1.35× lower latency** from the scheduling
  algorithm alone. Vs Triton: up to **58× more load and 11× lower latency**; 1–3 orders
  of magnitude higher throughput before saturation. Short-vs-long mix (ResNet-18 against
  InceptionV3, whose exec times are 1.58 ms vs 31.2 ms): ResNet-18 p99 improves up to
  **3×** over multi-stream CUDA.
- Instrumentation cost (Tesla T4, 90th percentile): notifications with no aggregation
  add **2.2 µs** at 160 blocks; with the aggregation conditional, **5.5 µs** (16 blocks)
  and **6.6 µs** (160 blocks).
- Client CPU: hybrid interrupt-then-poll holds the client at **~23 %** of a core versus
  100 % for pure polling, with no measurable latency loss; a plain Unix-socket baseline
  is ~10 % slower.
- **Scheduler cost budget** (Fig. 9): synthetic delay injected into the scheduling
  decision degrades throughput measurably from the low-µs region upward. The authors
  argue ~30× headroom in dispatch rate for MobileNet-scale jobs on a Xeon Silver 4114.

### 2.3 Hardware/driver assumptions

- **Holds**: hardware queues are finite and strictly FIFO per queue, so a job's own
  dependent kernels can block independent work. NVIDIA Kepler+ has 32 HW queues; AMD's
  HSA queues behave similarly. Both the 4090 and gfx1151 are exposed to this.
- **Holds**: an in-kernel atomic to a pinned host-mapped buffer is cheap, and the
  hardware exposes an SM/CU identifier. `%smid` on NVIDIA; `HW_ID`/`s_getreg_b32` on
  AMDGPU. Available on both targets.
- **Partly fails**: Paella needs to *rewrite* every kernel. It cannot instrument cuDNN or
  cuBLAS because the EULAs forbid disassembly. **cajeta has no such problem** — every
  Group/Tile kernel is compiled by cajeta's own KernelLowering, so instrumentation is a
  lowering pass, not a hack. This is the single biggest structural advantage cajeta has
  over Paella.
- **Fails**: Paella runs the dispatcher on a dedicated core at real-time priority. In a
  game or simulation process that core is not free; a frame-budget policy must fold
  dispatch into an existing thread or accept the loss.
- **Stale**: the block-placement predictability Paella depends on ("as long as placement
  is roughly predictable") is weaker on RDNA3, where workgroup distribution across WGPs
  and the CU-pair/dual-issue structure are less documented than Volta-era SM assignment.

### 2.4 Adopt / adapt / cannot

- **Adopt directly**: device→host completion notification as a *compiler-inserted* prolog
  and epilog on the cooperative-tile kernel body; aggregation across a fixed number of
  groups; a lock-free single-writer-per-lane ring in host-visible memory; late binding of
  the launch to a real queue; the "+B groups of slack" idea so the device never idles
  waiting for a host decision.
- **Adopt**: the per-decision cost budget. Paella's central lesson is that
  **software-defined scheduling only wins if the decision itself costs single-digit µs**.
  This is a hard constraint on the cajeta scheduler's data structures.
- **Adapt**: SRPT + deficit fairness fits `throughput` policy; `frame-budget` needs
  earliest-deadline, not shortest-remaining. Paella's remaining-time estimator (mean of
  prior observations per kernel identity) transfers directly.
- **Cannot**: rely on a dedicated real-time core in a game process; instrument
  vendor-blob kernels (irrelevant for cajeta, relevant if cajeta ever calls rocBLAS).
- **Implementation note**: deferred submission means the runtime must hold a *launch
  descriptor* (geometry + buffer set + tag) and issue it later. It cannot hold a closure —
  captured buffers are unreachable from the launch codegen, which is exactly the known
  `kernel launch inside a lambda SIGSEGVs` defect. The submit seam must be a data record.

### 2.5 Requirements

1. **When a cooperative-tile kernel is lowered, the compiler emits a group-start and a
   group-end notification from lane 0 of each group into the runtime's completion ring,
   and the aggregation factor is a compile-time constant (default 16 groups per
   record).** *(all)*
2. **When notification instrumentation is enabled, the added wall-clock cost of an
   otherwise-empty kernel is under 8 µs at 160 groups, asserted by a microbenchmark
   test.** *(all)*
3. **When the scheduler makes an admission decision, that decision costs under 10 µs of
   host CPU, asserted by a benchmark that injects synthetic delay and shows the
   throughput knee.** *(all)*
4. **When the runtime's view of device occupancy says the device has fewer than B groups
   of unstarted work outstanding, the scheduler submits the next eligible kernel even if
   it is not the best choice, so the device never idles on a host round-trip.** *(all)*
5. **When several independent kernels are ready and one job's kernels are mutually
   dependent, the scheduler does not fill the device queues with the dependent chain.**
   *(game, ML — this is the 18 %-of-GPU failure)*
6. **When the schedule policy is `throughput`, kernels are ordered by shortest estimated
   remaining job time, bounded by a deficit counter so no job's deficit exceeds a
   configured threshold.** *(ML, simulation)*
7. **When a launch is deferred, the deferred form is a value-typed launch descriptor
   (geometry, read set, write set, tag, policy), never a closure over the launch site.**
   *(all)*

## 3. Han, Zhang, Chen, Chen — **REEF: Microsecond-scale Preemption for Concurrent GPU-accelerated DNN Inferences** (OSDI '22)

### 3.1 Core mechanism

Two mechanisms on an open-source stack (AMD ROCm + TVM).
**Reset-based preemption** exploits DNN kernel *idempotence* (verified for all 320
kernels of 11 TVM models) to kill rather than drain. Three eviction points: (1) host
queues are reset by nullifying the head pointer, with memory reclaimed **asynchronously**
by a GC thread; (2) device queues use **lazy eviction** — the compiler injects a
preemption-flag check at kernel entry so already-fetched kernels self-terminate — and the
device queue **capacity is capped at 4**; (3) a retrofitted GPU driver call instructs the
command processor to **kill running kernels on the CUs while preserving device memory**.
Restore replays from at most `c = 4` kernels before the last transmitted one.
**Dynamic kernel padding (DKP)** fuses at *runtime*: a template `dkp` kernel partitions
CUs — reserving `ncus` for the real-time kernel and handing the remainder to best-effort
kernels — dispatching through **global** function pointers (so the compiler applies no
register cap and inserts no context save) plus **10 proxy kernels**, one per CU-occupancy
level, and dynamic shared memory. Selection rules: **(R1)** BE kernel exec time < RT
kernel exec time; **(R2)** BE kernel CU occupancy ≥ RT kernel CU occupancy.

### 3.2 Key quantitative results (AMD Radeon Instinct MI50, 60 CUs, 16 GB; i7-10700; ROCm 4.3, TVM 0.8)

Model shape (Table 1): ResNet 307 kernels / 13.6 ms; DenseNet 207 / 3.5 ms; VGG **55** /
4.4 ms; Inception 146 / 8.3 ms; Bert 205 / 5.4 ms. Individual kernel exec times span
**10–255 µs**, with **only a few µs of variance**. VGG's CU usage swings between
**6.7 % and 86.7 %** *within one inference*.

| metric | wait-based | REEF reset-based |
|---|---|---|
| preemption latency, per model | 268 µs (VGG) – 790 µs (ResNet) | **35–38 µs, model-independent** |
| across DISB workloads | — | **15.3–18.5× faster** |
| scaling with #kernels / kernel duration | **linear** | flat |

Breakdown: reset host queue **17 µs → 3 µs** (async reclamation); reset device queue
**424 µs → 31 µs** (capacity restriction); reset CUs **< 3 µs**. The two optimizations
together cut preemption latency **87–92 %**.

Device-queue capacity is the central trade: capacity 1→4 drops normal execution time
14.3 → 12.3 ms; beyond 4 the change is < 0.3 %; preemption latency grows **linearly**
with capacity; host CPU utilization goes 17 % (cap 256) → 31 % (cap 4) → 42 % (cap 1).
Inter-stream **dispatch delay is 20–40 µs**; fetching+dispatching one kernel from the
device queue costs **~20 µs**.

Restore costs 70–245 µs, ~2 % execution overhead (5.1 % for VGG, which has the fewest
kernels). DKP overhead: naive device function pointers cost **78 %–503 %**; global
function pointers cut that to 11.5–120 % (avg 46.4 %); proxy kernels bring it to **0.8 %
average, 1.21 % max**. Memory: static full kernel fusion needs **> 35 GB**; DKP without
the occupancy-merge trick 32 MB; with it **10 KB**. Kernel selection takes **0.2 µs**
(one BE client) to 0.4 µs (many). Padding accuracy: **37 %** of RT kernels see zero
slowdown; **> 90 %** see under 4 µs.

End-to-end: **< 2 % RT latency overhead with up to 7.7× throughput** vs dedicating the
GPU to RT (real Apollo autonomous-driving trace), up to 4.3× on DISB. Multi-stream
baseline amplifies RT latency **2.65–3.31×** for 3.94–8.19× throughput. Concurrency
without control takes RT latency from ~4 ms to **close to 50 ms**.
REEF-N (NVIDIA V100, no CU reset): preemption **71–288 µs**, still **6.3–12.3×** better
than wait-based; the CU-kill is worth another **2.0×**.

### 3.3 Hardware/driver assumptions

- **Assumes an open driver**: the CU-reset path required *retrofitting the AMD driver*.
  On gfx1151 with an open Mesa/ROCm stack this is at least *possible*; on the 4090 it is
  not, and cajeta lands in the REEF-N regime (71–288 µs instead of 35 µs).
- **Assumes idempotence.** True for DNN inference. **False in general** for a game
  pipeline (blend/accumulate passes), for training (weight updates), and for most
  simulation kernels (in-place time-stepping). REEF's own answer is transactionization,
  which they leave to future work.
- **Assumes a controllable device-queue depth.** cajeta's submit seam controls this
  natively — it decides how many descriptors to hand the driver. This is the cheapest
  REEF idea to adopt, and it costs 15–25 % more host CPU.
- **DKP assumes CU count is the only contended resource.** The paper says so explicitly:
  residual RT slowdown is "contention on GPU memory and shared L2 cache". On gfx1151,
  where LPDDR5X is shared with the CPU, that residual is *larger*, and R1/R2 alone will
  not bound interference — Orion's character matching must be layered on top.
- **Stale/hostile**: `global`-function-pointer dispatch with 10 proxy variants is a
  codegen trick against a specific LLVM AMDGPU register allocator. On RDNA3 with dual
  issue and different occupancy quantization, the "10 occupancy levels" number does not
  carry; the *shape* of the trick (generate one variant per occupancy class, not per
  register count) does.

### 3.4 Adopt / adapt / cannot

- **Adopt directly**: cap the in-flight device-queue depth as the primary preemption
  lever, with the depth exposed as a tunable and its host-CPU cost measured; the
  compiler-injected preemption-flag check at kernel entry (cheap, works on closed
  drivers); asynchronous reclamation off the preemption path; latency-predictability of
  kernels as a *precondition* for any of this (variance in µs, not ms).
- **Adopt**: the two DKP selection rules as *guards*, since a padded kernel's duration is
  the max over its parts and its occupancy the min over its parts. These are correctness
  constraints for any cooperative-tile fusion cajeta does, not heuristics.
- **Adapt**: idempotence must become an explicit property of the submit seam, derived from
  the **write buffer set** — a kernel whose write set is disjoint from its read set and
  which does not read-modify-write is restartable. Only restartable kernels may be killed;
  everything else must drain.
- **Cannot**: kill running work on NVIDIA; count on driver retrofits shipping to users;
  assume CU partitioning alone bounds interference.

### 3.5 Requirements

1. **When the runtime submits kernels ahead, at most N descriptors are in flight to the
   driver at once (default 4), N is configurable, and the host-CPU cost of the chosen N
   is reported by a benchmark.** *(all)*
2. **When a kernel's read set and write set overlap, or the kernel performs a
   read-modify-write on a buffer it does not exclusively own, the seam marks it
   non-restartable and the scheduler never cancels it mid-flight.** *(all)*
3. **When a latency-class kernel becomes runnable, the scheduler stops issuing new
   best-effort descriptors within one submit-seam turn, and the observed time from
   arrival to the latency kernel starting on device is under 100 µs on AMDGPU.**
   *(game, ML)*
4. **When two kernels are fused into one cooperative launch, the fused launch's expected
   duration is the max of its parts and its occupancy the min of its parts, and the
   scheduler refuses a fusion whose best-effort part is longer than its latency part.**
   *(game, ML)*
5. **When a kernel's measured duration varies by more than a configured fraction (default
   10 %) across runs at fixed geometry, it is marked unpredictable and excluded from
   duration-based admission decisions.** *(all)*
6. **When cancellation is used, the restart point is at most N kernels back (N = the
   in-flight depth), and the redundant re-execution cost is measured and reported.**
   *(ML)*
7. **When the backend is NVPTX or Vulkan, the runtime does not attempt compute-unit
   reset and falls back to flag-based self-termination plus queue-depth capping.** *(all)*

## 4. Yu, Chowdhury — **Salus: Fine-Grained GPU Sharing Primitives for Deep Learning Applications** (MLSys '20)

### 4.1 Core mechanism

Salus routes **all** GPU access for **all** jobs through one consolidated execution
service, reached from the framework via a thin adaptor, so no GPU context switch between
OS processes ever happens. Two primitives. **(1) Fast job switching at *iteration*
granularity**, made possible by classifying every DL allocation into three types —
*model* (weights, few large chunks, persistent), *ephemeral* (per-iteration scratch,
large, released between iterations), *framework-internal* (small, persistent) — and never
evicting the persistent classes. **(2) Memory sharing via GPU lanes**: the address space
is split into a persistent region and an ephemeral region growing from opposite ends;
the ephemeral region is divided into *lanes*, each backed by a CUDA stream, with
execution serialized within a lane and parallel across lanes. Admission is governed by a
single safety condition: `Σ_jobs P_i + Σ_lanes L_j ≤ C`, where `L_j = max_{i in j} E_i`.
Defragmentation is free — every lane's allocations vanish at the iteration boundary.

### 4.2 Key quantitative results (2× Tesla P100 16 GB, TF 1.5, CUDA 8)

- Peak memory ranges **13.8 GB (resnet152)** down to **35 MB (vae)** across 45 workloads.
  Persistent memory is **110.9 MB (googlenet_25) to 822.2 MB (resnet152_75)** — a small
  fraction of peak. This gap is the whole design.
- Theoretical minimum weight-transfer time at 30 GB/s is **several times the inference
  latency** for their models — so swapping cannot serve inference.
- **They built a kernel-level scheduler and rejected it.** Reasons given: too much
  overhead for the gain, it becomes a central bottleneck, and it *breaks the framework's
  own kernel batching and pipelining*. Plus a **deadlock**: with 12 GB capacity,
  `P_A = P_B = 1 GB`, `E_A = E_B = 7 GB`, progressive allocation interleaves to a state
  where neither job can finish acquiring, and GPUs offer no program-controllable paging.
- Results with iteration-granularity switching: SRTF gives **3.19×** better average JCT
  than FIFO (170.6 → 53.4 min; average queuing 167.6 → **28.6 min**) at essentially
  unchanged makespan (303.4 vs 306.0 min). PACK makespan 287.4 min. FAIR average JCT
  96.6 min. Switching happens at **sub-second** granularity (Gandiva: minutes-long slices,
  ~1 s switch).
- Hyper-parameter sweep of 300 jobs: makespan **2.38×** better for superres_128, but only
  **1.07×** for resnet50_50 — because resnet50_50 is compute-bound, so packing memory
  buys nothing.
- Inference: 42 models (14 architectures × 3) fit on **1 GPU** instead of 42 —
  **42× consolidation**, and **7×** better than MPS which needed 6 GPUs — with **< 5 ms**
  average latency overhead.
- Per-iteration overhead **< 10 %** for most CNNs; worse for models with heavy CPU work,
  which Salus also intercepts.

### 4.3 Hardware/driver assumptions

- **Assumes it can be the sole GPU consumer in the process** and that framework
  allocations are interposable. cajeta satisfies both trivially — it is the runtime.
- **Assumes DL's tri-modal allocation shape.** This holds for ML; it partly holds for
  simulation (persistent state grids + per-step scratch); it holds *well* for game
  rendering (persistent textures/meshes vs per-frame transient targets). The
  persistent/ephemeral split is more general than the paper's DL framing.
- **Fails on capacity for consumer parts**: the numbers are for a 16 GB P100. gfx1151's
  unified memory is large but *shared with the host*; the 4090's 24 GB is not. The safety
  condition still applies; the constant does not.
- **Stale**: NVIDIA MPS's "limited framework support" and TF crashes are 2018-era; UMA
  overcommit performance has improved. But the structural claim — MPS gives you no
  scheduling policy — is still true, and is why cajeta needs its own.

### 4.4 Adopt / adapt / cannot

- **Adopt directly**: the **safety condition** as the admission test for co-running.
  `Σ persistent + Σ (max transient per lane) ≤ capacity` is exactly the check a
  single-process co-scheduler needs before it lets two pipelines overlap, and it is
  cheap.
- **Adopt**: the lane abstraction — a lane is a serialized execution context with a
  reserved transient high-water mark. This maps onto cajeta queues one-to-one, and
  auto-defragmentation at the lane boundary is free for the same reason.
- **Adopt the negative result**: their kernel-level prototype failed on
  (a) central-bottleneck cost and (b) *progressive-allocation deadlock*. cajeta's
  cooperative-tile launches declare their read/write buffer sets **up front**, which is
  precisely what breaks the deadlock — allocation is not progressive if the seam knows
  the whole footprint at submit time. That is a design argument for making the buffer set
  mandatory in the seam, not optional.
- **Cannot**: assume iteration boundaries exist. A rendering frame has them (frame
  boundary); a simulation time-step has them; a fused ML graph launched as one CUDA-graph
  does not.

### 4.5 Requirements

1. **When the scheduler considers co-running two pipelines, it admits them only if the
   sum of their persistent buffer footprints plus the sum of per-lane transient
   high-water marks fits in device memory.** *(all)*
2. **When a kernel is submitted, its read and write buffer sets are complete — the
   scheduler never faces a partially-declared footprint.** *(all — this is what avoids
   Salus's progressive-allocation deadlock)*
3. **When a lane's work item completes, all transient allocations charged to that lane
   are released, so the lane's transient region is defragmented without any copy.**
   *(all)*
4. **When device memory is oversubscribed, the scheduler queues the new pipeline rather
   than admitting it and relying on driver paging.** *(all)*
5. **When a co-scheduling decision is made, it is made at a work-item boundary (frame,
   time-step, minibatch) unless the runtime can prove the footprint at kernel
   granularity.** *(game, simulation)*
6. **When two pipelines are both compute-bound, packing them must not be reported as a
   utilization win — the acceptance test measures makespan, not occupancy.** *(all —
   the resnet50_50 1.07× vs superres 2.38× lesson)*

## 5. Bai, Zhang, Zhu, Jin — **PipeSwitch: Fast Pipelined Context Switching for Deep Learning Applications** (OSDI '20)

### 5.1 Core mechanism

PipeSwitch attacks context-switch cost by decomposing it into four measurable components
and fixing all four. **(a) Pipelined model transmission**: because DNNs are layered and
computed layer-by-layer, transmission over PCIe overlaps computation; naive per-layer
pipelining pays a PCIe call and a synchronization per layer, so layers are combined into
**groups**, and an exponential-search DP with **two pruning rules** (prune a case whose
lower bound already exceeds the best found; never group fewer layers than the number that
fits under the preceding group's compute time) finds the optimal grouping offline.
**(b) Unified memory management**: a **memory daemon** `cudaMalloc`s all GPU memory once
at startup, keeps exactly one pinned host copy of each model, transmits directly to
device, and hands workers **64-bit offsets** rather than CUDA IPC handles — exploiting
that a model's allocation order is deterministic, so daemon and worker derive identical
pointers. **(c) Active-standby worker switching**: separate processes keep process-level
isolation, but old-task cleanup runs *in parallel* with new-task init; cleanup only
deletes pointer metadata, never touches the bytes.

### 5.2 Key quantitative results (AWS p3.2xlarge V100/PCIe3 ×16; g4dn.2xlarge T4/PCIe3 ×8; PyTorch 1.3, CUDA 10.1)

Baseline switch-cost breakdown, ResNet152 (Table 1) — **the number worth pinning**:

| component | T4 | V100 |
|---|---|---|
| task cleaning | 155 ms | 165 ms |
| **task initialization** (process launch + CUDA runtime load + context init) | **5530 ms** | **7290 ms** |
| GPU memory allocation | 10 ms | 13 ms |
| model transmission over PCIe | 91 ms | 81 ms |
| **total** | 5787 ms | 7551 ms |
| inference time itself | 105 ms | 32 ms |

Total overhead after optimization (Table 3): stop-and-start **5355–7536 ms**; NVIDIA MPS
**193–338 ms**; PipeSwitch **5.40–34.56 ms** — i.e. **10–50× better than MPS**.
Task startup to first layer: **2.53–6.57 ms**.

Scheduling-cycle sweep (ResNet152, 8 × p3.2xlarge): stop-and-start throughput is ~zero
for cycles below **10 s**; MPS is flat at ~100 batches/s with ~80 ms average latency
(hundreds of ms for the first batch of a cycle); PipeSwitch stays near the no-switching
upper bound at **1 s** cycles → near-100 % GPU utilization.

Ablations: pipelined transmission saves up to **38.2 ms**; the memory daemon saves
**2–23 ms**; the IPC-offset optimization saves **16–48 ms** (without it, latency is
*worse* than no memory management at all); pinning host pages saves a few ms; CUDA
unified memory *adds* **> 100 ms**. Active-standby saves **116–307 ms** vs one-process
reuse and **5–7 s** vs two processes.

Grouping-algorithm runtime: ResNet152 (**464 layers**) 1.33 s with both prunings, 2.09 s
with pruning-1 only, **3.44 h** with pruning-2 only, **> 24 h** with none.

Two standby workers suffice; each costs a few hundred MB for its CUDA context. Zeroing
ResNet-152's ~240 MB at 900 GB/s is sub-ms. Production trace context: 86 % of tasks are
single-GPU but only 18 % of GPU-hours.

### 5.3 Hardware/driver assumptions

- **The dominant cost — 5.5–7.3 s of task initialization — is a *process* cost**: process
  launch, PyTorch CUDA runtime loading, CUDA context creation. **In a single-process
  cajeta runtime this cost does not exist at all.** That is the single most important
  observation for cajeta from this paper: 95 % of PipeSwitch's problem is self-inflicted
  by the multi-process model.
- **PCIe transmission time is real and remains real** on the 4090 (PCIe 4/5 ×16), and is
  **~zero on gfx1151**, where host and device share LPDDR5X. The pipelining machinery is
  therefore high-value on discrete NVIDIA and near-worthless on the APU.
- **`cudaMalloc` at 10–13 ms per switch is a real, still-current cost** on both vendors,
  and pre-allocating a pool is still the fix.
- **Stale**: MPS at 193–338 ms is a CUDA 10.1 measurement; MPS has improved. The relative
  ordering (pool + pipeline ≫ MPS ≫ stop-and-start) has not changed.
- **Assumes layer-by-layer structure.** Generalizes to any DAG with a fixed issue order —
  which cooperative-tile pipelines have.

### 5.4 Adopt / adapt / cannot

- **Adopt directly**: pre-allocate the device pool once and never call the driver
  allocator on the scheduling path; keep exactly one host-side copy of any large
  read-only resource; pin host staging pages; **never** use unified/managed memory as the
  transfer mechanism on a latency path.
- **Adopt**: overlapping the transfer of stage k+1 with the compute of stage k, grouped
  so the per-transfer fixed cost is amortized. For cajeta this is the *streaming weights /
  streaming texture* case, and the grouping DP's two pruning rules make the search
  tractable (1.33 s vs > 24 h on a 464-node graph).
- **Adapt**: "active-standby workers" becomes "pre-warmed lanes" — reserve the queue,
  the descriptor pool and the scratch allocation *before* the switch, so a switch is
  metadata only.
- **Cannot / need not**: process-level isolation. cajeta is single-process by
  construction; the paper's headline mechanism solves a problem cajeta does not have.
  Which means cajeta should expect switch costs in the **single-ms or below** band, not
  the 5–35 ms band, and should set its acceptance thresholds accordingly.

### 5.5 Requirements

1. **When the runtime starts, it allocates the device memory pool once; no driver
   allocation call occurs on the kernel-submission path.** *(all)*
2. **When a large read-only resource (weights, textures, meshes) is needed on device, the
   runtime holds exactly one host-side pinned copy and streams it, and never routes that
   transfer through unified/managed memory on a latency-class path.** *(game, ML)*
3. **When a pipeline stage's inputs are transferred, the transfer of stage k+1 overlaps
   the compute of stage k, at a grouping granularity chosen so that per-transfer fixed
   cost is under a configured fraction of the group's compute time.** *(ML, game)*
4. **When the backend reports unified host/device memory (gfx1151 APU), the streaming
   pipeline collapses to zero-copy and the transfer stage is elided.** *(all)*
5. **When the scheduler switches between two co-resident pipelines, the switch touches
   only metadata — no reallocation, no re-upload of persistent buffers — and the measured
   switch cost is under 1 ms.** *(game, ML)*
6. **When a grouping search over a pipeline graph is run, it uses both the lower-bound
   prune and the minimum-group-size prune, and completes in under 5 s for a 500-node
   graph.** *(ML)*

## 6. Gujarati et al. — **Serving DNNs like Clockwork: Performance Predictability from the Bottom Up** (OSDI '20)

### 6.1 Core mechanism

Clockwork's thesis is **consolidating choice**: performance variability appears whenever
a *lower* layer is given a choice, so remove the choices. Workers expose exactly three
actions — `LOAD`, `UNLOAD`, `INFER` — each stamped with an **`earliest` and a `latest`
timestamp**. A worker executes **one `EXEC` and one `LOAD` at a time**, refuses any action
whose window has passed (treating it as an error rather than doing best-effort catch-up),
and reports the *measured* duration back. All caching, batching, placement and load
balancing decisions live in one central controller that keeps a per-(model, worker,
batch-size) profile of the **last 10 measurements** and predicts with a **rolling 99th
percentile**. GPU memory is a pre-allocated **PageCache of 16 MB pages** plus a 512 MB
Workspace and a 512 MB IOCache; there is no runtime allocation, **no JIT, and no CUDA
kernel caching**. Executors are pinned to dedicated cores at real-time priority and keep
only **5 ms of outstanding work**.

### 6.2 Key quantitative results (12 × Dell R740, 32 cores, 768 GB RAM, 2 × Tesla V100 32 GB)

- **The predictability claim**: 11 million ResNet50v2 inferences in isolation — the
  **99.99th percentile latency is within 0.03 % of the median** (~2.9 ms).
- **The cost of concurrency**: running inferences concurrently gains up to **25 %
  throughput** and increases **tail latency by 100×**. This single trade is the paper.
- Action costs (Table 1, V100, TVM 0.7): resnet50 weights 102.3 MB, **LOAD 8.33 ms**,
  **INFER B1 2.61 ms** / B16 15.67 ms; resnet152 240.9 MB, LOAD 19.58 ms, B1 7.71 /
  B16 44.60 ms; densenet169 56.5 MB / 4.50 ms; inceptionv3 95.3 MB / 7.77 ms.
  **Weight transfer is ~3× the inference time.**
- **Prediction error**: `INFER` 99th-percentile overprediction **144 µs**,
  underprediction **55 µs**; `LOAD` **431 µs / 348 µs**. Completion-time error compounds
  ~**4×** to a 99th-percentile of **≈1 ms** — and errors are statistically independent,
  so they do not systematically stack.
- vs Clipper and INFaaS: at a 500 ms SLO Clockwork and INFaaS both reach ~800 r/s; below
  a **100 ms** SLO both Clipper and INFaaS **collapse** and only Clockwork serves.
- Scale: **3,601** ResNet50 copies on one worker at a 100 ms SLO. 201 models fill GPU
  memory; PCIe then saturates at 100 %; cold-starts rise to **70 %**; and the **maximum**
  latency across the run never exceeded 100 ms.
- Floor: 6 workers satisfy a **10 ms** SLO at 600 and 1200 r/s and a **74 ms** SLO at
  2400 r/s. Below a 15 ms SLO, many latency-sensitive requests are rejected *in advance*
  — the system declines work it cannot finish.
- Realistic trace (Microsoft Azure Functions, 6 h, 12 workers, 4,026 model instances):
  offered load and goodput both **9,638 r/s**; of **208 million** requests, **58 failed**
  and **zero timed out**; ~987 models cold-start per minute (~25 % of models) but that is
  only 126 r/s = **1.3 %** of requests.
- Scaling limit: peak goodput **103,387 r/s** at N = 110 emulated workers; the centralized
  controller becomes the bottleneck beyond that. Action profiles cost **40 bytes** per
  (model, worker, batch-size).

### 6.3 Hardware/driver assumptions

- **Holds and is the most transferable finding in the corpus**: GPU kernels with no
  data-dependent control flow have deterministic duration. cajeta's cooperative-tile
  kernels (`Group`/`Tile`/`mac`/`reduce` over fixed geometry) are *exactly* this shape.
  REEF measured the same thing independently (variance of a few µs on MI50).
- **Holds**: concurrent `EXEC` makes the hardware scheduler's choices visible as tail
  latency. Confirmed on Volta; the same mechanism exists on RDNA3 and Ada.
- **Fails for cajeta's target workloads in one respect**: Clockwork's "one EXEC at a time"
  is only acceptable because DNN inference *saturates* a V100 at small batch. On gfx1151
  a decode kernel does **not** saturate the device, so serializing would leave the
  interference channel closed but the device idle. This is the direct contradiction with
  Orion/REEF/Paella (see §11).
- **Fails**: 768 GB of host RAM to keep every model warm; a dedicated real-time core per
  executor. Neither is available in a game process.
- **Assumes an SLO exists.** Rendering has one (frame budget); ML prefill/decode has a
  soft one; simulation typically does not.

### 6.4 Adopt / adapt / cannot

- **Adopt directly**: the **(earliest, latest) window on every submitted action**, and
  the rule that a missed window is an *error* and the action is dropped, not retried
  best-effort. This is what stops one late kernel from cascading into the next frame.
- **Adopt**: rolling-window duration profiles per (kernel, geometry, backend) using a
  high percentile, not a mean, plus explicit tracking of over- vs under-prediction. The
  144 µs / 55 µs figures are a realistic accuracy target and a good regression bound.
- **Adopt**: *proactive rejection* — declining work you can prove will miss its deadline
  rather than running it and missing anyway. For a frame-budget policy this is the
  difference between dropping a post-process and dropping a frame.
- **Adopt**: pre-allocated fixed-size pages so the memory state is a single integer
  (free-page count), making admission decisions O(1).
- **Adapt**: "one EXEC at a time" becomes "one EXEC at a time **per character class**" —
  keep Clockwork's determinism guarantee for the protected kernel while letting an
  opposite-character kernel share, which is Orion's compromise.
- **Cannot**: disable JIT and kernel caching wholesale (cajeta is a JIT); keep every
  resource in host RAM; dedicate cores at RT priority in an interactive process.

### 6.5 Requirements

1. **When a kernel is submitted, the descriptor carries an `earliest` and a `latest`
   timestamp, and a kernel whose `latest` has passed at dispatch time is dropped and
   reported, never run late.** *(game, ML)*
2. **When a kernel completes, its measured duration is recorded into a bounded rolling
   window per (kernel identity, geometry, backend), and predictions use a high percentile
   of that window rather than a mean.** *(all)*
3. **When the runtime predicts a kernel duration, over- and under-prediction are tracked
   separately, and 99th-percentile under-prediction stays under 100 µs for kernels marked
   predictable.** *(all)*
4. **When the scheduler can prove a work item will miss its deadline even if dispatched
   immediately, it rejects the item up front rather than dispatching it.** *(game, ML)*
5. **When the schedule policy is `latency`, and no opposite-character partner is
   available, exactly one kernel executes at a time on the device.** *(ML, game)*
6. **When device memory is managed, it is a pool of fixed-size pages so that the
   scheduler's view of memory state is a single free-page count.** *(all)*
7. **When a work item's deadline has an SLO, the runtime reports goodput (items completed
   within deadline) and not just throughput.** *(game, ML)*

## 7. Williams, Waterman, Patterson — **Roofline: An Insightful Visual Performance Model for Multicore Architectures** (CACM 2009)

### 7.1 Core mechanism

Bound-and-bottleneck, not prediction:

```
Attainable GFlop/s = min( peak FP performance,
                          peak memory bandwidth × operational intensity )
```

**Operational intensity is flops per byte of *DRAM* traffic** — traffic measured *after*
the cache hierarchy has filtered it, deliberately *not* processor↔cache traffic (that is
"arithmetic intensity" / "machine balance"). This choice is what lets cache optimizations
show up as movement along the x-axis. The **ridge point** — where the diagonal bandwidth
roof meets the horizontal compute roof — is the minimum OI needed to reach peak, and its
position tells you how hard the machine is to program. **Ceilings** below the roof encode
missing optimizations (ILP/SIMD, FP balance; unit stride, memory affinity, software
prefetch), ordered bottom-to-top by increasing programmer effort; a kernel's OI selects
which *region* of ceilings applies and therefore which optimizations are worth trying.

### 7.2 Key quantitative results

| machine | peak GFlop/s | STREAM GB/s | ridge point |
|---|---|---|---|
| Opteron X2 2214 (2.2 GHz, dual socket) | 17.6 | 15 (measured peak) | **1.0 flops/byte** |
| Opteron X4 2356 (Barcelona) | 74 | 16.6 | **4.4 flops/byte** |
| Xeon e5345 (Clovertown) | 75 | 5.9 | **6.7 flops/byte** = 55 flops per 8-byte DP operand |
| UltraSPARC T2+ (Niagara 2, 128 threads) | 19 | 26.0 | low |
| IBM Cell QS20 (3.2 GHz, local stores) | 29 | 47.0 | low |

The X2→X4 comparison is the sharpest lesson: **same socket, same DRAM channels, 4× the
FP throughput → the ridge point moves right by 4.4×**, so a kernel below 1.0 flops/byte
gains *nothing* from the new chip.

Ceilings on Opteron X2: **8.8 GFlop/s** if the multiply/add mix is imbalanced,
**2.2 GFlop/s** if ILP/SIMD is also missing; bandwidth ceilings **11 GB/s** without
software prefetch, **4.8 GB/s** without memory affinity, **2.7 GB/s** with only unit
stride. Kernel OIs (Table 2): SpMV **0.17–0.25**; Stencil **0.33–0.50**; LBMHD
**0.70–1.07**; 3D FFT **1.09–1.64**.

### 7.3 Hardware/driver assumptions

- **Holds, strongly**: the model is architecture-agnostic and is exactly the formalism
  behind Orion's binary compute/memory tag and Nsight's roofline verdict.
- **Ridge points have moved hard right on modern GPUs.** A 4090 at ~82 TFLOP/s FP32 and
  ~1 TB/s has a ridge point around **80 flops/byte**; with FP16/BF16 tensor throughput it
  is in the **hundreds**. gfx1151 at ~50 TFLOP/s FP16 against ~256 GB/s LPDDR5X sits
  even further right. **Consequence: on 2024+ hardware almost everything is
  memory-bound**, which is why the co-run opportunity Orion found (opposite-character
  pairs) is *rarer* and *more valuable* than the 2019-era V100 data suggests.
- **The DRAM-traffic definition needs restating for GPUs**: the filter is L2 (and on
  RDNA3, the Infinity Cache / MALL), not a CPU cache hierarchy. For a fused APU, the
  "DRAM" is shared with the CPU, so the denominator includes contention cajeta does not
  control.
- **Ceilings translate**, but the list changes: for GPU kernels the ordered ceilings are
  roughly {occupancy / latency hiding, coalescing, LDS bank conflicts, vector width,
  register spilling, dual issue}. The 55-%-win-from-halving-accumulators result in the
  cajeta record is a spilling ceiling.

### 7.4 Adopt / adapt / cannot

- **Adopt directly**: OI as the *definition* of the arithmetic-character tag. It is not a
  heuristic label — it is a ratio the compiler can compute from the Group/Tile IR (bytes
  touched per buffer × element size, divided by mac/reduce op count) and the runtime can
  correct from measurement.
- **Adopt**: the ridge point as a **per-device constant the runtime must know**, so
  "compute-bound" means `OI > ridge` and "memory-bound" means `OI < ridge` on *this*
  device, not on a reference device. This directly addresses the recorded
  `cajeta-llama-geometry-is-literals` problem: nothing re-derives on new hardware because
  the device can't report its own constants.
- **Adapt**: the binary tag is too coarse near the ridge. A kernel with OI within a factor
  of ~2 of the ridge is genuinely balanced and will interfere with *both* classes; it
  should be `indeterminate`, not forced into a bucket. Orion's 60 %-utilization rule is a
  crude version of the same idea.
- **Cannot**: use flops/byte alone for kernels whose bottleneck is neither (launch-latency
  bound decode kernels, fixed-function raster/RT work, atomics-bound reductions). Those
  need a third and fourth tag.

### 7.5 Requirements

1. **When the runtime initializes a device, it records that device's peak arithmetic
   throughput and peak achievable memory bandwidth (measured, not spec) and derives the
   ridge point; no scheduling constant is a source literal tied to one GPU.** *(all)*
2. **When a kernel's operational intensity is computed, it is bytes of device-memory
   traffic (post-last-level-cache) per arithmetic operation, derived from the declared
   read/write buffer sets and the mac/reduce counts in the tile body.** *(all)*
3. **When a kernel's operational intensity is within a factor of 2 of the device ridge
   point, its character tag is `indeterminate`.** *(all)*
4. **When a kernel is measured to reach a fraction of the roofline bound below a
   configured threshold, the runtime reports which ceiling it is under (occupancy,
   coalescing, spilling, bank conflicts) rather than only reporting the shortfall.**
   *(simulation, ML)*
5. **When the same kernel is scheduled on two backends, its character tag is recomputed
   per device, because the ridge point differs.** *(all)*
6. **When a workload is bandwidth-bound on a unified-memory device, the scheduler
   accounts for host-side memory traffic in its bandwidth budget.** *(game, simulation —
   gfx1151-specific)*

## 8. Volkov — **Better Performance at Lower Occupancy** (GTC 2010, 75 slides)

### 8.1 Core mechanism

Little's Law, applied to a GPU, twice. **Needed parallelism = latency × throughput.**
That parallelism can be supplied three ways: by threads (TLP), by *independent
instructions within one thread* (ILP), or by *wider accesses per thread* (bit-level
parallelism — `float2`/`float4` loads). Therefore occupancy is one term in a product, not
a proxy for utilization. And because register bandwidth is the only bandwidth fast enough
to feed peak arithmetic, running *fewer, fatter* threads that hold more state in
registers is often strictly better — even though it lowers occupancy. Both effects are
achieved by the same transformation: **compute multiple outputs per thread.**

### 8.2 Key quantitative results

Arithmetic parallelism required (latency × cores/SM):

| GPU | ALU latency | cores/SM | ops/SM in flight |
|---|---|---|---|
| G80–GT200 | ≈24 cyc | 8 | ≈192 |
| GF100 | ≈18 cyc | 32 | ≈576 |
| GF104 | ≈18 cyc | 48 | ≈864 |

GTX 480 (GF100), one block, peak 89.6 GFlop/s per SM: **ILP=1 needs 576 threads/SM** for
100 % of peak; **ILP=2 needs 320**; **ILP=3 needs 256**; **ILP=4 needs 192**; past ILP=4 it
stops helping. At **12.5 % occupancy** with ILP=4 you still reach ~100 %. On G80,
~100 % of peak at **25 %** occupancy with no ILP, or **8 %** occupancy with ILP=3.

Memory: latency < 800 cycles × 177 GB/s ⇒ **~100 KB must be in flight** on a GTX 480.
At 4 B/thread that is **25,000 threads**; at 100 B/thread it is **1,000 threads**.
Measured `memcpy` as a fraction of the 177.4 GB/s pin bandwidth:

| bytes per thread | occupancy needed for ~peak |
|---|---|
| 1 float (4 B) | 85 % of peak only at **100 %** occupancy |
| 2 floats | ~86 % at **50 %** |
| 4 floats | 87 % at **~25 %** |
| 8 × float4 (128 B) | **87 % of pin bandwidth at 8 % occupancy** |
| 14 × float4 (224 B) | 84 % at **4 % occupancy** |

(`cudaMemcpy` itself achieves at best **71 %**.)

Bandwidth hierarchy on Fermi: `a*b+c` at 1.3 Tflop/s demands **8.1 TB/s** of operand
bandwidth; shared memory supplies only 4 B × 32 banks × 15 SMs × ½ × 1.4 GHz =
**1.3 TB/s**; global supplies **177 GB/s**. So **shared memory is ≥ 6× slower than
registers on Fermi (≥ 3× before)**. Bank-to-ALU ratio regressed across generations:
G80–GT200 16 banks : 8 thread processors (2:1); GF100 32:32 (1:1); GF104 32:48 (2:3).
Max registers per thread fell from ≈128 (G80–GT200) to ≈64 (Fermi).

SGEMM case study (GTX 480, SDK 3.1, 1024³), showing the whole thesis in one table:

| outputs/thread | Gflop/s | registers | occupancy | blocks/SM | B/flop from LDS |
|---|---|---|---|---|---|
| 1 (SDK baseline) | 242 | 21 | 67 % | 1 | 4.0 |
| 2 | 341 (1.4×) | 28 | 67 % | 2 | 3.0 |
| 4 | 427 (1.76×) | 41 | **50 %** | 3 | 2.5 |
| 8 | 485 (2×) | 63 | **33 %** | 4 | 2.25 |
| 36 (MAGMA BLAS) | **838** | — | **33 %** | 2 | **0.67** |

FFT-1024 case study: 2 outputs/thread 152 Gflop/s @ 100 % occupancy → 4 outputs 311 @
100 % → 8 outputs 357 @ 59 % → **16 outputs 402 Gflop/s @ 33 % occupancy**, with the
shared-memory shuffle count going 3 → 1 → 0.

Also stated plainly: **"threads don't stall on memory access — only on data dependency."**

### 8.3 Hardware/driver assumptions

- **The mechanism holds; the constants are 14 years stale.** Ada and RDNA3 have deeper
  pipelines, larger register files (RDNA3: 192 KB VGPR per SIMD in wave32 mode), and
  memory latencies well over 800 cycles at far higher bandwidth — so the **in-flight bytes
  requirement is much larger than 100 KB** on a 4090, and the "fatter threads" argument
  is *stronger*, not weaker.
- **The shared-memory-vs-register gap persists.** RDNA3 LDS is still bank-limited relative
  to VGPR bandwidth. The cajeta record already contains an independent confirmation of the
  same effect from the other side: halving accumulators to stop spilling won **55–70 %**
  on gfx1151, and only shader-stats inspection revealed it.
- **RDNA3 adds a wrinkle Volkov did not have**: dual-issue (VOPD) requires *paired
  independent* VALU ops, i.e. it makes ILP a *hard requirement* for peak, not an
  alternative to TLP. This is the GF104 situation from slide 14 ("on GF104 you *must* use
  ILP to get > 66 % of peak") reappearing.
- **Fails**: the ILP=4 saturation point and the 8 %/4 % occupancy figures are per-uarch.
  They must be re-measured, and the cajeta record's `gpu-kernel-read-shader-stats` note
  says how (RADV_DEBUG=shaderstats/asm), because wall-clock A/B tests are blind to it.

### 8.4 Adopt / adapt / cannot

- **Adopt directly, as design law for the `Group`/`Tile`/`mac`/`reduce` surface**: the
  authoring API must make "compute k outputs per lane" the *natural* expression, with k a
  tunable, because that one knob simultaneously raises ILP, raises bytes-per-lane, and
  lowers LDS traffic. If the surface only expresses one output per lane, cajeta forfeits
  the entire 2×–3.5× range in the SGEMM table.
- **Adopt**: occupancy is **not** a scheduling input. The scheduler's footprint model
  (from Orion) needs group-slot counts for *admission*, but the runtime must never
  optimize *for* occupancy, and the tooling must never report high occupancy as success.
- **Adopt**: the in-flight-bytes formulation. `bytes_in_flight = latency × bandwidth` is
  a per-device constant that tells the scheduler how much concurrent memory work the
  device can actually absorb — which is the missing term in Orion's memory-bound
  admission test.
- **Adapt**: the ILP knob interacts with the co-scheduling decision. A kernel tuned to
  ILP=4 and low occupancy leaves *group slots* free but leaves *register file* consumed.
  Two low-occupancy kernels can co-reside where two high-occupancy ones cannot — the
  admission test must be on registers/LDS, not on group count alone. Paella's Table 1
  (blocks, threads, registers, shared memory) is the right resource vector.
- **Cannot**: infer utilization from occupancy; assume more waves is safe; use wall-clock
  A/B to detect a spill-driven regression.

### 8.5 Requirements

1. **When a cooperative-tile kernel is authored, the number of outputs computed per lane
   is an explicit, tunable parameter of the Tile abstraction, defaulting to more than
   one.** *(ML, simulation, game)*
2. **When the runtime models a kernel's device footprint, it models the full resource
   vector — group slots, lanes, vector registers, scalar registers, LDS — not occupancy.**
   *(all)*
3. **When two kernels are considered for co-running, admission requires that the sum of
   their per-CU register and LDS demands fits, independently of whether group slots
   fit.** *(all)*
4. **When occupancy is reported by tooling, it is never presented as a performance target,
   and any report that cites occupancy also cites achieved fraction of the roofline
   bound.** *(all)*
5. **When a kernel spills to scratch, the build fails or warns loudly; a spilling kernel
   is never silently accepted as tuned.** *(all)*
6. **When the runtime computes how much memory-bound work a device can absorb
   concurrently, it uses measured `latency × bandwidth` bytes-in-flight for that device,
   not a constant.** *(all)*
7. **When the target is RDNA3, the tile body's inner loop exposes at least two
   independent VALU chains so dual issue is reachable.** *(ML, simulation)*

## 9. Ausavarungnirun et al. — **MASK: Improving Multi-Application Concurrency Support Within the GPU Memory System** (PACT 2018)

### 9.1 Core mechanism

MASK is the only paper in the corpus that instruments the interference channel *below*
the kernel: **address translation**. It adds three cooperating mechanisms to a GPU MMU
with a shared L2 TLB. **(1) TLB-Fill Tokens** — an epoch-based (100 K cycles) scheme that
limits how many warps *per shader core* may fill the shared L2 TLB; token count is
adjusted ±10 % each epoch based on the *direction* of the shared-TLB miss rate (starting
at 80 %), and warps without tokens are served from a **32-entry fully-associative bypass
cache**. (2) **TLB-Request-Aware L2 Bypass** — page-walk requests are tagged with their
page-table level (3 extra bits, values 0 or 7–6); levels whose L2 hit rate falls below the
non-TLB hit rate bypass the L2 entirely. (3) **Address-Space-Aware DRAM Scheduler** —
three request queues instead of one: **Golden** (all TLB-related requests, FIFO),
**Silver** (data requests of one selected application, rotated with a threshold
`thres_i = thres_max · (Concurrent_i · WrpStalled_i) / Σ_j(...)`), **Normal** (everyone
else); FR-FCFS within each queue.

### 9.2 Key quantitative results

Measured on **real hardware** (Figure 1): per-process context-switch overhead under
contention is **8–12 % on a Tesla K40** and **10–12 % on a GTX 1080**, growing with the
number of concurrent processes.

Simulated (GPGPU-Sim 3.2.2 / MAFIA, Maxwell-like: 30 cores, 64 exec units/core, 1020 MHz,
64-entry per-core L1 TLB, 512-entry 16-way shared L2 TLB, 2 MB L2, GDDR5 1674 MHz,
4-level page table, 64-thread walker, up to 64 concurrent walks):

- A **single TLB miss can stall over 30 warps**, and over **50 outstanding TLB misses**
  can be contending at once. This is the mechanism: TLB misses destroy the *supply of
  schedulable warps*, which is the GPU's only latency-hiding tool.
- 2 MB large pages with demand paging cost **93 % average slowdown**.
- Page-walk requests are only **13.8 % of utilized DRAM bandwidth (2.4 % of peak)** but
  suffer **higher latency than data requests**, because FR-FCFS favours the GPGPU data
  stream's excellent row-buffer locality.
- MASK vs a state-of-the-art GPU MMU: **+45.2 % system throughput, +43.4 % IPC
  throughput, −22.4 % unfairness**, landing **within 23 %** of a perfect always-hit TLB.
- Per component: TLB-Fill Tokens raise the shared-TLB hit rate **49.3 % → 73.9 %**
  (bypass-cache hit rate 66.7 %); L2 Bypass raises the L2 hit rate for TLB requests
  **70.7 % → 98.3 %** for **+17.6 %** performance; the DRAM scheduler averages only
  **+0.83 %** but reaches **+30.2 %** on the worst-hurt pair and cuts TLB request latency
  by up to 10.6 %.
- Scaling: **+35.5 %** over GPU-MMU at 1 app, **+45.2 %** at 2, **+47.3 %** at 3 — the
  benefit *grows* with concurrency.
- Portability: on Fermi (GTX 480) **+29.1 %**, within 22 % of ideal, TLB hit rate +64.7 %.
  On an **integrated GPU**, shared-L2-TLB contention is "significantly more severe" and
  causes a significant performance drop; MASK + translation cache reaches **72.6 %** of
  ideal versus **52.1 %** for the translation cache alone.
- Hardware cost: **436 bytes per core**, +6 % DRAM request-queue storage, **< 0.1 % area,
  0.01 % power**.

### 9.3 Hardware/driver assumptions

- **Everything MASK builds is hardware.** None of it is implementable in a language
  runtime. Its value to cajeta is entirely **diagnostic and constraint-setting**.
- **Its central premise — multiple address spaces — does not apply to a single-process
  cajeta runtime.** All cajeta kernels share one address space, so the cross-address-space
  TLB thrashing MASK targets does not arise. This is a *large* free win: MASK's whole
  45.2 % is a tax cajeta simply does not pay.
- **What does transfer**: the **8–12 % measured context-switch tax per process** on real
  K40/GTX 1080 hardware is the price of *any* multi-process sharing scheme (MPS, MIG,
  separate processes). It is a direct argument for cajeta's single-process design over the
  Orion/PipeSwitch/Salus multi-process architectures.
- **What transfers and hurts**: the finding that the integrated-GPU case is *worse*, not
  better, because the shared L2 TLB and memory system are more contended. gfx1151 is an
  APU. The runtime must expect TLB/MALL pressure from CPU-side work it does not control.
- **What transfers as a warning**: co-running two kernels with different, large working
  sets thrashes the shared L2 and TLB even when their compute characters are
  complementary. Orion explicitly leaves cache interference out of scope. That is the
  known unmodelled channel, and MASK quantifies its size.

### 9.4 Adopt / adapt / cannot

- **Adopt as a *design justification***: single-process, single address space eliminates
  the dominant interference channel this paper is about. Record it as a rationale, not as
  a mechanism.
- **Adopt the metric**: MASK measures **unfairness = max_i (IPC_alone,i / IPC_shared,i)**
  and **weighted speedup = Σ IPC_shared/IPC_alone**. These are exactly the right two
  numbers for a co-scheduling acceptance test, far better than aggregate throughput.
- **Adapt**: the "bypass the shared cache for a request class that pollutes it" idea has a
  software analogue — non-temporal / streaming loads and stores for a best-effort kernel's
  bulk traffic so it does not evict the latency kernel's working set. Both AMDGPU
  (`glc`/`slc` / `nt`) and NVPTX (`ld.global.nc`, `cp.async` bypass) expose this.
- **Adapt**: the epoch-based feedback loop — measure a contention proxy over a fixed epoch,
  and move an admission threshold by a fixed percentage in the direction that improved it.
  This is a good shape for auto-tuning `SM_THRESHOLD` / `DUR_THRESHOLD` at runtime rather
  than hard-coding Orion's constants.
- **Cannot**: touch TLBs, page-walk caching, DRAM scheduling, or memory-request priority.

### 9.5 Requirements

1. **When co-scheduling is evaluated, the acceptance metric is per-kernel slowdown
   relative to its solo run (unfairness = max over kernels) and weighted speedup, not
   aggregate device throughput.** *(all)*
2. **When a best-effort kernel's declared read set exceeds a configured fraction of the
   device's last-level cache, it is not co-run with a latency-class kernel.** *(game, ML —
   this is the cache channel Orion leaves unmodelled)*
3. **When a best-effort kernel performs bulk streaming traffic, its loads and stores are
   lowered as non-temporal so they do not evict the latency kernel's working set.**
   *(game, ML)*
4. **When admission thresholds are tuned at runtime, they are adjusted by a bounded step
   at fixed epoch boundaries in the direction that improved the contention proxy, never
   per-launch.** *(all)*
5. **When the device is an integrated GPU sharing memory with the host, the bandwidth
   budget the scheduler works against is the measured achievable bandwidth under
   concurrent host activity, not the idle-device figure.** *(game, simulation)*
6. **When the runtime documents its single-process design, it records that this
   eliminates the cross-address-space TLB interference channel and the measured 8–12 %
   per-process context-switch tax.** *(all)*

## 10. Zou, Xu, Ni, Chen, Ma, Li, Gill, Zhang, Jin — **A Survey of Real-time Scheduling on Accelerator-based Heterogeneous Architecture for Time Critical Applications** (arXiv 2505.11970, May 2025)

### 10.1 Core mechanism

Not a system — a classification of ten years of real-time accelerator scheduling. Its
organizing observation is that heterogeneous platforms have **three tiers with different
preemption properties**: CPU cores are **preemptive**; **memory copies are
non-preemptive**; and accelerator PEs are one of **{non-preemptive & non-partitioning,
preemptive, partitioning}**. It then splits the literature by deadline class (soft vs
hard), by accelerator count (single vs multi), and by objective (timing-only vs
multi-objective: energy, thermal). Because most accelerators forgo preemption circuitry to
maximize throughput per unit area, most "preemption" in practice is a **software**
construct (Effisha preempts at arbitrary thread-block boundaries with no hardware
changes), and most **isolation** in practice is **partitioning** (MIG, MPS, FPGA DPR).

### 10.3 Key quantitative results

The survey is qualitative, but carries these:
- **sBEET** cuts deadline misses and energy by up to **13 % and 21 %** on Jetson Xavier
  AGX; the accompanying theorem is that a job set's schedule *with* spatial multitasking
  can never be more energy-efficient than the schedule without it, if the jobs are
  linear-speedup.
- **DREAM** reduces its author-defined metric by **32.2 %–50 %** for multi-accelerator
  RTMM workloads.
- **TherMa-MiCs** improves QoS for low-criticality tasks by an average of **44 %** while
  meeting temperature and timing constraints.
- Copy-engine counts, which bound how many memory copies can overlap: **GTX TITAN Black
  and Jetson TX2 have 1 copy engine; 1080 Ti, TITAN X and Xavier have 2.**
- Utilization is defined **two incompatible ways** in the literature: CPU-centric
  `U = ΣΣC_i^j / N_CPU` (accelerators are subordinate) versus
  `U = ΣΣ(C_i^j + A_i^j) / (N_CPU + N_accel)` (co-equal). Papers using the same task model
  report non-comparable numbers.

### 10.4 Hardware/driver assumptions

- **The survey's own conclusion is that no universal scheduler exists** and that response
  time analysis becomes pessimistic fast as the number of PE *types* grows. Commercial
  platforms almost always have CPU + exactly one accelerator type; cajeta's
  AMDGPU/NVPTX/Vulkan/CPU spread is the *harder* case the survey says is under-studied.
- **Explicitly flagged as newly non-negligible (§VII-B)**: memory-bus and data-copy
  overheads. "Data copy times across processor memories via the memory bus should no
  longer be treated as negligible," and GEMM-dominated AI workloads "often experience
  substantial delays due to data transfers." Zero-copy and unified memory change the model
  rather than removing it.
- **Holds for cajeta**: memory copies are non-preemptive on every target. So a
  frame-budget scheduler must model transfers as blocking intervals, not as background.
- **Fails for consumer targets**: MIG is datacenter-only (A100/H100). Neither gfx1151 nor
  the 4090 has hardware partitioning. Everything cajeta does must be in the
  software-spatial or temporal-division column.
- **Relevant and current**: Llumnix's framing of LLM serving as an OS problem — isolation,
  priorities, and "context switching" implemented as **inference-request migration** — is
  the closest published analogue to what cajeta wants for prefill/decode co-running.
  BOXR's **contention-preventive scheduling** for XR (co-optimizing motion-to-display
  latency against rendering) and Heimdall's **pseudo-preemptive GPU coordinator** for
  multi-DNN + rendering on a mobile GPU are the closest analogues for the game target.

### 10.5 Requirements

1. **When a work item spans CPU segments and device segments, the runtime models it as a
   self-suspending segmented task — CPU compute, device suspension, CPU compute — and does
   not treat the device segment as free CPU time.** *(all)*
2. **When a host↔device transfer is scheduled, it is modelled as a non-preemptive blocking
   interval charged against the frame or step budget.** *(game, simulation)*
3. **When the number of concurrently overlapping transfers exceeds the device's copy-engine
   count, the scheduler serializes them rather than assuming overlap.** *(game, ML)*
4. **When the schedule policy is `frame-budget`, no admitted device work may cross the
   frame boundary; the scheduler enforces a forbidden zone at the end of each budget in
   which only work that provably completes is admitted.** *(game)*
5. **When a pipeline is expressed as a chain where stage `i+1` reads what stage `i` wrote,
   the scheduler treats the buffer handoff as a scheduling constraint, not just a
   dependency.** *(game, simulation, ML)*
6. **When utilization is reported, the definition used (accelerator-only, CPU-centric, or
   combined) is stated with the number.** *(all)*
7. **When a kernel supports degraded output (fewer iterations, lower resolution, partial
   reduction), the seam can express it, and the scheduler may select the degraded variant
   to meet a deadline rather than dropping the work.** *(game — RTScale / PAP* /
   foveated-rendering pattern)*

## 11. Cross-paper synthesis

### 11.1 Interference channels the corpus agrees dominate

Ordered by how much evidence there is, and by whether cajeta can act on them:

1. **Memory bandwidth, not compute.** Orion's decisive experiment is that two kernels each
   using only 40 % of SMs still fail to co-run (BN2d+BN2d, 1.08×) while a
   compute/memory pair wins 1.41×. Roofline explains why, and says the situation is worse
   now: ridge points have moved from ~1 flop/byte (Opteron X2) to ~80+ flops/byte (4090),
   so *almost every real kernel is on the bandwidth roof*. Volkov gives the quantitative
   handle: a device can only absorb `latency × bandwidth` bytes in flight (~100 KB on a
   GTX 480; far more now), and that budget is shared. **Actionable, and it is the primary
   scheduling signal.**
2. **Head-of-line blocking in finite FIFO hardware queues.** Paella's 18 %-of-a-GTX-1660
   result and REEF's 20–40 µs inter-stream dispatch delay are the same phenomenon from two
   sides. **Actionable: cap in-flight depth and choose what goes in.**
3. **Shared L2 / last-level cache and TLB.** MASK measures it at up to 45.2 % of achievable
   throughput in the multi-address-space case; REEF names it as the *residual* interference
   its CU partitioning cannot remove; Orion explicitly excludes it as future work. In a
   single address space the TLB half of this goes away, but the **cache-capacity half does
   not**. **Partly actionable: working-set-size admission plus non-temporal hints.**
4. **Host↔device transfer.** Clockwork: LOAD is 8.33 ms against a 2.61 ms INFER for
   ResNet50 — the transfer is *3× the compute*. PipeSwitch: 81–91 ms for ResNet152.
   Orion: the GPU cannot schedule kernels *at all* during a memcpy. The 2025 survey calls
   this newly non-negligible. **Actionable, and ~free on gfx1151's unified memory.**
5. **Process/context-switch tax.** MASK measures 8–12 % per process on real K40 and GTX
   1080 hardware; PipeSwitch measures 5.5–7.3 s of process/CUDA-context init.
   **Eliminated by construction in a single-process runtime — this is cajeta's structural
   advantage and should be stated as such.**
6. **The host scheduler itself.** Paella: injected scheduling delay degrades throughput
   from the low-µs region; Triton's non-CUDA overhead is up to 66 % of request latency.
   Salus rejected kernel-granularity scheduling partly on this ground. **Actionable, as a
   hard budget.**

### 11.3 Classification signals a scheduler needs per kernel

Merging all ten papers, the submit seam must carry (or the runtime must derive):

1. **Arithmetic character** — operational intensity relative to *this device's* ridge
   point, three-valued {compute, memory, indeterminate}. *(Roofline defines it; Orion
   proves it is the decisive signal; §7.5 R3 handles the near-ridge case.)*
2. **Resource footprint vector** — groups, lanes/group, vector registers, scalar
   registers, LDS/shared memory. Not occupancy. *(Paella Table 1; Volkov's whole
   argument; Orion's `sm_needed`.)*
3. **Expected duration + a predictability flag** — a rolling high-percentile per (kernel,
   geometry, backend), plus a boolean saying whether variance is small enough to schedule
   against. *(Clockwork's profiles; REEF's Rule 1 needs the duration; Orion's
   `DUR_THRESHOLD` needs it.)*
4. **Deadline window `(earliest, latest)`** — and the rule that a missed window is an
   error, not a retry. *(Clockwork.)*
5. **Read set and write set, complete at submit time** — which yields, for free:
   working-set size (MASK's cache channel), footprint for the Salus safety condition, and
   the handoff constraints of a task chain (survey).
6. **Restartability** — derived from read/write set disjointness. Only restartable kernels
   may be cancelled. *(REEF's idempotence assumption, made checkable.)*
7. **Priority class / schedule policy** — {latency, throughput, frame-budget} plus a
   protected/best-effort bit. *(Every system in the corpus.)*
8. **Degradation options**, where they exist — a cheaper variant the scheduler may
   substitute to hit a deadline. *(Survey: PAP*, RTScale, foveated rendering.)*

### 11.4 Where the papers contradict each other

- **Serialize versus co-run.** **Clockwork** measures that concurrency buys +25 %
  throughput at 100× tail latency and concludes: run **one** kernel at a time.
  **Orion, REEF and Paella** all conclude the opposite — co-run aggressively, and get
  1.3×–7.7×. The contradiction is not about facts; it is about **whether the protected
  kernel saturates the device**. Clockwork's ResNet50 at batch 16 on a V100 does; Orion's
  Table 1 shows MobileNetV2 inference at 6 % SM utilization does not. **Resolution for
  cajeta**: the decision is per-kernel, not global — serialize when the protected kernel's
  footprint already fills the device, co-run when it does not. The footprint vector is
  what decides, which is another reason it must be in the seam.
- **Scheduling granularity.** **Salus built a kernel-granularity scheduler and rejected
  it** (central bottleneck, breaks the framework's own kernel batching and pipelining,
  progressive-allocation deadlock) in favour of iteration granularity. **Orion, REEF and
  Paella all schedule at kernel granularity and it is the point.** Resolution: Salus's
  objections are all consequences of scheduling *underneath* an uncooperative framework.
  A runtime that owns the seam and gets complete buffer sets at submit time has neither
  the deadlock nor the broken-batching problem. But Salus's *cost* objection stands and
  becomes Paella's < 10 µs budget.
- **Preemption versus padding.** **REEF** argues you must be able to kill running work
  (35 µs) and pad the survivor's leftover CUs. **Orion** argues preemption is unavailable
  on the platforms that matter and you should instead *not submit* work you will regret,
  and beats REEF on the protected job's tail latency by 2.3–3× while getting the
  best-effort job much further than REEF does (REEF "barely executes the best-effort
  job"). Resolution: they optimize different things — REEF minimizes arrival-to-start,
  Orion minimizes *interference while running*. cajeta needs both, and Orion's own results
  show admission control is the cheaper half.
- **Occupancy.** **Volkov** says maximize work per lane and let occupancy fall to 8 %.
  **Orion/Paella/REEF** all use occupancy-derived footprint as an admission signal, and
  REEF's Rule 2 explicitly requires the best-effort kernel's *CU occupancy to be at least
  as high as* the real-time kernel's. These are compatible but easy to confuse: occupancy
  is a **capacity accounting unit** for the scheduler and a **non-goal** for the kernel
  author. Anything in cajeta that reports occupancy must say which of the two it means.
- **Where the model lives.** **Clockwork** consolidates every choice centrally and treats
  any deviation as an error. **Paella** distributes ground truth (the device tells the
  host where every block landed) and schedules reactively. Clockwork's approach needs
  prediction accuracy; Paella's needs a fast feedback path. cajeta can have both —
  Clockwork's windows for admission, Paella's notifications for correction — and the
  combination is stronger than either, because Clockwork's measured 4× error compounding
  is exactly what a feedback signal fixes.
- **Fairness.** Paella needs a deficit counter to stop SRPT starving long jobs; REEF's
  policy explicitly starves best-effort work to protect real-time; Orion sits between with
  a tunable throttle. There is no agreement, and the survey confirms there is no universal
  scheduler. This argues for cajeta's three named policies rather than one.

### 11.5 What is stale on 2024+ hardware

- **Volkov's constants (2010).** ILP=4 saturation, 192/576/864 ops per SM, ~100 KB in
  flight, ≈64 registers per thread, 6× register:LDS bandwidth gap. All of these must be
  re-measured on gfx1151 and AD102. The *mechanism* (Little's Law; more work per lane;
  registers are the only fast bandwidth) is more relevant than in 2010, not less — and
  RDNA3's dual issue makes ILP a **requirement** for peak rather than an alternative to
  occupancy, which is the GF104 situation Volkov flagged as unusual.
- **Roofline's ridge points (2009).** 1.0–6.7 flops/byte then; **~80+ flops/byte** on a
  4090 for FP32 and into the hundreds for tensor formats. The consequence is a change of
  regime, not a change of model: in 2009 the interesting kernels straddled the ridge; in
  2025 nearly everything is memory-bound, so opposite-character pairs are scarcer and each
  one is worth more. Also: "DRAM traffic filtered by the cache hierarchy" now means
  filtered by a 96 MB L2 (4090) or a MALL/Infinity Cache (RDNA3) — a much bigger filter
  than a 2009 L2.
- **MPS overhead numbers.** PipeSwitch's 193–338 ms and Salus's "MPS crashes TensorFlow"
  are CUDA 8–10.1 era. MPS has improved. The structural criticism — MPS gives you
  concurrency but no *policy* — is unchanged, and is exactly why every paper in this corpus
  had to build something on top of it.
- **"GPUs lack preemption."** Pascal added instruction-level preemption in 2016; REEF and
  Paella both note it exists but that there is no public software-controllable interface
  and the swapping overheads are prohibitive in practice. Effectively still true for a
  userspace runtime in 2025, so the papers' conclusions stand — but the reason is
  *interface availability*, not silicon, and it could change.
- **Datacenter-only mechanisms.** MIG (A100/H100), MPS's process model, and MASK's entire
  hardware proposal do not exist on gfx1151 or a 4090. Every partitioning idea cajeta can
  use is in the software-spatial or temporal-division column of §10.2.
- **Memory-capacity framing.** Salus's whole GPU-lane design is dimensioned around a 16 GB
  P100 where resnet152 at 13.8 GB nearly fills the device. On gfx1151 the capacity picture
  is completely different (large, unified, shared with the host); the *safety condition*
  survives, the constants and the urgency do not.
- **PCIe as the transfer bottleneck.** PipeSwitch (PCIe 3.0 ×8/×16) and Clockwork's 8.33 ms
  LOAD are both discrete-GPU facts. On gfx1151 they largely vanish; on a 4090 over PCIe 4/5
  they shrink but persist. Any transfer-pipelining machinery cajeta builds must be
  conditional on the backend reporting non-unified memory.
- **Not stale, and worth restating**: Clockwork's determinism measurement (99.99th
  percentile within 0.03 % of median) and REEF's independent confirmation (few-µs variance
  on a completely different vendor's hardware) are the foundation everything else rests on,
  and there is no reason to believe modern GPUs are less deterministic for branch-free
  fixed-geometry kernels. cajeta's cooperative-tile surface produces exactly that shape of
  kernel, so cajeta gets to build on the strongest result in the corpus.

# Reading B

# GPU co-scheduling papers — batch B extraction for the cajeta `xpu` kernel scheduler

Scope note that applies to every section below. Six of the nine papers
(Nexus, Clipper, AlpaServe, AntMan, TGS, Gandiva) are **cluster**
schedulers; two (iGniter, MISO) are cluster provisioners built on a
**per-device** interference model; one (gpu-lets / Choi 2022) is a
single-node multi-GPU scheduler. For each I separate the per-device
mechanism (which can transfer to a single process) from the
cluster-only machinery (placement across nodes, migration, bin
packing over devices, autoscaling). Cajeta's target is one process,
one or two devices, no MPS, no MIG, with `hipExtStreamCreateWithCUMask`
on HIP and CUDA green contexts on NVIDIA as the only spatial knobs.

Hardware shorthand used throughout:
- **gfx1151** = RDNA3.5 Strix Halo APU. Unified LPDDR5X (CPU and GPU
  share physical memory), ~32 MB MALL/Infinity Cache, package power
  budget shared with the CPU, no MIG-equivalent, CU masking available
  per-stream via `hipExtStreamCreateWithCUMask` (WGP granularity).
- **RTX 4090** = AD102, CC 8.9. 72 MB L2, 450 W board power, no MIG,
  MPS available but multi-process only, **CUDA green contexts (12.4+)
  give in-process SM partitioning** — this is the single most
  load-bearing hardware fact for reusing this literature.

## 1. Xu et al. 2023 — iGniter (TPDS)

### 1.1 Core mechanism

iGniter builds a **closed-form analytical latency model** for a DNN
inference workload co-located with others on one GPU under MPS
`set_active_thread_percentage`, then uses that model inside a greedy
placement + resource-allocation loop. What is *measured*: per-workload,
offline and once, the input/output byte size per unit batch, the
**number of kernels** `n_k`, the solo per-kernel scheduling delay
`k_sch`, the solo GPU active time `k_act` as a function of (batch,
resource), solo power `p`, and solo **L2 cache utilization** `c` (from
Nsight Compute). What is *decided*: per workload, a batch size `b` and
an SM percentage `r` in 2.5% units (~2 SMs on V100), and which device
hosts it. The interference is decomposed into exactly three additive
channels — **GPU scheduler queueing** (grows with the *count* of
co-runners and with `n_k`), **L2 cache contention** (grows with the sum
of the *other* workloads' solo L2 utilizations), and **power-cap-driven
frequency droop** (grows with the sum of solo power draws). Granularity
is per-workload-per-device over a provisioning epoch, not per-kernel;
the model's inputs, however, are per-kernel counts and per-kernel solo
times.

### 1.2 Formulas, reproduced exactly

Notation: workload `i ∈ I`, GPU `j ∈ J`. `r^{ij} ∈ [0, r_max]` is the
allocated SM fraction (`r_max = 1`). `b^i` is batch size.

**End-to-end latency and throughput**

    t_inf^{ij} = t_load^i + t_gpu^{ij} + t_feedback^i                      (1)

    h^{ij} = b^i / (t_gpu^{ij} + t_feedback^i)                             (2)

**Transfer phases** (`d_load^i`, `d_feedback^i` are byte sizes at
`b^i = 1`; `B_pcie` is measured host→device bandwidth)

    t_load^i     = d_load^i · b^i / B_pcie
    t_feedback^i = d_feedback^i · b^i / B_pcie                             (3)

**GPU execution phase, scaled by the frequency droop**

    t_gpu^{ij} = (t_sch^{ij} + t_act^{ij}) / (f^j / F)                     (4)

**Scheduling-delay term — linear in kernel count**

    t_sch^{ij} = (k_sch^i + Δ_sch^j) · n_k^i                               (5)

           ⎧ 0,                                    if Σ_{i∈I} v^{ij} ≤ 1
    Δ_sch^j = ⎨                                                             (6)
           ⎩ α_sch · Σ_{i∈I} v^{ij} + β_sch,       otherwise

           ⎧ 1   if workload i runs on GPU j  (r^{ij} > 0)
    v^{ij} = ⎨                                                              (7)
           ⎩ 0   otherwise                    (r^{ij} = 0)

**L2-contention term — the co-runners' solo L2 utilizations, summed**

    t_act^{ij} = k_act^i · ( 1 + α_cache^i · Σ_{i'∈I\i} ( c^{i'} · v^{i'j} ) )   (8)

**Power-cap frequency droop** (`P` = board power cap, `F` = max clock;
`α_f` is negative)

           ⎧ F,                                    if p_demand^j ≤ P
      f^j = ⎨                                                               (9)
           ⎩ F + α_f · ( p_demand^j − P ),         if p_demand^j > P

    p_demand^j = p_idle + Σ_{i∈I} ( p^i · v^{ij} )                        (10)

**Solo active time as a function of batch and allocated resource**
(quadratic in batch, inverse in resource)

    k_act^i = ( k_1^i·(b^i)² + k_2^i·b^i + k_3^i ) / ( r^{ij} + k_4^i ) + k_5^i  (11)

**Solo power and solo L2 utilization are linear in "GPU processing
ability" `b^i / k_act^i`**

    p^i = α_power^i      · b^i / k_act^i + β_power^i
    c^i = α_cacheutil^i  · b^i / k_act^i + β_cacheutil^i

**Closed-form batch size and lower-bound resource** (Theorem 1)

    b_appr^i = ⌊ T_slo^i · R^i · B_pcie / ( 2 · ( B_pcie + R^i · d_load^i ) ) ⌋   (17)

    r_lower^i = ⌈ γ^i / ( δ^i · r_unit ) − k_4^i / r_unit ⌉ · r_unit             (18)

    where  γ^i = k_1^i·(b_appr^i)² + k_2^i·b_appr^i + k_3^i
           δ^i = T_slo^i/2 − (d_load^i + d_feedback^i)·b_appr^i / B_pcie
                           − k_5^i − k_sch^i · n_k^i

Optimization: minimize `C = Σ_j u^j` s.t. `Σ_j h^{ij}·v^{ij} ≥ R^i`
(13), `Σ_j t_inf^{ij}·v^{ij} ≤ T_slo^i/2` (14), `Σ_i r^{ij} ≤ r_max`
(15), `Σ_j v^{ij} = 1` (16). The **half-SLO rule in (14)** — batch
execution latency may not exceed half the SLO — is inherited from Nexus
and is the reason batching and residency interact.

### 1.3 Required per-kernel / per-workload inputs

**8 workload-specific**: `d_load`, `d_feedback`, `n_k`, `k_sch`,
`k_act`, `p`, `c`, `α_cache`.
**7 hardware-specific**: `P`, `F`, `p_idle`, `B_pcie`, `α_f`, `α_sch`,
`β_sch`.
`d_load`, `d_feedback`, `n_k`, `k_sch` come from **one** Nsight Systems
trace. `α_f`, `α_sch`, `β_sch`, `α_cache` come from launching 2–5
workloads concurrently. `k_act`, `p`, `c` come from **11 configurations**
of (resource, batch) per workload, fit by least squares — vs. 40 × 32 =
1280 for exhaustive.

### 1.4 Quantitative results (V100 / p3.2xlarge, some T4 / g4dn.xlarge)

- Measured interference on V100 with 5 co-located workloads at 20% each:
  latency **+0.83% to +34.98%**; co-runner batch size 1→32 alone moves a
  victim's latency **+6.36% to +13.93%**.
- Scheduling delay rises roughly **linearly in co-runner count 2→5**;
  ResNet-50 rises faster than AlexNet because `n_k` is larger.
- L2 hit ratio drops 83%→~72% as co-runners go 1→5; active time is
  inversely related.
- Power: AlexNet 108→156 W, VGG-19 139→179 W as batch 1→32; clock
  1530→1440 MHz for VGG-19 under contention, 1530→1515 MHz in the
  4-workload example.
- Measured V100 coefficients: `P = 300 W`, `F = 1530 MHz`,
  `p_idle = 53.5 W`, `B_pcie = 10 GB/s`, **`α_f = −1.025 MHz/W`**,
  **`α_sch = 0.00475`**, **`β_sch = −0.00902`**, `r_unit = 2.5%`.
- Prediction error: **0.04–7.61%** across resource sweeps; **1.10–9.29%**
  across batch sweeps; **1.53–5.02%** with 4 co-located workloads (where
  gpu-lets' 2-workload regression cannot predict at all). Average
  ResNet-50 error 3.82% (iGniter) vs 4.15% (gpu-lets).
- Cost: 6 GPUs and **0 SLO violations** vs gpu-lets 8 GPUs / 3
  violations, GSLICE 6 GPUs / 3 violations, FFD 5 GPUs / 10 violations;
  **25% hourly cost saving** vs gpu-lets.
- Overhead: profiling **229–247 s per model**, one-time. Algorithm
  **3.64 ms / 53 MB** at 12 workloads; **4.61 s / <55 MB** at 1000.

### 1.5 Hardware assumptions — what holds, what fails

| Assumption | 4090 / gfx1151, single process |
| --- | --- |
| MPS `active_thread_percentage` partitions SMs at 2.5% granularity | **Fails as written** (MPS is cross-process, NVIDIA-only). **Substitutable**: CUDA green contexts partition SMs in-process on Ada+; HIP CU masks partition CUs per stream. Granularity is coarser — green contexts round to SM-partition units (typically 8 SMs on Ada, i.e. ~6%); HIP masks are per-WGP. |
| Each workload is a separate process with its own kernel stream | Fails; in-process the "workloads" are streams, and Eq (6)'s co-runner count is the number of **concurrently resident streams**, which cajeta knows exactly and does not have to infer. |
| L2 is shared and not partitionable | **Holds and is worse.** 4090 has 72 MB L2, gfx1151 ~32 MB MALL. Neither can be partitioned. Eq (8) transfers directly. |
| Board power cap causes clock droop above `P` | **Holds and is far more severe.** gfx1151 shares a package power budget with the CPU, so `p_idle` is not constant and `p_demand` must include CPU draw. 4090 at 450 W throttles hard on dense-FP32 + tensor mixes. `α_f` must be measured per part. |
| PCIe transfer is a separate serialized phase | **Fails on gfx1151** — unified memory, `t_load`/`t_feedback` collapse to near zero and Eq (3), (17) degenerate. Holds on 4090 (dGPU over PCIe). This bifurcates the model. |
| Frequency and power readable at runtime | Holds via `rocm-smi` / NVML, but at ~10–100 ms latency — too slow for per-kernel decisions, fine for an epoch-scale controller. |
| Kernel count `n_k` is a fixed per-workload constant | **Holds better than in the paper.** Cajeta's submit seam sees every launch; `n_k` is exact, not profiled. |

### 1.6 Adopt / adapt / cannot

**Adopt directly**
- The **three-channel additive decomposition** (scheduler queueing, L2,
  power/frequency). It is the only model in this batch that scales past
  two co-runners with a lightweight profile, and each channel maps to a
  measurable in-process quantity.
- Eq (8) verbatim, with `c^i` replaced by a **statically estimated L2
  footprint** from the read/write buffer set the submit seam already
  carries — this is a strict improvement, since cajeta knows the working
  set size that iGniter has to profile with Nsight Compute.
- Eq (9)/(10) verbatim for the power channel; substitute measured
  per-kernel energy for `p^i`.
- The "**resource that just meets the target, not the resource that
  maximizes throughput**" principle (§5.3): allocating for peak
  throughput cost gpu-lets 2 extra GPUs and 3 SLO violations.

**Adapt**
- Eq (5)+(6): `Σ v^{ij}` becomes concurrent resident kernels, and
  `α_sch`, `β_sch` must be re-fit per backend — HIP's hardware queue
  arbitration and NVIDIA's are different mechanisms. On a frame-budget
  policy the scheduling delay term is the dominant one for many small
  kernels (game workloads), so re-fit it against a many-small-kernel
  microbenchmark, not against DNN inference.
- Eq (11): reparameterize `b^i` as "work per launch" (grid size ×
  per-item cost) rather than DNN batch. The quadratic-in-batch /
  inverse-in-resource shape is a fit, not a law; verify it holds for a
  cooperative-tile `mac`/`reduce` kernel before trusting it.
- Eq (17): only applies where a batching/latency tradeoff exists —
  ML serving, not game frames.

**Cannot / cluster-only**
- Algorithm 1's greedy device placement, `r_inter^{min}` minimization,
  ANYFIT bin packing, heterogeneous-instance selection, shadow-process
  failover, monetary-cost objective — all cluster-only.
- The 2.5%-granularity search space. In-process the granularity is
  8 SMs (green ctx) or 1 WGP (HIP), so the `r_unit` loop in Algorithm 2
  must be re-derived, and `r_lower` rounded up to a legal partition.

### 1.7 Testable requirements

1. **[all]** When two or more kernels are concurrently resident on one
   device, the scheduler shall estimate each kernel's slowdown as
   `k_act · (1 + α_cache · Σ_{others} c)` where `c` is the co-runner's
   L2 working-set fraction derived from its declared read/write buffer
   set, and the estimate shall be within 15% of measured for a 4-kernel
   mix.
2. **[all]** When the sum of concurrently resident kernels' measured
   power draw exceeds the device power cap `P`, the scheduler shall
   apply a clock-droop correction `f = F + α_f·(p_demand − P)` with
   `α_f` calibrated per device at build or first run, and shall not
   admit a further kernel whose admission drives predicted `f` below a
   configured floor.
3. **[game]** When a kernel is tagged frame-budget and its launch count
   `n_k` in the frame exceeds a threshold, the scheduler shall charge it
   a per-launch scheduling delay `(k_sch + α_sch·N_resident + β_sch)·n_k`
   and shall reject co-residency that pushes the frame past budget, even
   when both kernels' arithmetic-character tags are complementary.
4. **[ML]** When a memory-bound and a compute-bound kernel are candidates
   for co-residency, the scheduler shall admit the pair only if the
   predicted combined latency is below each kernel's declared deadline,
   using the additive three-channel model — not on the arithmetic tag
   alone.
5. **[ML]** When profiling a kernel for the interference model, the
   runtime shall require no more than 11 (geometry, resource)
   configurations and no more than 5 minutes wall clock per kernel.
6. **[all]** When the device is an APU with host-unified memory, the
   scheduler shall set the transfer terms `t_load`, `t_feedback` to zero
   rather than deriving them from a PCIe bandwidth constant.
7. **[simulation]** When a long-running kernel is admitted alongside a
   latency-sensitive one, the scheduler shall allocate the
   latency-sensitive kernel the smallest legal CU/SM partition that
   meets its deadline under the interference model, not the partition
   that maximizes its throughput.

## 2. Li et al. 2022 — MISO (SoCC)

### 2.1 Core mechanism

MISO chooses an **A100 MIG partition** for a mix of up to 7 co-located
training jobs, without paying the cost of exploring MIG configurations.
The insight: run the job mix briefly in **MPS** (cheap, no GPU reset, no
checkpoint) at three SM percentages — **100%, 50%, 14%** — for **10 s
each**, measure each job's progress rate (mini-batches/s), and feed the
resulting 3×7 matrix (normalized per column to (0,1]) into a small
**U-Net convolutional autoencoder** that predicts a 3×7 matrix of
speedups on the **7g, 4g, 3g** MIG slices. Speedups on 2g/1g are then
predicted by linear regression from those three (R² = 0.96). A trivial
optimizer then enumerates the ≤18 legal A100 MIG partitions and picks
`argmax Σ_i f_i(x_i)` subject to `x⃗ ∈ P_mig` and `‖x⃗‖₀ = m` (no
bubbles, no unscheduled jobs). What is intercepted: nothing — MISO reads
job progress rate and `nvidia-smi` memory. Granularity: per-job, per-GPU,
re-run on every job arrival or completion.

### 2.2 Quantitative results (8× A100-PCIe-40GB testbed; 40-GPU simulation)

- vs unpartitioned: **JCT −49%**, makespan −15%, system throughput +23%
  (real system); median **JCT −70%**, makespan −20%, STP +30% in the
  40-GPU / 1000-job simulation.
- vs optimal *static* MIG partition (exhaustive offline search):
  **JCT −16%**, makespan −23%, STP +35%.
- Within **10%** of an offline Oracle on all three metrics (7% on STP).
- vs MPS-only equal three-way split: **JCT −35%**; 80% of jobs within 2×
  of exclusive-A100 JCT under MISO vs 30% under MPS-only.
- Time breakdown: NoPart spends **>60% of job life in the queue**; MISO
  and Oracle eliminate queue time entirely; MISO's costs are **12% in
  MPS profiling mode** and **3% checkpointing**. MIG-based profiling
  instead of MPS would push checkpointing past **20%** and profile
  **8×** slower.
- MIG reconfiguration costs **~4 s** per GPU reset plus seconds-to-minutes
  of checkpoint/restore for all resident jobs.
- Predictor: **2800 job mixes → 14000 after 4 column permutations**, 75%
  train; 50 epochs, **3 s/epoch on one A100**; validation MAE **0.017**
  (1.7%). Robust to error degrading to 9%. Optimizer runtime **0.5 ms**
  at 18 configs, **80 ms at 180**, <1 s at 1800.
- Cutting MPS profiling to 0.5× sharply raises error; raising to 1.5×
  gains nothing and **costs 4% JCT**.
- Heuristics (cosine similarity of the partition vector to job memory /
  power / SM util) give **8–14% lower throughput** than optimal.
  Collaborative filtering, linear regression, regression trees and MLPs
  all failed to converge on this feature set.

### 2.3 Hardware assumptions — hold / fail

| Assumption | 4090 / gfx1151, single process |
| --- | --- |
| MIG exists, with 18 legal partitions and hard cache/BW isolation | **Fails outright.** No MIG on 4090, none on RDNA3, none on any consumer part in 2024+. The entire output space of MISO is unavailable. |
| MPS gives a cheap, disruption-free proxy execution mode | Fails as MPS; **the idea survives** — cajeta can run the same kernels at reduced CU masks in-process at zero reset cost, which is *cheaper* than MPS. |
| Reconfiguration requires stopping all resident work (4 s reset) | **Does not apply.** CU masks and green contexts are set at stream/context creation and cost microseconds; there is no reset. This removes MISO's entire reason for existing. |
| Jobs are long-running (minutes to hours), so 30 s of profiling amortizes | **Fails for game and for LLM decode.** A frame is 16.7 ms; a decode token is ~10–100 ms. 10 s per probe level is 600 frames. |
| Per-job progress rate is observable | Holds — a cooperative-tile kernel's completion rate is directly observable at the submit seam. |
| Memory capacity is per-slice and jobs can OOM on a small slice | Partially holds; on gfx1151 the GPU shares host memory so the capacity constraint is soft. |

### 2.4 Adopt / adapt / cannot

**Adopt**
- The **"probe in the cheap mode, predict the expensive mode"** pattern,
  inverted: cajeta's cheap mode is *unrestricted co-run*, its expensive
  decision is *what CU mask to pin*. A short unrestricted co-run gives
  the same 3-level signal.
- The **three probe levels** {100%, 50%, 1/N} as a design point — the
  paper measured that 2 levels is not enough and 4+ is wasted. Use
  {full, half, 1/N of CUs}.
- **Prediction error tolerance**: 1.7% → 9% error barely moved the
  outcome. A crude estimator is enough; do not over-engineer.
- **No-bubble constraint** (`‖x⃗‖₀ = m`): never leave a partition unit
  idle while work is queued.

**Adapt**
- The optimizer objective `max Σ f_i(x_i)` is *throughput*. For cajeta's
  latency and frame-budget policies the objective must become
  `max Σ f_i` subject to per-kernel deadline satisfaction, i.e. MISO's
  optimizer with iGniter's constraints.
- The 18-config enumeration becomes an enumeration over legal CU-mask
  splits; on gfx1151 (WGP granularity) and 4090 (8-SM granularity) the
  space is larger than 18 but still small enough for exhaustive search
  at 80 ms scale.

**Cannot / cluster-only**
- MIG configuration and reconfiguration, checkpoint/restart, the
  least-loaded-GPU initial placement, the "maximum spare slice" record,
  QoS-by-minimum-slice, multi-instance job spawning — all cluster-only
  and all MIG-specific.
- The U-Net predictor itself. Its *purpose* is to avoid a
  reconfiguration cost cajeta does not pay.

### 2.5 Testable requirements

1. **[ML, simulation]** When a new long-running kernel stream joins a
   device that already has resident work, the scheduler may probe the
   mix at up to three CU-mask levels (full, half, 1/N) for a bounded
   probe window, and the probe shall not require stopping, resetting, or
   checkpointing any resident work.
2. **[game]** When any kernel on the device carries a frame-budget
   policy, the scheduler shall not enter a probing mode; it shall use
   the declared arithmetic-character tag and prior-frame timings only.
3. **[all]** When the scheduler holds a partition assignment, no
   partition unit shall be left masked-off while any admitted kernel is
   queued (no-bubble invariant).
4. **[all]** When the interference predictor's error is inflated to 10%,
   the resulting partition choice shall still beat an equal-split
   baseline on aggregate throughput — the policy shall not be sensitive
   to predictor precision beyond that.
5. **[ML]** When a partition decision must be made, the enumeration over
   legal partitions shall complete in under 1 ms for the device's native
   partition granularity.
6. **[all]** When a heuristic partition (proportional to declared working
   set, power, or occupancy) is used instead of a measured one, the
   scheduler shall record the gap; the measured design target is that
   such heuristics lose no more than 15% throughput.

## 3. Choi et al. 2022 — gpu-lets (USENIX ATC; arXiv title "Multi-model
Machine Learning Inference Serving with GPU Spatial Partitioning")

### 3.1 Core mechanism

gpu-lets is the direct antecedent iGniter compares against. It carves
each physical GPU into at most **two** virtual GPUs ("gpu-lets") using
post-Volta MPS `active_thread_percentage`, and schedules heterogeneous
models onto them with **elastic partitioning**: for each model, compute
`p_eff` (the knee of the throughput-vs-partition curve, found as the
local curvature maximum of an offline profile) and `p_req` (the minimum
partition that meets the SLO at the current request rate), take
`p_ideal = min(p_eff, p_req)`, then best-fit onto the sorted remaining
gpu-lets, splitting a 100% gpu-let if needed and **merging temporally**
where two models can share one gpu-let in a duty cycle. Interference is
predicted by a **linear regression on four solo-run counters**:

    interference_factor = c1·l2_m1 + c2·l2_m2 + c3·mem_m1 + c4·mem_m2 + c5

where `l2_*` is solo L2 utilization and `mem_*` is solo DRAM bandwidth
utilization for the two co-runners. Granularity: per model, per
scheduling period (20 s, chosen because MPS repartitioning takes 10–15 s).

### 3.2 Quantitative results (4× RTX 2080 Ti, Turing, 616 GB/s, PyTorch 1.2)

- Interference CDF over 250 co-located pairs (5 models × 5 batch sizes ×
  5 split ratios): **90% of pairs below 17.66% latency overhead**, but a
  long tail well beyond.
- Interference model: **90% of cases within 10.26% error**, **95% within
  13.98%**, trained on 1750 of 2500 profiled data points (**1250 pairs**).
- Throughput vs Nexus SBP baseline: **+106.0%** without interference
  awareness, **+102.6%** with it (the 3.4% gap is the price of the
  conservative interference check). vs GSLICE guided self-tuning:
  **+74.8%**.
- Interference awareness is what turns "schedulable" into "actually
  meets SLO": the interference-blind variant showed >1% SLO violation on
  rates it declared schedulable.
- Schedulability: **861 of 1023 scenarios** vs an exhaustive ideal
  scheduler's 879 — within **1.8%**.
- Rate-fluctuation trace over 1800 s: **0.14% of requests** violated SLO
  while partitions were resized.
- Cost framing: for the `game` app, 1502 req/s vs SBP's 720 req/s = a
  **47.9% effective cost saving** on identical hardware.
- Search space is `O(P^N · N·P·M²)` — the reason a greedy heuristic is
  required.

### 3.3 Hardware assumptions — hold / fail

- **Consumer GPU is the *actual* testbed** (RTX 2080 Ti, Turing). This
  is the only paper in this batch whose hardware resembles cajeta's.
  Turing's MPS resource provisioning is the same feature family as Ada's.
  But: it is still **multi-process** MPS. In-process, use green contexts.
- Turing has **no memory-bandwidth isolation** (the paper says so
  explicitly, footnote 1 — that landed with Ampere). Neither does RDNA3.
  So the DRAM-bandwidth term in the interference model is essential, not
  optional, on cajeta's targets.
- The **at most 2 partitions per GPU** limit is an artifact of MPS
  bookkeeping, not hardware. In-process, cajeta can have more, and
  iGniter's evidence is that gpu-lets' 2-way limit costs real efficiency.
- **10–15 s repartition cost** is an MPS-process-launch cost (spawn,
  load kernels, load models, warm up). In-process with green contexts /
  CU masks this collapses to microseconds — the 20 s scheduling period
  is entirely an artifact and should not be inherited.
- The **only five legal partition sizes** (20/40/50/60/80%) that gpu-lets
  allows is a self-imposed limit; iGniter shows the finer 2.5% grid wins.

### 3.4 Adopt / adapt / cannot

**Adopt**
- The **`p_eff` knee** — profile throughput vs partition size, take the
  local curvature maximum. This is exactly the "how many CUs does this
  kernel actually scale to" question a cooperative-tile kernel author
  wants answered, and it is directly measurable from the submit seam's
  geometry plus a resource sweep.
- **`p_ideal = min(p_eff, p_req)`** — never allocate past the knee, and
  never allocate past what the deadline needs. Spill the remainder to
  the next iteration/partition.
- The **two-counter interference model shape** (L2 utilization + DRAM
  bandwidth utilization of both co-runners, linear, with intercept).
  Both counters are available on RDNA3 (`rocprofv2`: `L2CacheHit`,
  `FetchSize`/`WriteSize`) and on Ada (Nsight `lts__*`, `dram__*`).
- The **conservatism principle**: a scheduler that predicts interference
  and refuses marginal co-residency delivered 3.4% less throughput and
  eliminated the SLO violations. Take the 3.4%.

**Adapt**
- The linear model needs **1250 pair profiles**. That is a
  build-time-only cost for a fixed kernel set, and untenable for
  user-authored kernels. Adapt to: fit the coefficients once per
  *backend* over a synthetic kernel family spanning the L2×DRAM plane,
  then apply to user kernels using their *declared* arithmetic character
  and buffer-set sizes as the feature values.
- Two-way partition → N-way. Re-fit: the model is pairwise by
  construction; iGniter's Eq (8) is the N-way generalization and should
  replace it.

**Cannot**
- The multi-GPU best-fit placement and the merge-across-GPUs logic
  (single-node but multi-device; cajeta's single/dual-device case makes
  it degenerate).
- The 20 s scheduling period and the dynamic partition reorganizer's
  background process-respawn — both exist only to hide MPS cost.

### 3.5 Testable requirements

1. **[all]** When a kernel is registered, the runtime shall determine its
   scaling knee `p_eff` — the smallest CU/SM partition beyond which
   throughput gain per added unit falls below a threshold — and shall
   never allocate it more than `p_eff` units while any other kernel is
   queued.
2. **[all]** When a kernel's deadline requires fewer units than `p_eff`,
   the scheduler shall allocate `min(p_eff, p_req)` and shall route the
   unserved work to the next scheduling round rather than growing the
   partition.
3. **[ML, simulation]** When predicting the slowdown of two co-resident
   kernels, the scheduler shall use both co-runners' L2 utilization *and*
   DRAM bandwidth utilization; a model using only one of the two shall be
   rejected in test.
4. **[all]** When the interference prediction is uncertain, the scheduler
   shall refuse co-residency rather than admit it; the measured
   acceptable price is ≤5% aggregate throughput.
5. **[game]** When repartitioning, the cost shall be bounded by stream or
   context creation only (microseconds); no design shall require
   respawning a process, reloading kernels, or a warm-up period.
6. **[all]** When the target device provides no memory-bandwidth
   isolation (RDNA3, Ada, Turing), the scheduler shall treat DRAM
   bandwidth as a shared, unpartitionable resource and shall account for
   it explicitly in admission.

## 4. Crankshaw et al. 2017 — Clipper (NSDI)

### 4.1 Core mechanism

Clipper is a **layered prediction-serving system** sitting between
applications and ML frameworks, and the only per-device mechanism worth
extracting is its **adaptive batching**. Each model container gets its
own batching queue and a thread; Clipper accumulates queries into a
mini-batch bounded by a **maximum batch size discovered online by AIMD**
— additively increase the max batch size until the measured batch
latency exceeds the latency SLO, then multiplicatively back off by
**10%** (a much smaller decrease constant than TCP-style AIMD, because
the optimum barely moves). It also uses **delayed batching**: under
bursty load, wait a short fixed timeout for more queries so the fixed
per-batch cost is amortized (Nagle's algorithm, explicitly). Model
selection uses Exp3 (pick one arm) or Exp4 (weighted ensemble), and
**straggler mitigation** enforces a latency deadline at which the
`combine` function is invoked with whatever predictions have arrived,
trading accuracy for a bounded tail. Granularity: per-model-container,
per-batch, continuously adapting.

### 4.2 Quantitative results (2× Haswell-EP, K20c GPUs, 2017)

- Batching gain: **up to 26×** throughput (Scikit-Learn linear SVM) under
  a 20 ms SLO. The maximum batch executable inside 20 ms differs by
  **241×** between a linear SVM and a kernel SVM (30,000 qps vs 200 qps).
- AIMD vs quantile regression on the P99-latency-vs-batch curve:
  **near-identical performance**; AIMD chosen for simplicity and for
  robustness to throughput shifts (e.g. a Spark GC pause).
- Delayed batching: **+3.3× throughput** at a 2 ms wait for the
  Scikit-Learn SVM (high fixed cost, BLAS-parallel variable cost);
  **zero gain** for the Spark SVM (low fixed cost). The gain is a pure
  function of fixed-cost / variable-cost ratio.
- Caching: **1.6×** feedback throughput (6K → 11K obs/s).
- Replication: **3.95×** on 4 GPUs over 10 GbE (19,500 → 77,000 qps);
  **saturates at 2 replicas over 1 GbE** — network, not GPU, becomes the
  bottleneck.
- Stragglers: P99 latency rises "sharply well beyond the 20 ms
  objective" at even small ensemble sizes; the deadline-cut strategy
  converts that into a small accuracy loss instead.
- vs TensorFlow Serving on identical TF models (MNIST bs 512, CIFAR bs
  128, ImageNet bs 16): C++ containers **within noise**; Python
  containers **15–18% slower** — the modular/RPC architecture itself
  costs ~nothing.

### 4.3 Hardware assumptions — hold / fail

- Clipper makes **almost no hardware assumptions**. It treats models as
  black boxes and needs only (a) that batch latency is a monotone
  function of batch size and (b) that an SLO exists. Both hold on
  gfx1151 and 4090.
- The one stale assumption: "frameworks that leverage GPU acceleration
  such as TensorFlow often enforce **static** batch sizes." Untrue since
  ~2019; every modern runtime handles variable batch. Cajeta's kernels
  are compiled per-geometry, so a *changing* batch means a new launch
  geometry, not a new compilation — but this must be verified against
  cajeta's kernel specialization, because if each batch size triggers a
  recompile, AIMD's continuous batch-size search is catastrophic.
- The **latency-profile linearity** Clipper observed (`lat ≈ αb + β`) is
  the same form Nexus adopts (Eq 1 there). It still holds on modern GPUs
  in the regime where the kernel is already occupancy-saturated; it fails
  below saturation (small batches on a 4090 are latency-flat, which is
  exactly the regime a knee-finder like gpu-lets' `p_eff` detects).

### 4.4 Adopt / adapt / cannot

**Adopt directly**
- **AIMD batch-size control with a 10% multiplicative decrease.** It is
  three lines of code, needs no profile, and matched a fitted quantile
  regression. This is the correct default for cajeta's throughput policy.
- **Delayed batching with a per-kernel wait timeout**, gated on the
  measured fixed/variable cost ratio. Cajeta can compute that ratio from
  two launches (b=1 and b=N) — no sweep needed.
- **Deadline-cut / best-effort completion**: at the deadline, act on
  whatever is done. This is the mechanism a frame-budget policy needs.
- The observation that **a modular RPC-mediated architecture costs ~0%**
  when the language binding is native — relevant to whether cajeta's
  submit seam adds measurable overhead. Target: within noise of a direct
  `hipModuleLaunchKernel`.

**Adapt**
- Batching in Clipper aggregates *independent requests*. Cajeta's
  analogue is aggregating independent tile launches into one grid, or
  merging decode requests. Only meaningful where the work is genuinely
  independent and the kernel is under-occupied.

**Cannot / cluster-only**
- Model selection (Exp3/Exp4), ensembling, contextualization, the
  prediction cache, container replication across a cluster. None of
  these are scheduling.

### 4.5 Testable requirements

1. **[ML]** When a kernel is under a throughput policy and its work
   items are independent, the runtime shall discover the maximum batch
   geometry by AIMD against the declared latency target, with a 10%
   multiplicative decrease, and shall converge without any offline
   profile.
2. **[ML]** When a kernel's fixed launch cost exceeds a configured
   fraction of its per-item cost, the scheduler shall apply a bounded
   delay before dispatch to accumulate more items; when it does not, the
   delay shall be zero.
3. **[game, all]** When a frame-budget deadline arrives and some
   submitted work has not completed, the scheduler shall complete the
   frame with the results available and report which submissions were
   cut, rather than blocking past the deadline.
4. **[all]** When batch geometry changes under AIMD, the runtime shall
   not trigger kernel recompilation; a geometry change shall cost no more
   than a launch-argument change.
5. **[ML]** When the same input is submitted repeatedly, results may be
   cached; the cache shall never be invalidated by a scheduling decision.
6. **[all]** When the submit seam is interposed, its overhead relative to
   a direct backend launch shall be within measurement noise for kernels
   above 100 µs and shall be reported for kernels below that.

## 5. Shen et al. 2019 — Nexus (SOSP)

### 5.1 Core mechanism

Nexus schedules DNN invocations on a GPU cluster with three per-device
ideas that matter here. **(a) Squishy bin packing**: a task's "size" is
not fixed — it shrinks as batch size grows — so packing must reason over
(model, batch, duty cycle) jointly. Each GPU cycles round-robin through
its assigned sessions within a **duty cycle** `d`; worst-case latency for
a session is `d + ℓ(b)`, not `2ℓ(b)`. Batching profile is fit as
**`batch_lat(b) = αb + β`**. **(b) Query analysis**: for a multi-stage
pipeline (detect → recognize), split the end-to-end SLO across stages by
dynamic programming, minimizing total GPU count; the optimal split
depends on the fan-out `γ` (outputs per input) and there is *no universal
best split*. **(c) Batch-aware dispatch**: at the node, a dedicated
thread launches batched kernels while a CPU thread pool does pre/post
processing (overlap), models on a shared GPU are cycled by the Nexus
runtime rather than left to the driver's FCFS interleaving, common model
prefixes are batched together, and requests are dropped with an
**early-drop** policy (skip requests that would force a sub-optimal
batch) rather than lazy drop.

### 5.2 Quantitative results

- Batching gain on **GTX 1080** (consumer!): **4.7–13.3×** throughput at
  batch 32 for VGG / ResNet / Inception vs batch 1.
- vs Clipper and TF Serving on 16 GPUs: **9.4× / 12.7×** on the `game`
  app; **1.8–4.4×** on `traffic`.
- Game ablation (4120 req/s full): removing prefix batching → 3628;
  −squishy → 2489; −early drop → 2413; **−CPU/GPU overlap → 325**
  (a 7.4× drop). Overlap dominates in the **tight-SLO (50 ms),
  small-model (6.2 ms ResNet-50, <0.1 ms LeNet), high-preprocessing
  (~10 ms)** regime — because serializing preprocessing with GPU
  execution leaves **~half the GPU cycles idle** and forces batch≈1.
- Traffic ablation (534 req/s full, 400 ms SLO, SSD 47 ms at b=1):
  −query analysis → 433 (**−19%**); −squishy → 337; −early drop → 326;
  −overlap → 216 (only **−34%**, not 7.4×). **Relaxed SLO + large model
  ⇒ overlap stops mattering.**
- Query analysis picked **345 ms of a 400 ms budget for the SSD stage**
  — a wildly asymmetric split that an even split would never find.
- Early drop vs lazy drop (Clipper's policy): **up to +25% throughput**
  at 99% SLO attainment; lazy drop's bad rate reaches ~35% at small `α`
  because it always serves the oldest request and therefore always picks
  a small, inefficient batch.
- GPU multiplexing: Nexus **1.4–2.1×** over TF Serving and **1.9–9.8×**
  over Clipper on a single GPU as the number of co-resident models rises
  2→5. TF Serving beats Clipper because TF round-robins while Clipper
  runs independent containers that interfere.
- 16-GPU controlled workload: **11.7 GPUs used vs a 9.8-GPU theoretical
  lower bound = 84% of optimal**. 100-GPU deployment: **0.27%** SLO
  violations; workload change detected in **12 s** with 30 s epochs;
  deallocation lag ~10 s.
- Prefix batching: throughput and memory both scale well as the number of
  last-layer-only variants of ResNet-50 grows.

### 5.3 Hardware assumptions — hold / fail

- **The GPU multiplexing result is the most transferable finding in the
  batch and it is a *negative* result about drivers**: "if two models
  that share a GPU execute in two processes or containers, they will
  independently issue kernels... the GPU runtime will typically serve
  these requests in **first-come-first-served** fashion, resulting in an
  arbitrary interleaving... The interleaving increases the execution
  latency of both models and **makes it hard to predict the latency**."
  This holds exactly on HIP and CUDA today. It is the argument for
  cajeta owning the submit seam.
- `batch_lat = αb + β` holds where occupancy is saturated. On a 4090 or
  gfx1151 with a small kernel, `β` dominates for a wide range of `b` and
  the line is flat — the same regime gpu-lets' knee-finder detects.
- CPU/GPU overlap requiring **4–5 CPU cores per GPU** to saturate: on
  gfx1151 the CPU and GPU contend for the *same* memory bandwidth and the
  same package power, so the overlap gain is smaller and the interference
  is real. This must be re-measured, not assumed.
- The duty-cycle round-robin assumes the runtime can serialize kernels
  from different logical workloads. In-process with one stream per
  logical workload, cajeta controls this directly and more cheaply than
  Nexus does across processes.
- Drop-and-move-on service model: appropriate for video frames and for
  game rendering; **inappropriate for training and simulation**, where
  every item must complete.

### 5.4 Adopt / adapt / cannot

**Adopt directly**
- **The duty-cycle latency accounting**: worst-case latency for a
  co-resident workload is `duty_cycle + own_batch_latency`, not
  `2 × own_batch_latency`. Any admission test that gets this wrong
  under-provisions.
- **Own the submit order.** Do not let the driver FCFS-interleave
  kernels from independent logical workloads; cycle them explicitly.
  Measured value: 1.4–2.1× over a round-robin baseline, 1.9–9.8× over
  uncoordinated containers.
- **Early drop over lazy drop** where dropping is legal: +25%.
- **CPU/GPU overlap is the single biggest lever in the tight-deadline
  small-kernel regime** (7.4×). That regime is exactly game rendering and
  LLM decode. Host-side work (argument marshalling, tile setup, buffer
  binding) must be pipelined against device execution by construction,
  not as an optimization.
- The **`αb + β` fit** as the default cost model for a cooperative-tile
  kernel, with `β` as the launch-and-fixed cost the scheduler must
  amortize.

**Adapt**
- **Query analysis / latency splitting** generalizes directly to cajeta's
  multi-kernel pipelines (prefill → attention → FFN; G-buffer → lighting
  → post). The DP over a tree of stages with a per-stage budget `k` is
  reusable verbatim; the fan-out parameter `γ` becomes the ratio of
  output tiles to input tiles, which the submit seam's buffer sets
  already reveal. **The finding that the optimal split is 345/400 ms, not
  200/200, is the whole point** — an even split is always wrong.
- **Prefix batching** maps to merging kernels that share a leading
  subgraph — relevant for MoE experts and for LoRA variants.

**Cannot / cluster-only**
- The integer program and the greedy `ScheduleSaturate` /
  `ScheduleResidue` bin packing over GPU nodes, epoch scheduling
  (30–60 s), routing tables, frontends, admission control at cluster
  scale. All cluster-only.

### 5.5 Testable requirements

1. **[all]** When multiple independent kernel streams are resident, the
   runtime shall control their submit order explicitly and shall not rely
   on driver FCFS arbitration; a test shall show bounded per-stream
   latency variance under a mixed load where the uncontrolled baseline
   does not.
2. **[all]** When admitting a kernel to a device that cycles N resident
   workloads with duty cycle `d`, the admission test shall use
   `d + ℓ(b)` as the worst-case latency, not `2·ℓ(b)`.
3. **[game, ML]** When a kernel's deadline is tight relative to its
   device execution time, host-side submission work shall be overlapped
   with device execution; a test shall show device idle time below a
   threshold in the small-kernel/tight-deadline regime.
4. **[ML, game]** When a multi-kernel pipeline carries a single
   end-to-end deadline, the scheduler shall derive per-stage budgets by
   optimization over the stage cost curves and the inter-stage fan-out,
   and shall not split the budget evenly.
5. **[game]** When requests must be shed to hold a frame budget, the
   scheduler shall drop the requests that would force an inefficient
   launch geometry (early drop), not merely those already past deadline
   (lazy drop).
6. **[ML]** When two kernels share a leading subgraph, the runtime may
   execute the shared prefix once for the merged input set and the
   suffixes separately.
7. **[simulation]** When the workload forbids dropping, the drop policy
   shall be disabled and admission control shall instead reject at
   submit time.

## 6. Li et al. 2023 — AlpaServe (OSDI)

### 6.1 Core mechanism

AlpaServe's claim is counterintuitive and is the reason it is in this
batch: **model parallelism is worth its overhead even when a model fits
on one device**, because splitting a model across devices lets a burst
addressed to one model use *all* devices — statistical multiplexing. It
partitions a cluster into device groups; each group runs a shared
model-parallel runtime hosting several models; requests go to the group
with the shortest queue; each group is FCFS and rejects a request it
cannot serve within SLO (possible because DNN execution time is highly
predictable). Placement is chosen by a **simulator-guided greedy beam
search** (Algorithm 1) wrapped in an **enumeration over group partitions
and parallel configurations** (Algorithm 2), with models pre-clustered
into **size buckets to avoid convoy effects** (small-model requests
queued behind large-model requests). Two parallelism axes with different
cost structures: **inter-op / pipeline** (overhead dominated by *stage
imbalance*, not communication; does not reduce single-request latency)
and **intra-op** (overhead is pure collective communication, cannot be
overlapped, but *does* reduce single-request latency).

### 6.2 Quantitative results (64× V100-16GB, 8 nodes; MAF1/MAF2 traces)

- Two 6.7B models on two 16 GB V100s, 0.4 s/request, Poisson λ=1.5/s:
  mean latency **0.70 s → 0.55 s (1.3×)** from 2-stage pipelining.
  Gamma arrival with **CV=3: 1.9×**. Skewed 20/80 split: **6.6×**.
- Headline: **up to 10× higher request rate, 2.5× tighter SLO, 6× more
  burstiness, or 2.3× fewer devices** at ≥99% SLO attainment.
- **Queueing-theory boundary conditions** (M/D/1, `W = D + λD²/(2(1−λD))`):
  model parallelism wins when **device memory is limited, arrival rate is
  low, CV is high, or SLO is tight**. It loses when the cluster is
  saturated, when memory is large enough to hold everything, or when SLO
  is loose. Fig. 10 gives the maximal tolerable overhead `α` (comm) and
  `β` (imbalance) as a function of total utilization `λD`: at high
  utilization the tolerable overhead collapses; at *very low*
  utilization `α` must also be small (nothing queues, so latency is pure
  processing time).
- SLO scale: model parallelism dominates below **~10× model latency**;
  real-world SLOs are **<5×**.
- Simulator fidelity vs testbed: **<2% error** on SLO attainment at every
  SLO scale (Table 2).
- Overhead decomposition: inter-op overhead is **mostly uneven partition,
  not communication**; intra-op overhead is **mostly communication** and
  is much larger.
- **Batching gain is limited for large models** — a small batch already
  saturates the GPU; execution latency grows linearly with batch size, so
  at SLO scale < 2 batching is not an option at all.
- Robustness: with a *deliberately mismatched* arrival trace, AlpaServe's
  static placement still beat an online replacement algorithm given the
  true trace.

### 6.3 Hardware assumptions — hold / fail

- **Multi-device by construction.** On a single-GPU host (gfx1151 alone,
  or one 4090) the central premise is void. On a dual-device host
  (gfx1151 iGPU + a dGPU, or 2× 4090) it applies but with only 2 groups.
- The **memory-capacity argument is inverted on gfx1151**: an APU with
  96–128 GB of unified memory holds every model. AlpaServe explicitly
  states that when memory is large enough to hold all models,
  **model parallelism yields nothing**. So on a big-memory APU, replicate.
- On a 4090 (24 GB) with large LLMs the memory argument holds.
- Inter-device communication on the same package (gfx1151) or over PCIe
  (4090) is far cheaper / far more expensive respectively than the V100
  NVLink assumed here. `α` must be measured per topology.
- The "DNN execution time is highly predictable" assumption **holds for
  fixed-shape kernels and fails for autoregressive decode with variable
  sequence length** — the paper says so, limiting itself to
  non-autoregressive one-forward-pass models. Cajeta's LLM decode target
  violates this.
- Batching disabled in most experiments **is stale for LLM serving**:
  continuous batching (2023+) is now the dominant throughput lever for
  decode, precisely because decode is memory-bound GEMV that batches into
  GEMM. AlpaServe's "small batch saturates the GPU" holds for large
  *prefill* and dense forward passes, not for decode.

### 6.4 Adopt / adapt / cannot

**Adopt (as a decision rule, not as a mechanism)**
- The **four-condition rule for when splitting work across devices beats
  replicating it**: limited memory, low arrival rate, high burstiness
  (CV), tight SLO. Encode this as the policy that decides between
  "one kernel on all CUs" and "two kernels on disjoint CU masks".
- The **convoy-effect finding**: never put a short-deadline kernel behind
  a long-running one in a FCFS queue. Bucket by expected duration.
- **Reject at admission when the deadline cannot be met**, rather than
  queueing and missing — possible because kernel time is predictable.
- **Simulator-guided search**: a discrete-event simulator with <2% error
  is cheap and lets the scheduler evaluate placements without running
  them. Cajeta can build this from the `αb + β` cost model plus the
  interference model.
- Least-slack-time-first with preemption named as future work — worth
  evaluating directly.

**Adapt**
- Inter-op vs intra-op maps onto cajeta's tile-partitioning choices:
  splitting a `Group` across CU partitions (intra-op-like: reduces
  latency, costs cross-partition reduction traffic) vs pipelining stages
  across partitions (inter-op-like: costs imbalance, not bandwidth). The
  measured claim that **imbalance, not communication, dominates the
  pipeline case** is a direct instruction for the tile scheduler: balance
  stage cost first, optimize inter-stage transfer second.

**Cannot / cluster-only**
- Group partitioning across 64 GPUs, controller-based dispatch,
  auto-parallelization compiler passes (Alpa's DP + ILP), periodic
  re-placement, the whole placement search.

### 6.5 Testable requirements

1. **[ML]** When a workload's working set fits comfortably in device
   memory and the device is not saturated, the scheduler shall replicate
   rather than split, and a test shall show splitting is a measurable
   loss in that regime.
2. **[ML, simulation]** When the request arrival coefficient of variation
   exceeds a threshold and the deadline is under ~5× the solo execution
   time, the scheduler shall split work across partitions even at a
   measured 10–50% partitioning overhead.
3. **[all]** When kernels with materially different expected durations
   are queued on the same partition, the scheduler shall separate them
   into duration buckets; a short-deadline kernel shall never queue
   behind a long one under FCFS.
4. **[all]** When a submitted kernel cannot meet its declared deadline
   even if dispatched immediately, the scheduler shall reject it at
   submit and report the rejection, rather than dispatching it.
5. **[all]** When evaluating a candidate placement, the scheduler may use
   a discrete-event simulation driven by the per-kernel `αb + β` cost
   model; the simulation shall agree with measured deadline attainment
   within 5%.
6. **[ML]** When splitting a pipeline across partitions, the scheduler
   shall balance per-stage cost before minimizing inter-stage transfer;
   imbalance is the dominant overhead term.
7. **[ML]** When the workload is autoregressive decode with variable
   sequence length, the "execution time is predictable" assumption shall
   be explicitly disabled and admission shall use a conservative bound.

## 7. Xiao et al. 2020 — AntMan (OSDI)

### 7.1 Core mechanism

AntMan co-designs a cluster scheduler with **modified DL frameworks** to
let a low-priority *opportunistic* job scavenge a GPU already holding a
high-priority *resource-guarantee* job, with near-zero impact on the
latter. Two per-device mechanisms. **(a) Dynamic memory scaling**: the
framework allocator gets an adjustable upper bound; tensors are allocated
by a `UniversalAllocator` that falls back to pinned host memory when the
GPU bound is hit, and the bound is raised/lowered **at mini-batch
boundaries** (which is where GPU memory use is at a cyclic minimum, so
almost nothing has to be copied). **(b) Dynamic computation scaling**: a
`GpuOpManager` intercepts every GPU operator *before* launch, queues it,
and **inserts idle slots to throttle the kernel launch rate** of the
opportunistic job — CPU operators keep running, so only the GPU stream is
throttled. The local coordinator drives both knobs using the
resource-guarantee job's **mini-batch time as the feedback signal**,
raising the opportunistic job's usage in step-like increments while the
guaranteed job's mini-batch time stays flat, and pessimistically clamping
it if that time becomes unstable.

### 7.2 Quantitative results (64× V100-32GB testbed; >5000-GPU production)

- Production cluster reality: only **20% of GPUs** use more than half
  their memory; only **10%** exceed 80% utilization. **90% of DL models
  occupy under 500 MB**; **80% of tasks have a mini-batch under 600 ms**.
- The motivating failure table (32 GB GPU, Job-A GCN 3.5 GB opportunistic,
  Job-B ResNet-50 30 GB guaranteed arriving 26 min later):
  preempt → A **fails**; FIFO → B queues 17.1 min extra;
  Gandiva-style packing → B **fails OOM**; universal memory without
  coordinated scaling → B takes **541.6 min** (SLA blown);
  **AntMan → A 43.9 min, B 91.8 min** vs B's 91.1 min exclusive.
- Memory scaling cost: ResNet-50 shrink 17.6 GB → 1.3 GB in **17 ms**;
  growth back in **143 ms** of which **115 ms is real overhead**. Across
  VGG16/Inception3/GoogleNet the worst overhead at a 1-minute scaling
  interval is **0.4%**.
- **Sensitivity to memory starvation is wildly model-dependent**:
  SuperResolution loses only **~25%** at a **90%** memory cut; VGG16 keeps
  most performance at **50%**; **ResNet-50 loses >60% at a 10% cut**.
  AntMan therefore allocates memory by introspective trial-and-error to
  whichever job improves normalized aggregate performance most.
- Computation scaling: ESPnet (guaranteed) co-run with ResNet-50
  (opportunistic) — naive packing stretches ESPnet **20.1 → 105.2 min**;
  with adaptive launch-rate throttling ESPnet holds **20.8 min** while
  ResNet-50 still retains **57%** of its solo performance.
- Trace on 64 GPUs: average JCT **2.05×** better than YARN capacity
  scheduler, **1.84×** better than Gandiva; makespan 1.76× / 1.67×.
  Guaranteed-job JCT matches preemptive YARN, which achieved it by
  **preempting 46% of jobs**.
- Production: **+17.1% more GPUs** made available, **GPU memory
  utilization +42%**, **SM utilization +34%**, queuing delay **2.05×**
  lower (tail 5960 s → 489 s). Of 10,000 sampled production jobs,
  **99% suffered zero measurable interference** (>10 ms mini-batch
  difference) during packing.

### 7.3 Hardware assumptions — hold / fail

- **AntMan needs no special hardware at all.** No MPS, no MIG, no CU
  masking. It works by throttling launch rate and bounding allocations
  inside the framework. This makes it the *most* transferable paper in
  the batch to consumer GPUs.
- The launch-rate throttle assumes the framework owns kernel dispatch.
  **Cajeta's submit seam is exactly that position** — a `GpuOpManager`
  equivalent is a natural fit.
- Memory scaling assumes a **discrete-GPU memory hierarchy** where host
  memory is a slower backing store. **On gfx1151 this is void** — GPU and
  host memory are the same physical DRAM, so "spilling to host" costs a
  page-table change at most. The entire memory mechanism collapses to
  "don't over-cache", which is still useful but not a scheduling lever.
  On a 4090 it holds fully.
- The cyclic-memory-minimum trick requires a **repeating iteration
  structure**. Holds for training and for LLM decode (per-token), holds
  for a game frame, does **not** hold for one-shot simulation kernels.
- The `mini-batch time` feedback assumes a stable periodic workload.
  Frame time is a direct analogue.

### 7.4 Adopt / adapt / cannot

**Adopt directly**
- **Launch-rate throttling as the isolation primitive.** Queue the
  low-priority stream's launches in the submit seam and insert idle
  slots; do not touch the high-priority stream. This needs no hardware
  partitioning, works on both backends, and is measured at 99%
  no-interference in production.
- **Progress rate of the protected workload as the only feedback
  signal.** Not GPU utilization, not queue depth — the protected
  workload's own iteration time.
- **Step-like increase, pessimistic clamp on instability.** When the
  protected workload's period becomes unstable, cut the opportunistic
  stream hard.
- **Scale at iteration boundaries**, where the resident memory is at its
  cyclic minimum.
- The **model-dependence of memory sensitivity** (ResNet-50 −60% at −10%
  memory; SuperResolution −25% at −90%) is a caution: never assume a
  uniform response to resource reduction; measure per kernel.

**Adapt**
- Universal memory / host spill: on APUs, replace with "bound the
  allocator cache" only. On dGPUs, keep the spill path but note the
  measured shrink/grow asymmetry (17 ms vs 115 ms) — growth is ~7× more
  expensive than shrinkage, so hysteresis must be asymmetric.

**Cannot / cluster-only**
- Global scheduler, tenant quotas, resource-guarantee vs opportunistic
  job classes as a cluster construct, gang scheduling, job upgrade,
  queue-delay estimation. Cajeta's analogue of the two classes is the
  schedule *policy* on the submit seam (latency/frame-budget = protected;
  throughput = opportunistic), which is a much better-defined signal than
  AntMan's tenant quota.

### 7.5 Testable requirements

1. **[all]** When a latency- or frame-budget-policy kernel stream and a
   throughput-policy stream are resident on one device, the scheduler
   shall throttle only the throughput stream, by deferring its launches,
   and shall never defer a launch on the protected stream.
2. **[all]** When throttling, the feedback signal shall be the protected
   stream's own iteration period; GPU utilization counters shall not be
   used as the control signal.
3. **[game]** When the protected stream's frame time variance exceeds a
   threshold, the scheduler shall immediately reduce the opportunistic
   stream's launch rate to zero and re-measure the baseline before
   resuming.
4. **[ML, simulation]** When resource allocation is reduced for a kernel,
   the scheduler shall use that kernel's measured sensitivity curve, not
   a uniform assumption; a test shall include one kernel that loses >50%
   at a 10% reduction and one that loses <25% at a 90% reduction.
5. **[ML]** When the device shares physical memory with the host (APU),
   the scheduler shall not implement a device→host spill path; it shall
   instead bound the allocator's retained cache.
6. **[ML]** When the device has discrete memory, growing an allocation
   bound shall be treated as materially more expensive than shrinking it,
   and hysteresis shall be asymmetric accordingly.
7. **[all]** When resource bounds are adjusted, the adjustment shall
   occur at an iteration or frame boundary and its cost shall be under 1%
   of the iteration period at the configured adjustment interval.

## 8. Wu et al. 2023 — TGS (NSDI)

### 8.1 Core mechanism

TGS is AntMan's mechanism moved **below** the application, into an
interposition layer between containers and the GPU driver, so it needs no
framework modification. It **intercepts CUDA driver API calls**: kernel
launches (for rate control) and memory allocations (`cuMemAlloc` →
`cuMemAllocManaged`). Compute sharing uses **adaptive rate control**: a
monitor thread counts **CUDA blocks launched per unit time** by the
production container (`α_in`) as a proxy for its throughput — chosen over
GPU utilization, which the paper argues is vaguely defined and only
loosely coupled to performance. An AIMD controller then adjusts the
opportunistic container's launch rate `β_out` to maximize it subject to
`α_in ≥ R`, where `R` is the production job's solo rate. The controller
has a slow-start phase (multiplicative growth), a congestion-avoidance
phase (additive increase / multiplicative decrease), and a reset that
re-measures `R` when the production job's own rate shifts by more than a
threshold. Memory sharing redirects all allocations into **CUDA unified
memory**, with `cuMemAdvise` setting the preferred location to the GPU
for production containers so that opportunistic pages are the ones
evicted, and `cuMemPrefetchAsync` to pull pages back when the production
job exits.

### 8.2 Quantitative results (2× A100-40GB PCIe; V100 for TF experiments)

- **Production-job overhead from sharing: 5% (low contention,
  ShuffleNet+MobileNet), 10.8% (high contention,
  ResNet-50+ShuffleNet).** Under memory oversubscription: **2.3%**
  (ResNet-50 + DLRM) and **12.3%** (BERT-Base + DLRM).
- Naive co-execution drops the production job to **57%** of exclusive.
- **MIG loses.** Partitioned two ways on an A100, each instance gets at
  most **4/7 of SMs and 1/2 of memory**; when the production job needs
  more than 4/7 SMs it falls to **77% of exclusive**. TGS beats MIG
  **1.5×** on the production job in the BERT+DLRM case.
- Opportunistic-job throughput vs the alternatives under memory
  oversubscription: **7.8× over MPS** (ResNet-50+DLRM); **24× over
  co-execution, 15× over MPS, 259× over MIG** (BERT+DLRM). Headline claim
  vs MPS: **up to 15×**.
- vs AntMan (application-layer): production job **104.1–104.3%** of
  AntMan's; opportunistic job **103–122%** of AntMan's. **An OS-layer,
  framework-agnostic implementation matched a framework-modifying one.**
- Mixed 100-job trace: co-execution inflates production JCT to **135%**
  of exclusive; **TGS costs 6%**. Opportunistic JCT falls to **48%** of
  exclusive.
- Rate-monitoring overhead alone: **0.3–5%** across models and batch
  sizes.
- Convergence: demonstrated across a dynamic arrival (job joins at 350 s)
  and a dynamic-phase workload (ESPnet2 cycling between GPU-heavy
  training, GPU-idle validation, and CPU-only phases at ~30 s scale) —
  TGS tracks the phase changes and reclaims/releases within the phase.
  MIG and MPS cannot change allocation at all while a job is running.
- Theorem 1: AIMD converges in `O(B log B)` calls, `B` = throughput limit.
- JCT reduction for the opportunistic job vs exclusive queuing reaches
  **95%** (low contention) / **47%** (high contention) at a 20× job
  duration ratio.

### 8.3 Hardware assumptions — hold / fail

- **TGS needs only two things: the ability to intercept launches, and
  the ability to count CUDA blocks per launch.** Both hold trivially at
  cajeta's submit seam, and cajeta gets them *for free* — it does not
  need an LD_PRELOAD shim.
- The **block count is available from the launch geometry**, which the
  submit seam already carries. This is the cheapest usable interference
  signal in the entire batch: no profiling, no counters, no model.
- The **critique of GPU utilization as a signal is directly applicable**:
  "the definition of GPU utilization is hardware-specific and often
  vague... it is unclear what a single utilization value actually means
  for a GPU with several types of compute units." RDNA3 has vector ALUs,
  matrix cores, and LDS; `rocm-smi --showuse` is a single number that
  means very little. Do not build a controller on it.
- Unified-memory redirection: **on gfx1151 this is meaningless** (already
  unified) and on RDNA3 the HIP equivalent (`hipMallocManaged` +
  `hipMemAdvise`) has weaker guarantees than CUDA's. The compute half of
  TGS transfers cleanly; the memory half does not.
- The MIG result — that a *hard* partition loses to a *soft* launch-rate
  throttle, because the hard partition cannot give the protected job more
  than its fixed slice — is the strongest available argument that
  cajeta's lack of MIG is not a limitation.
- The two-class (production / opportunistic) model maps onto cajeta's
  schedule policy field directly; TGS discovers the class externally,
  cajeta is *told*.

### 8.4 Adopt / adapt / cannot

**Adopt directly**
- **Launch-rate AIMD with block-count as the feedback signal.** This is
  the recommended default mechanism for cajeta's co-run isolation: no
  profiling, no hardware partitioning, converges in `O(B log B)`, costs
  0.3–5%, and matched a framework-modifying baseline.
- **Slow-start → congestion-avoidance → reset state machine**, including
  the reset that re-measures the protected baseline `R` when it shifts
  beyond a threshold. Phase-change detection falls out of this for free.
- **Reject GPU utilization as a control signal**, explicitly, with the
  stated reasoning.
- **Placement preference / eviction priority**: when both streams contend
  for a shared resource that has an eviction policy, the protected stream
  wins. On RDNA3 the equivalent lever is LDS/scratch reservation and
  allocation ordering, not page placement.

**Adapt**
- TGS controls a *rate*; cajeta can control a *rate and a CU mask*
  simultaneously. The rate controller should sit on top of the partition
  decision: choose the mask by the iGniter/gpu-lets model, then trim with
  AIMD. TGS does not evaluate this combination and it is the obvious
  cajeta-specific experiment.
- Block-count rate is a poor proxy when block cost varies wildly. Cajeta
  can do better with the arithmetic-character tag: weight the block count
  by declared per-block cost class.

**Cannot / cluster-only**
- Container interposition, Docker/Kubernetes integration, fate-sharing
  and fault-isolation arguments (cajeta is one process — the fault
  isolation TGS gains over MPS, cajeta does not have and does not need).

### 8.5 Testable requirements

1. **[all]** When two streams with different schedule policies are
   resident, the scheduler shall regulate the lower-priority stream's
   launch rate by AIMD, using the higher-priority stream's launched-block
   rate as the feedback signal, and shall converge within a bounded
   number of control intervals.
2. **[all]** When the higher-priority stream's launched-block rate
   deviates from its established baseline by more than a threshold, the
   controller shall zero the lower-priority rate and re-establish the
   baseline before resuming.
3. **[all]** The scheduler shall not use any driver-reported "GPU
   utilization" scalar as a control input.
4. **[game]** When a frame-budget stream co-runs with a throughput
   stream, the frame-budget stream's frame time shall stay within 10% of
   its solo frame time; a test shall show the uncontrolled baseline
   exceeding 40%.
5. **[ML]** When a protected stream has phases with materially different
   device demand (train / validate / host-only), the controller shall
   track the phase transitions and reallocate within one control interval
   after each transition.
6. **[all]** The rate-monitoring path shall add no more than 5% to a
   solo-running kernel stream's throughput, measured across models and
   launch geometries.
7. **[all]** When the device offers a fixed hard partition whose largest
   slice is smaller than the protected stream's requirement, the
   scheduler shall prefer soft rate control over the hard partition.

## 9. Xiao et al. 2018 — Gandiva (OSDI)

### 9.1 Core mechanism

Gandiva schedules DL training on a GPU cluster by exploiting **intra-job
predictability**: a job is millions of near-identical mini-batches, and
its GPU memory use follows a **cyclic pattern** with the minimum at the
mini-batch boundary. From that one observation it builds five primitives:
**suspend-resume** (wait for the memory-cycle minimum, copy the small
residual GPU state to host, free all GPU memory including cache, then
SIGSTOP — the memory ratio between cycle max and min is up to **77×**, so
this is an order of magnitude cheaper than a naive checkpoint);
**packing** (run two jobs concurrently on one GPU, retained only if
measured aggregate progress improves); **migration** (checkpoint-aware,
warm the destination first, move only training state); **grow-shrink**
(opportunistically widen a job's GPU count when the cluster idles);
and **profiling** (mini-batch period, measured as the time between two
GPU-memory-cycle minima, is the universal progress proxy). The scheduler
runs in a **reactive** mode (arrivals, departures) and an
**introspective** mode (continuous greedy trial-and-error: pack the
lowest-utilization job onto the lowest-utilization GPU, keep it if
aggregate throughput improved, undo otherwise).

### 9.2 Quantitative results (180-GPU cluster, P100/P40; PyTorch 0.3, TF 1.4)

- **Packing is model-dependent and sometimes negative** (Table 1, single
  P40, PyTorch, packing gain vs time-slicing):

  | Model | GPU util % | time-slice mb/s | packing max mb/s | gain |
  | --- | --- | --- | --- | --- |
  | VAE | 8.7 | 81.8 | 419.3 | **+412%** |
  | SuperResolution | 14.1 | 40.3 | 145.2 | **+260%** |
  | RHN | 61.6 | 10.1 | 14.8 | +46% |
  | SCRNN | 66.8 | 16.7 | 23.3 | +39% |
  | MI-LSTM | 76.2 | 22.2 | 25.9 | +17% |
  | LSTM | 87.2 | 63.8 | 53.0 | **−16%** |
  | ResNet-50 | 94.0 | 10.3 | 9.0 | **−13%** |
  | ResNext-50 | 98.9 | 83.6 | 74.4 | **−11%** |

  The paper's conclusion: "predicting packing performance **even with
  jobs of the same type appears challenging**", hence profiling-based
  trial-and-error rather than a model.
- Interference measurements: two Language Model jobs co-located under one
  PCIe switch → **19% slowdown each**; ResNet-50 co-located with LM →
  **none**. Across a 40 G InfiniBand pair: ResNet-50 **−47%**,
  InceptionV3 **−30%**, DeepSpeech **−5%**.
- Locality: VGG16 on 2 P100s gets **60%** of best-locality throughput
  when the GPUs are on different CPU sockets; ResNet-50 is unaffected.
- Suspend-resume cost: **<100 ms** for image classification, **up to 1 s**
  for large language translation → **≤2%** at a 60 s time-slice interval.
  Changing GPU costs 5–10 s (`cudaDeviceReset` + `CudaInit`) and is
  hidden in the background.
- Migration: CRIU-based is **8–10 s** for a 1-GPU job; checkpoint-aware TF
  migration is **1–3.5 s** (6 of 10 models under 1 s; DeepSpeech's 1.4 GB
  checkpoint 3.5 s), saving **98% of the 35 s** overhead for 8-GPU jobs.
- Time-slicing six 1-GPU jobs over 4 GPUs: aggregate throughput loss
  **<2%**.
- Cluster: average GPU utilization **50.1% → 62.8% (+26% relative)**;
  time to 100 mini-batches **2203 s → 498 s (−77%)**; full-trace average
  JCT **−26.8%**, makespan **−17.8%**, ~1 migration every 20 minutes.
- AutoML: **~10×** more hyperparameter configurations explored;
  **5.5–7×** faster to a qualified config on 4 GPUs, 3.4–6× on 16.
- **Stale caveat, stated by the authors**: "these packing results are
  without enabling NVIDIA's MPS. We found that MPS results in significant
  overhead in P40/P100 GPUs. However, hardware support for MPS in V100
  GPUs suggests that the use of MPS may be able to increase further
  packing gains."

### 9.3 Hardware assumptions — hold / fail

- The packing table was measured **without MPS on pre-Volta hardware**.
  On Ada/RDNA3 with proper concurrent-kernel execution the negative
  numbers would likely be smaller. **Treat the −11..−16% entries as
  stale; treat the +412%/+260% entries as still directionally right.**
  The *shape* — packing pays hugely below ~15% occupancy and hurts above
  ~85% — is the durable finding.
- The 77× memory-cycle ratio is a **training** artifact (activations
  freed on the backward pass). It holds for cajeta's training target.
  For LLM decode the KV cache is persistent and the ratio collapses. For
  a game frame there is a cyclic minimum but transient allocations are
  small relative to persistent textures/buffers.
- Suspend-resume as implemented requires framework cooperation (track GPU
  objects, patch device addresses on resume). **Cajeta owns its runtime,
  so this is available**, but a `hipDeviceReset` equivalent costing 5–10 s
  makes GPU-change-on-resume unattractive; stay on one device.
- Locality/affinity results (PCIe switch topology, NUMA sockets) are
  multi-GPU and largely irrelevant to a single-device target; they
  matter only for the gfx1151 iGPU + dGPU case.
- **Profiling-based trial-and-error needs a stable, repeating workload
  and tolerates seconds of settling time.** That is fine for training and
  simulation; it is unusable inside a 16.7 ms frame.

### 9.4 Adopt / adapt / cannot

**Adopt**
- **Occupancy-thresholded packing.** Only co-locate kernels whose
  measured occupancy leaves room; the measured cutover is around
  60–75% occupancy, with clear wins below ~15% and clear losses above
  ~87%. This is a directly usable admission rule and it is *cheap* —
  occupancy is a static property of a compiled kernel plus its geometry,
  which cajeta knows at the submit seam without profiling.
- **Trial-and-revert as the fallback when the model is uncertain.** Pack,
  measure aggregate progress for a bounded window, undo if it did not
  improve. The paper's honest admission that packing is not analytically
  predictable is worth respecting: cajeta should have a revert path even
  with an interference model.
- **Progress rate from the memory-cycle period** as a zero-instrumentation
  iteration detector. Cajeta has a better signal (it sees launches), but
  the principle — derive the iteration boundary from the workload's own
  periodicity — is right.
- **Suspend at the cyclic memory minimum**, if suspend is ever needed.

**Adapt**
- Time-slicing at a **60 s** interval is a cluster-fairness quantum.
  Cajeta's analogue is a much smaller interleave quantum, and the
  relevant measured constant is not 60 s but the **≤2% aggregate loss**
  Gandiva achieved when the switch cost was ≤2% of the quantum. That
  ratio is the design rule: **switch cost ≤ 2% of quantum**.

**Cannot / cluster-only**
- Migration (intra- and inter-server), grow-shrink across servers,
  affinity-aware placement, defragmentation, the node-allocation
  algorithm, the AutoML integration, cluster fairness. All cluster-only.

### 9.5 Testable requirements

1. **[all]** When two kernels are candidates for concurrent residency,
   the scheduler shall admit the pair only if their combined static
   occupancy leaves headroom; kernels whose solo occupancy exceeds a
   configured high-water mark shall be time-interleaved rather than
   co-resident.
2. **[all]** When a co-residency decision is made under model
   uncertainty, the scheduler shall measure aggregate progress over a
   bounded window and revert the decision if progress did not improve;
   the revert shall be observable in a test.
3. **[ML, simulation]** When a kernel stream is interleaved rather than
   co-resident, the context-switch cost shall not exceed 2% of the
   interleave quantum; the runtime shall choose the quantum to satisfy
   this given the measured switch cost.
4. **[ML]** When a training workload must be suspended, the suspend shall
   occur at the iteration's memory minimum, and the resident state copied
   shall be at least an order of magnitude smaller than the iteration's
   peak allocation.
5. **[all]** When a kernel's solo occupancy is below ~15%, the scheduler
   shall prefer co-residency over interleaving; the measured gain target
   is >2× aggregate throughput.
6. **[simulation]** When a long-running kernel holds a device and a
   short-deadline kernel arrives, the scheduler shall admit the short
   kernel immediately by co-residency or interleaving rather than
   queueing it to completion; the measured target is a >50% reduction in
   time-to-first-result.

# Cross-paper synthesis

## A. The interference models, and what each demands per kernel

Four distinct models appear, at four price points.

| Model | Form | Inputs per kernel | Profiling cost | Co-runners | Reported accuracy |
| --- | --- | --- | --- | --- | --- |
| **TGS** (launch rate) | none — closed-loop AIMD on `α_in` | launched blocks per launch (from geometry) | **zero** | N | n/a; converges `O(B log B)`, 0.3–5% overhead |
| **Gandiva** (occupancy threshold + revert) | none — trial and revert | solo GPU utilization, solo memory | one solo run | 2 | none; explicitly declared unpredictable |
| **gpu-lets** (linear regression) | `Δ = c1·l2₁ + c2·l2₂ + c3·mem₁ + c4·mem₂ + c5` | solo L2 util, solo DRAM BW util | **1250 pairs / 2500 points** | **2 only** | 90% within 10.26%, 95% within 13.98% |
| **iGniter** (analytical, 3 channels) | Eq (5)–(11) above | `d_load`, `d_feedback`, `n_k`, `k_sch`, `k_act(b,r)`, `p`, `c`, `α_cache` | **11 configs**, ~4 min | **N** | 1.53–5.02% at 4 co-runners; 0.04–9.29% overall |
| **MISO** (learned MPS→MIG) | U-Net autoencoder | 3×7 progress-rate matrix from 30 s of probing | 2800 mixes offline | ≤7 | MAE 1.7%; tolerant to 9% |

**The per-kernel inputs cajeta already has for free at the submit seam,
that these papers had to profile:**

- `n_k` (launch count) — iGniter profiles it with Nsight Systems.
- Launched block count per kernel — TGS builds an interposition layer for it.
- Read/write buffer sets → **L2 working-set estimate `c`** — iGniter and
  gpu-lets both measure this with Nsight Compute / rocprof.
- Read/write byte volume → **DRAM bandwidth demand `mem`** — gpu-lets
  profiles it.
- Arithmetic-character tag (compute vs memory bound) — this is precisely
  the latent variable that gpu-lets' four-counter regression and MISO's
  autoencoder exist to recover. **Cajeta is told it. This is the single
  largest structural advantage over every system in this batch**, and it
  should collapse gpu-lets' 1250-pair profiling requirement to a
  per-backend one-time calibration over a synthetic kernel family.
- Static occupancy (registers, LDS, waves per CU) — known at compile time.

**What still must be measured at runtime, per kernel, no shortcut:**

1. Solo kernel duration as a function of geometry and CU count —
   `k_act(b, r)`, needed by iGniter Eq (11) and by the `p_eff` knee.
   Minimum viable: 3 CU levels × 2 geometries = 6 runs.
2. `α_cache` — the kernel's *sensitivity* to L2 pressure, which is not
   the same as its L2 footprint. Requires at least one co-run.
3. Power draw `p` — needed for Eq (9)/(10) and unavoidable at the
   ~10–100 ms sampling latency of `rocm-smi` / NVML.
4. `α_sch`, `β_sch`, `α_f` — per-backend constants, calibrated once.

**Recommended layering** (cheapest first, escalate only on failure):
TGS launch-rate AIMD as the always-on safety net → Gandiva's occupancy
threshold as the admission gate → iGniter's three-channel model to choose
the CU mask when a deadline is declared → gpu-lets' `p_eff` knee to cap
the mask. Do not build MISO's learned predictor; its purpose is to avoid a
reconfiguration cost cajeta does not pay.

## B. Batching-vs-latency rules that transfer to a single process

1. **The half-SLO rule.** Nexus and iGniter both enforce: batch execution
   latency ≤ SLO/2, because a request that misses one batch is served by
   the next. Generalized for a duty cycle over N resident workloads:
   worst case is **`duty_cycle + ℓ(b)`**, not `2·ℓ(b)` (Nexus §4.1).
   Any admission test that uses `2·ℓ(b)` under-provisions the moment a
   second workload is resident.
2. **`ℓ(b) = αb + β`** is the transferable cost model (Nexus Eq 1,
   Clipper's observed linearity). `β` is the launch-and-fixed cost; the
   whole point of batching is amortizing it. Cajeta can obtain `α` and
   `β` from **two launches**.
3. **Delayed batching pays exactly in proportion to `β/α`.** Clipper
   measured +3.3× for a high-`β` model and **0×** for a low-`β` one at the
   same 2 ms wait. Do not apply a global batch-wait timeout; gate it on
   the measured ratio.
4. **AIMD with a 10% multiplicative decrease** matched a fitted quantile
   regression (Clipper Fig. 4) and is robust to throughput shifts. Use it
   as the default for the throughput policy.
5. **Early drop beats lazy drop by up to 25%** (Nexus Fig. 9). Lazy drop
   (Clipper's policy) always serves the oldest request, therefore always
   picks a small batch, therefore falls further behind. Where dropping is
   legal (game frames, streamed video), drop the requests that would
   force a bad geometry, not merely the expired ones.
6. **Batching stops paying when a single item already saturates the
   device.** AlpaServe measured this for large models. The corollary:
   whether to batch is a function of the *occupancy* of the unbatched
   kernel, which cajeta knows statically. Below ~15% occupancy, batch
   aggressively; above ~85%, do not batch at all, interleave instead.
7. **Latency budgets across a pipeline must be split by optimization,
   not evenly.** Nexus's traffic pipeline optimum was **345 ms of 400 ms**
   to the first stage; an even split cost 19% throughput. The optimum
   depends on inter-stage fan-out `γ` and changes with the workload
   (Nexus Fig. 4: the best of three splits differs for γ = 0.1, 1, 10).
8. **CPU/GPU overlap is worth 7.4× in the tight-deadline small-kernel
   regime** and only 1.34× in the loose-deadline large-model regime
   (Nexus, game vs traffic ablations). Game rendering and LLM decode are
   the first regime. This is not a batching rule but it dominates every
   batching rule in that regime.

## C. Spatial-partition mechanisms on consumer AMD/NVIDIA, and what each buys

| Mechanism | Available on | In-process? | Granularity | Cost to change | What it buys | Evidence |
| --- | --- | --- | --- | --- | --- | --- |
| **HIP CU mask** (`hipExtStreamCreateWithCUMask`) | RDNA3 incl. gfx1151, CDNA | **yes** | per-WGP, per-stream | stream creation, µs | true spatial isolation of vector ALUs; L2/MALL and DRAM BW still shared | not evaluated by any paper here; closest analogue is MPS thread-percentage |
| **CUDA green contexts** (12.4+) | Ada incl. 4090, Hopper, Blackwell | **yes** | SM-partition units (~8 SMs on Ada) | context creation | same as above, in-process | post-dates all nine papers |
| **CUDA MPS `ACTIVE_THREAD_PERCENTAGE`** | Volta+ incl. 4090 | **no** (cross-process) | 1% nominal, coarser in practice | 10–15 s (process respawn, model load, warm-up) | what iGniter/gpu-lets/MISO actually used | gpu-lets: +102.6% throughput; iGniter: −25% cost |
| **MIG** | A100/A30/H100 only | n/a | 7 fixed slice types, 18 legal partitions | ~4 s GPU reset + checkpoint all jobs | hard SM + L2 + memory-BW + fault isolation | MISO: +16% JCT over best static; **TGS: loses to soft rate control** |
| **Stream priority** (`hipStreamCreateWithPriority`, `cudaStreamCreateWithPriority`) | both | yes | 2–3 levels, no resource guarantee | free | weak hint only; the driver still FCFS-arbitrates ready work | Nexus's negative result on driver FCFS applies |
| **Launch-rate throttling** (submit seam) | both, everywhere | yes | continuous | free | isolation without any hardware support | **TGS: 5–12.3% overhead, matches AntMan, 15× over MPS on the opportunistic job** |
| **Time-interleaving / suspend-resume** | both | yes | iteration boundary | ≤100 ms (Gandiva image models) | full isolation, zero interference | Gandiva: <2% aggregate loss at 60 s quantum |
| **Vulkan queue priority / async compute** | both | yes | queue | free | graphics/compute overlap only | not covered by these papers |

**The load-bearing conclusions.**

- **The absence of MIG is not a limitation.** TGS measured a hard MIG
  partition *losing* to soft launch-rate control — 77% of exclusive
  throughput for the protected job, because MIG's largest 2-way slice is
  4/7 of SMs and half the memory, and it cannot be resized while jobs
  run. Cajeta's soft mechanisms are strictly more flexible.
- **CU masking / green contexts recover almost everything MPS gave
  iGniter and gpu-lets**, at a repartition cost of microseconds instead
  of 10–15 seconds. This means the 20 s scheduling period (gpu-lets) and
  the epoch-scale provisioning (iGniter) are artifacts that should not be
  inherited; cajeta can repartition per frame.
- **Nothing available on consumer hardware partitions L2 or DRAM
  bandwidth.** Turing, Ada and RDNA3 all lack memory-bandwidth isolation
  (gpu-lets footnote 1 says Ampere introduced it; consumer parts did not
  inherit it). So iGniter's Eq (8) L2 term and gpu-lets' DRAM term are
  *mandatory*, not optional — spatial partitioning does not make them go
  away.
- **Rate control and spatial partitioning are complementary and no paper
  evaluates the combination.** TGS has rate control and no partitioning;
  iGniter/gpu-lets/MISO have partitioning and no rate control. Choosing a
  CU mask by the interference model and then trimming with AIMD is the
  obvious cajeta design and is an open question in the literature.

## D. Where the papers contradict each other

1. **Hard partition vs soft control.** MISO: MIG's hardware isolation
   beats MPS "in most cases" and dynamic MIG beats optimal static MIG by
   16%. TGS: MIG loses to software rate control on the production job
   (77% vs ~90% of exclusive) and loses catastrophically on the
   opportunistic job (TGS is 259× better in one case), because MIG's
   slices are fixed and cannot be resized while work runs.
   **Resolution:** MISO's workloads are long training jobs where a 4 s
   reset amortizes and both jobs are equal citizens; TGS's are a
   protected job plus a scavenger, where the protected job needs more
   than any fixed slice can give. Cajeta's case is TGS's case. **Prefer
   soft control; use partitioning as a coarse hint, not a guarantee.**

2. **Concurrent packing vs time-slicing.** Gandiva measures packing as
   **negative** (−11% to −16%) for high-occupancy models and refuses to
   model it ("predicting packing performance even with jobs of the same
   type appears challenging"). AntMan and TGS both co-run
   high-utilization models successfully (ResNet-50 retaining 57% while
   ESPnet holds its SLA; production job at 89–95% of exclusive).
   **Resolution:** Gandiva packs *without any rate control* and *without
   MPS* on pre-Volta hardware. The difference is not packing vs
   time-slicing, it is regulated vs unregulated co-residency. **Unregulated
   co-residency of two high-occupancy kernels is a loss; regulated
   co-residency is not.**

3. **Drop policy.** Clipper uses lazy drop (drop only after the deadline
   is missed) and determines batch size from the earliest request's
   remaining budget. Nexus measures this policy as up to 25% worse than
   early drop, and shows its bad rate reaching ~35% under Poisson arrival
   with a small `α`. **Nexus wins on measurement; Clipper is the earlier
   paper.**

4. **Batching's importance.** Nexus: batching is 4.7–13.3× and is the
   organizing principle of the whole system. AlpaServe: "we do find
   batching is helpful, but the gain is limited," and disables it for
   most experiments. **Resolution:** the difference is whether one
   request saturates the device. It does for a 6.7B-parameter forward
   pass on a V100; it does not for LeNet or ResNet-50 on a GTX 1080.
   The deciding variable is unbatched occupancy — which cajeta knows
   statically. *Also note this is where AlpaServe is most stale:
   continuous batching for LLM decode (2023+) re-established batching as
   the dominant lever for exactly the workload AlpaServe excluded.*

5. **What is observable.** iGniter builds its scheduler on the claim that
   GPU scheduling delay grows linearly and predictably with co-runner
   count and can be modelled from `n_k`. TGS argues the opposite about
   the closely related signal — "an empty production queue does not mean
   production jobs are not using the GPU... keeping track of GPU kernels
   running on the GPU is also not feasible, because the state of the GPU
   is not fully visible" — and explicitly rejects GPU utilization as a
   control signal. **Both can be right:** iGniter's `Δ_sch` is an offline
   *statistical* fit over co-runner count, not an online observation.
   Cajeta should use iGniter's fit for admission planning and TGS's
   arrival-rate signal for online control, never the reverse.

6. **Profiling cost.** gpu-lets: 1250 pairs (2500 data points), and the
   model still only handles 2 co-runners. iGniter: 11 configurations per
   workload, ~4 minutes, handles N. MISO: 2800 job mixes offline plus
   30 s online per mix. Gandiva: zero offline, pure trial-and-revert.
   TGS: zero, ever. **The measured accuracy ordering does not follow the
   cost ordering** — iGniter (11 configs) is more accurate than gpu-lets
   (1250 pairs) at 4 co-runners because it is analytical rather than
   regressed. Cheap and structured beats expensive and fitted.

7. **Spatial vs temporal as the primary axis.** Gandiva's entire design
   is temporal (60 s time slices, suspend-resume, migration), with
   packing as an opportunistic add-on. gpu-lets/iGniter/MISO's entire
   design is spatial, with temporal merging as an add-on. AntMan and TGS
   are neither — they regulate *rate*, which is a third axis both camps
   ignore.

## E. What is stale on 2024+ hardware

1. **"MPS is the only spatial partitioning knob."** False since CUDA 12.4
   (green contexts, in-process SM partitioning on Ada/Hopper/Blackwell)
   and false on ROCm (per-stream CU masks). Every "requires MPS, therefore
   requires multiple processes, therefore 10–15 s to repartition"
   conclusion in gpu-lets, iGniter and MISO is obsolete. **The 20 s
   scheduling period and the 4 s MIG reset are not costs cajeta pays.**

2. **Gandiva's packing table.** Measured **without MPS on P40/P100**
   (pre-Volta, no hardware concurrency support), and the authors say so.
   The negative entries (−11% to −16% for ResNet-50/ResNext-50/LSTM)
   should not be taken as a prediction for Ada or RDNA3. The *shape* —
   large gains below ~15% occupancy, losses above ~87% — is durable.

3. **MIG's relevance.** Still zero on consumer parts in 2024–2026 (no MIG
   on 4090, 5090, or any RDNA generation). MISO's entire output space is
   unreachable. Meanwhile MIG's *limitation* that TGS exposed — fixed
   slices, no live reconfiguration — persists on the datacenter parts.

4. **AntMan and TGS's memory-swap mechanism on APUs.** Both are built on
   "GPU memory is separate from and faster than host memory, so evict to
   host." **On gfx1151 the GPU and CPU share one physical LPDDR5X pool.**
   The compute half of both papers transfers cleanly; the memory half
   degenerates to "bound the allocator's retained cache," which is still
   worth doing (both papers show frameworks over-claim memory) but is no
   longer a scheduling lever. On a 4090 the original mechanism holds.

5. **AlpaServe's "batching gain is limited."** True for non-autoregressive
   large-model forward passes, which is what it measured, and explicitly
   scoped that way in the paper. **Stale for LLM decode**, where
   continuous batching is now the dominant throughput mechanism because
   decode is a memory-bound GEMV that becomes a GEMM under batching.
   Cajeta's LLM decode target must not inherit this conclusion.

6. **Clipper's "frameworks enforce static batch sizes."** Obsolete. But
   it raises a live cajeta-specific question: if cajeta specializes
   kernels per geometry, does an AIMD batch-size search trigger
   recompilation? If so, AIMD is unusable and the batch-size ladder must
   be quantized to pre-compiled geometries.

7. **PCIe as the transfer bottleneck** (iGniter Eq (3), Clipper's 1 GbE
   saturation, Nexus's overlap analysis). On gfx1151 there is no transfer.
   On a 4090 over PCIe 4.0 x16 (~25 GB/s effective) vs the paper's V100
   at 10 GB/s, the term is smaller but not gone.

8. **Power as a second-order effect.** iGniter treats the power/frequency
   channel as the third and smallest of three. On consumer parts it is
   arguably first-order: a 4090 throttles under mixed dense-FP32 +
   tensor-core load well before it runs out of SMs, and gfx1151 shares a
   package budget with the CPU so that host-side overlap (Nexus's 7.4×
   lever) *directly steals GPU clock*. **The Nexus overlap result and the
   iGniter power result interact on an APU in a way no paper in this
   batch measures, and that interaction should be an early experiment.**

9. **"4–5 CPU cores per GPU to saturate"** (Nexus). Modern host-side
   submission is cheaper (CUDA graphs, HIP graphs, persistent kernels),
   and on an APU the cores contend for the GPU's own memory bandwidth.
   Re-measure; do not inherit the constant.
