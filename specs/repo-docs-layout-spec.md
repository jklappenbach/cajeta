# One documentation layout for every repo (spec)

Status: draft, written 2026-10-11 at Julian's request. Open questions in 6.

## 1. Definition

### 1.1 Purpose

A user of cajeta or of a `dev.cajeta.*` library should find the same things in
the same places in every repository: what the project is and how to start, what
changed in each release, how to use it overall, how each package is used, and
which calls are the front doors. Today each repository answers differently, and
none answers "what changed in this release" at all.

### 1.2 What is there today, read 2026-10-11

- cajeta keeps no release notes. `.github/workflows/release.yml` publishes a
  fixed body ("Automated release of cajeta ..."), so a release says nothing of
  its contents, and int64-scan-verbs plan item 5.2.3 (a release-notes entry)
  had no home.
- cajeta's `README.md` is 1046 lines; it already has a Version section that a
  bot updates with release links.
- cajeta's `docs/` has the shape this spec asks for: `guide/` (usage, numbered
  chapters), `stdlib/` (a page per package, 25 of them), `specification/`.
- `cajeta doc` renders `/** */` comments to an HTML site, and `@EntryPoint`
  methods feed its Entry Points index (`entry-points.html`). It writes no
  Markdown.
- The libraries differ: cajeta-llm and cajeta-jinja have a README and no
  `docs/`; cajeta-cabra has neither; cajeta-logging has `docs/` and no README;
  cajeta-codec, -http, -ml, -unit and cajeta-xgboost have both, each laid out
  its own way.

### 1.3 Constraints

- Authored in Markdown, as `docs/` already is; site builders import it.
- Nothing generated is edited by hand: a generated page says so in its first
  line and is rebuilt, not patched.
- `specs/` and `agents/` stay workflow artifacts, never user docs
  (td-project-workflow).

## 2. The layout

Every repository has:

- **`README.md`**: what the project is, how to install or depend on it, a
  quick start that compiles, and links to the four below. It does not hold
  release notes or reference material.
- **`CHANGELOG.md`**: one section per released version, newest first, headed
  `## <version> (<date>)`, with the user-visible additions, changes and fixes.
  An `## Unreleased` section at the top collects entries as work lands.
- **`docs/guide.md`** (or `docs/guide/` for a large project, as cajeta has):
  overall usage, task by task.
- **`docs/packages/<package>.md`**: one page per public package, what it is
  for and how its classes are used together. cajeta's `docs/stdlib/` is this
  for the standard library.
- **`docs/entry-points.md`**: the `@EntryPoint` methods grouped by package,
  generated by `cajeta doc` (3).

### 2.1 Use cases

- **2.1.1** When a user opens any repository, the README links to its
  changelog, guide, package pages and entry points.
- **2.1.2** When a version is released, its changelog section exists and is
  the GitHub release's body.
- **2.1.3** When a public package has no page, the repository's docs check
  names it.

## 3. Generated entry points

`cajeta doc` gains a Markdown mode that writes `entry-points.md` from the same
`@EntryPoint` model the HTML index uses: per package, each method's signature
and the first sentence of its comment, linking to its package page.

### 3.1 Use cases

- **3.1.1** When a method gains `@EntryPoint`, the regenerated page lists it
  under its package.
- **3.1.2** When the page is stale against the source, the docs check fails
  and names the method.

## 4. Release notes in the release

`release.yml` (cajeta) and `lib-release.yml` (the libraries) take the release
body from the changelog section of the version being released. A release
whose version has no section is refused before anything builds, as the guard
job refuses a tag outside `release`.

### 4.1 Use cases

- **4.1.1** When v0.40.0 is published, its GitHub release shows the
  `## 0.40.0` section.
- **4.1.2** When `VERSION` names a version with no changelog section, the
  release fails in its first job, naming the missing section.

## 5. Adoption

cajeta first (a `CHANGELOG.md` whose first entry is the release in flight, and
the release-body wiring), then each library in the order its next release
falls. A library is done when its README links all four and the docs check
passes.

## 6. Open questions

- **6.1** Changelog sections: free prose, or the Keep a Changelog headings
  (Added, Changed, Fixed, Removed)? Recommended: the headings, so a release
  body reads the same everywhere.
- **6.2** When are entries written: with each change (into `## Unreleased`),
  or at release time from the commits? Recommended: with each change, since
  the commit that makes a user-visible change knows what it is; the release
  renames `Unreleased` to the version.
- **6.3** Does cajeta keep its numbered `docs/guide/` and `docs/stdlib/`, with
  `docs/packages/` as a new name only for the libraries? Recommended: keep
  cajeta's names, and say in the layout that `stdlib/` is cajeta's
  `packages/`.
- **6.4** v0.40.0 is being cut now (2026-10-11), before this spec can land. Its
  notes: write them by hand into a first `CHANGELOG.md` and paste them into the
  release body after it publishes, or leave v0.40.0 with the fixed body?
  Recommended: by hand, so the first changelog entry is the first release
  that needed one.
