What transfers, and what does not

The kernels are correct on NVIDIA. Every numerical check run today passed, including the wave32 cooperative paths. What does not transfer is the geometry: the block sizes, row-per-wave factors and LDS tile extents were fitted by hand on one gfx1151 part, and three of them are wrong here in ways that are derivable from numbers the driver already reports.

Transfers

Arithmetic and correctness

Wave width is 32 on both parts, so the 44 kernels that hardcode globalIdX() / 32 are accidentally correct here. MXFP4 scalar, fast3, coop and coopQ8 all verify against the reference, and 88 device tests executed on the card without a failure.

0 of 142 failed
Degrades

Block and grid sizing

A 32-thread block caps Ada at half occupancy through a resident-block limit that does not bind on gfx1151. The grid, sized for a 20-WGP part, leaves a 128-SM part two thirds empty.

7.2× swing
Does not run

Most coop variants

Five of six Q4_K coop variants — X1, X3, N256, N256G and the router that picks them — fail at launch with no registered kernel, while Device.kernelAvailable() reports every one of them present. See §9.

5 of 6 absent

The single controlled measurement. The same Q4_K wave mat-vec kernel, moving the same 31.5 MB, reaches 348.8 GB/s at 14336 output rows and 48.4 GB/s at 4096 output rows. Nothing differs but the row count, and therefore the number of workgroups the launcher creates. On gfx1151 both row counts fill the machine; on Ada only the larger one does.

2.5 The tuned path that nothing writes

waveRowsPerBlock() is the one device-aware helper. It recalls a per-machine value through Autotune.recallFor, falls back to a default, and clamps the group to the device thread limit. Three things keep it inert: only q2kQ8Wave calls it, no production code ever writes a value, and the tune directory defaults to empty so the recall is skipped entirely. Its fallback is rpb = 1, so on this box it resolves to a 32-thread group.

03

What llama.cpp configures

llama.cpp answers the same question with an explicit per-architecture parameter table, selected at run time from the compute capability. Nothing in its decode or prefill path is a single constant shared across vendors.

3.1 Decode — the mmvq parameter table

04

The reconciler we already ship, and why it is silent here

cajeta has an occupancy model: occupancy(), occupancyLimiterName(), candidateBlocks(), pickLaunch(), LaunchPick. It is not dead code — KernelManifest.cpp calls it and writes feasibleBlocks and occupancyLimiter into every kernel's manifest, and cajeta source can read them back through KernelManifest.of(name).

It produces nothing on NVIDIA. fillOccupancy() begins if (!lookupArch(archName, model)) return; and the arch table has exactly two rows, both AMD:

constexpr std::array<ArchRow, 2> kArchTable = {{
    {"gfx1151", 32, 1024, 196608, 64, 65536, 32, 4, 2},
    {"gfx1100", 32, 1024, 196608, 64, 65536, 32, 4, 2},
}};

DeviceProfile.cpp:30 — there is no sm_89 row, and no NVIDIA row of any kind.

Measured rather than inferred — a probe compiled for nvptx, asking the manifest on this 4090:

backend            : cuda          mf.waveWidth       : 32

multiprocessors    : 128           mf.ldsStaticBytes  : 0

Two device models, only one of which knows NVIDIA. The runtime model (queryLiveDeviceModel) is correct here and reports everything in §1. The compile-time model (lookupArch) is AMD-only, and the block-size advice is wired to the compile-time one. So the component that would answer "what block should this kernel use" is structurally unable to answer for this part — the same shape as KernelIsa being AMD-only.

The 32-thread block is optimal on gfx1151 and half-rate on Ada, and the reason is a single driver attribute: Ada reports a resident-block cap of 24 per SM, so 24 one-warp blocks fill only 24 of 48 warp slots. gfx1151 reports no such cap. This is the whole mechanism, and it needs no benchmark to see — only the attribute, which the runtime already has.

The coop/tile family, measured

Added 2026-09-19. The coop/tile family is 58 of the 144 kernels and carries the prefill GEMM. Two probes were compiled against the kernel sources so the runtime registry is populated: one asking Device.kernelAvailable() and the manifest for all 58, one launching the six Q4_K variants at prefill shapes.

Three consequences. The four that do have manifests all spill 32 bytes to scratch, which is the failure mode the orders note we cannot otherwise see on NVIDIA without KernelIsa. q4kF16CoopKernel's manifest reports 8,192 B of shared memory where its two Shared<float16>[128 * 72] declarations sum to 36,864 — so §2.6's column describes the source, not the allocation. And QuantKernel.tuneBuildId() is built on KernelManifest.of(...), whose contract returns "none" when the manifest is absent, which would make any Autotune hint unrecallable for a kernel in the 54.

No timing is quoted for this family, deliberately. The one variant that ran returned 119.4 µs at tokens=256 / outDim=14336 / K=4096. That work is 30.1 GFLOP, which implies 252 TFLOPS against the 4090's ~165 TFLOPS dense FP16 peak — impossible, so the harness is measuring something other than execution, most likely not synchronizing the launches it queues. The number is recorded here only as the reason it is not being reported as performance. The registration result above is categorical and does not depend on it.

Open, and worth testing next. Linear latches ten routing decisions from Device.kernelAvailable — q4kWmmaMwKernel, q4kWmmaDeqMw8/Mw4, q6kWmmaDeqMw8/Mw4, q5k, q80, q2k, q3kWmmaDeqMw8 and q6kQ8BatchMatMulKernel. If that predicate lies about those the way it lies about the coop kernels, the engine routes to kernels that never run and the output is silently zero. That is a hypothesis, not a measurement — the Wmma names have not been probed — but it is a candidate mechanism for the standing report that nvptx generation emits garbage tokens.

The portable tier is a correctness escape hatch, not a performance answer. It makes 56 of 58 coop kernels exist on nvptx, and it costs a median 11 KB of scratch per work-item — about 5 MB of local memory per 256-thread block. The portable tile is the scratch, which is the case the compiler's own spill warning already names. The real fix is to resolve the vise: teach the native path non-row-major operands, give the software tier the four native-only operations, or re-tile to row-major.

Two kernels fail on both tiers — q4kF16CoopN256Kernel and q6kF16CoopN256Kernel, the two whose Shared declarations sum to 55,296 B against Ada's 49,152 per-block ceiling. §2 called this correctly; a partial lowering on the native tier briefly made it look wrong.

08

Scope of this report

Measured on the 4090: the device model, the occupancy model's answers, per-format DRAM-cold bandwidth for eight formats at four shapes, llama.cpp's per-type MUL_MAT across five batch widths, MXFP4 numerical parity, and the non-Vulkan device tests.

Read from source, not measured: llama.cpp's parameter tables, and cajeta's launch geometry inventory across all 144 kernels.

Taken from prior records rather than re-measured: gfx1151's achieved bandwidth (~200 GB/s for the Q4_K control, ~238 GB/s roofline) and llama.cpp's 58.4 µs MXFP4 figure there. No AMD hardware is attached to this box, so every gfx1151 number is cited rather than reproduced.

Not covered: Vulkan on NVIDIA, which this host cannot reach; MoE MUL_MAT_ID shapes; and end-to-end tokens per second, which needs the llm CLI path rather than the kernel benches.
